# DISKBEN — файловый и прямой доступ к дискам MXOS

В штатной банковой сборке DOS остаётся в собственной странице, memtop основной памяти равен 8BFFh. Сохранённый вызов C8DBh не выгружает банковую DOS. LOW/HIGH-буферы бенчмарка находятся в доступной программе памяти.

При запуске утилита включает KOI-8, сохраняя исходный режим. При обычном выходе восстанавливаются режим KOI и стек вызывающей программы.

`DISKBEN.COM` запускается с 0000h. Аргументы запуска и слова в интерактивных полях выделяет штатный `bios_argNext`. Недостающие параметры вводятся через `bios_input`, выход — `Press any key to exit` через `bios_getch`. Сборка входит в `build: OS`.

В штатной банковой системе B: использует общий CPM16. RAMD.COM подготавливает том, не устанавливая прежний отдельный резидент R4. Исторические алгоритмы сравниваются автономным COPYBEN; результаты DISKBEN включают текущую обвязку BIOS/DOS.

## Параметры

```text
DISKBEN H: -C=0 -W=1 -S=8
DISKBEN B: -C=1 -W=3 -S=24
DISKBEN H: -W=0
DISKBEN -?
```

| Аргумент | Значение |
|---|---|
| `A:`…`H:` | Тестируемый диск |
| `-C=0/1/2` | Без дополнительной проверки / проверка всего файла / посекторная проверка RAW |
| `-W=0..9` | Число проходов записи с сопутствующим чтением; 0 — только RAW-чтение |
| `-S=1..24` | Размер тестового файла в КиБ (1024 байта); `-S=8` означает 8192 байта |
| `-?` | Справка |

Порядок аргументов произвольный, регистр ключей и буквы диска не важен. Числа десятичные; дублирующиеся параметры, неизвестные ключи и значения вне диапазона отклоняются до выбора диска и начала тестов. Для пропущенного параметра остаётся интерактивный вопрос. Если явно задано `-W=0` или носитель доступен только для чтения, вопросы о проверке и размере файла не задаются: файл не создаётся. В этом режиме `-S` не меняет фиксированный объём RAW-чтения. Нажатие клавиши в конце результата сохраняется и при полностью заданных аргументах.

Технология и возможности берутся из B=FFh физического драйвера. Для записи выбираются число проходов 0–9 и размер 1–24 КиБ (Enter = 8). Размер задаёт число кластеров и объём расчёта скорости. Текущий формат: кластер = сектор = 256 байт; число кластеров равно КиБ × 4. FAT12/FAT32 не добавляются.

Режимы записи:

- 0: обычный B=1; завершение записи — штатные барьеры драйвера/DOS.
- 1: весь файл записывается B=1, затем читается и побайтово сравнивается с оригинальным буфером. Проверка реализована в приложении и не прерывает конвейер записи. Режим доступен также RAMD, без физического B=5.
- 2: посекторный RAW B=5, только при DISK_CAP_VERIFY. Запись каждого физического сектора завершается и проверяется до следующей. Для DOS WRITE банкового ядра проверяется готовый файл целиком, как в режиме 1; это не проверка каждого сектора FAT/каталога.

Режим 1 проверяет данные файла через DOS либо Raw после завершения всей записи. Оригинал остаётся в ОЗУ до завершения проверки. Оба варианта проверки входят в итог WRITE; VERIFY — часть WRITE, а не добавочное время.

## Порядок операций

Каждый проход создаёт настоящий `DISKBEN.TMP` через `bios_fileCreate`, измеряет чтение того же файла через DOS, затем прямые запись и чтение тех же кластеров. Удаление выполняется только после всех чтений и сравнений, вне замеров. File WRITE включает распределение кластеров, данные, FAT, каталог и flush. Raw использует готовую FAT-цепочку; построение списка секторов вне замера.

Перед каждой серией RAW выполняется подготовительный запрос: первый сектор читается в отдельный временный буфер до запуска таймера. Он подготавливает локальный маршрут драйвера и при необходимости копию службы H:, сохраняя исходный файл и проверочный буфер. Такая подготовка после flush перед полной RAW-проверкой также исключена из VERIFY/WRITE. Измеряемый объём не увеличивается: каждый сектор затем участвует в обычном цикле. Это подготовка физического маршрута, а не прогрев файлового кэша: дополнительных `fread` и пробных файлов нет. DOS READ/WRITE измеряют файловую операцию целиком, включая поиск имени, FAT, каталог и flush там, где они нужны. Посекторный режим `-C=2` сохраняет цену каждого B=5 и его проверки.

Перед каждым проходом печатается `Pass i/N`, после удаления — `done`. Сводка показывает диск, метку, технологию, драйвер, режим, размер и кластеры. Существующий DISKBEN.TMP не заменяется: его надо удалить или переименовать. При ошибке делается попытка удалить только собственный временный файл. Все записи расходуют ресурс flash.

## LOW и прямой HIGH на A:

На A: измеряются READ LOW/HIGH и Raw WRITE LOW/HIGH. Для WRITE HIGH источник действительно находится в 8200h..8BFFh; подготовка порций из нижнего оригинала исключена из WRITE. Файловая запись DOS измеряется отдельно из LOW и HIGH. Для B:–H: остаются обычные READ и WRITE, без подписей Buffer LOW/HIGH.

LOW — полный буфер от 2000h до 7FFFh максимум (24 КиБ). Для чтения ROM в нижнюю память драйвер переключает ROM/RAM; текущий FlashSys переносит пары байтов через регистры. HIGH — прямое чтение в 8200h..8BFFh порциями до 2560 байт. ROM-источник и верхнее назначение одновременно видны CPU; FlashSys использует `bios_memcpy_bc_hl`. Дополнительной копии HIGH → LOW в замере нет.

Файловый HIGH читает описание через `bios_fileLoadInfo`, затем передаёт порции через `bios_fileStream` (A=2, BC=байты, DE=курсор). Raw читает те же секторы непосредственно драйвером. Порции сравниваются с оригинальным нижним буфером, после чего верхнее окно используется повторно. Сравнение исключено из READ. Так весь выбранный файл измеряется без размещения его поверх экрана, системных переменных или DOS. HIGH — потоковый верхний буфер; полный файл одним вызовом `bios_fileLoad2` в верхнее ОЗУ не загружается.

Полная проверка записи использует этот же верхний потоковый буфер. При ней побайтовое сравнение с сохранённым оригиналом включено во время VERIFY/WRITE. Перед чтением верхнее окно заполняется противоположными данными вне замера, чтобы старое содержимое не могло скрыть отсутствие реального чтения. Время VERIFY в сводке показывается отдельно для LOW и HIGH; оно включено в соответствующий WRITE.

## Вывод и flush

```text
Raw access: direct writing/reading of sectors
READ:  ... ms   ... KiB/s
WRITE: ... ms   ... KiB/s
VERIFY: ... ms (included in WRITE)
FLUSH: ... ms   ... times

File access: writing and reading file with DOS
READ:  ... ms   ... KiB/s
WRITE: ... ms   ... KiB/s
VERIFY: ... ms (included in WRITE)
FLUSH: ... ms   ... times
```

На A: сначала идут READ LOW / READ HIGH, затем WRITE LOW. VERIFY показывается только для полной проверки файла. FLUSH — только при DISK_CAP_FLUSH. Между столбцами выводится TAB, поле времени дополнено до 8 знаков. Скорость — КиБ/с (1024 байта/с), время — мс с тремя знаками после точки.

`bios_fileCreate` завершает запись данных и FAT/каталога общим физическим барьером: один B=4 на файл у FlashFst. Верхний вариант дополнительно использует барьер подготовки перед потоковой записью. Raw вызывает один B=4 после всего пакета. Внутри секторного цикла B=4 не вызывается. Запись FileStream завершается явным `bios_flushVolume`; копирование DOS вызывает его в конце операции. B=5 синхронно ждёт каждый сектор, но это не дополнительные B=4. FLUSH уже включён в WRITE, повторно прибавлять его не нужно.

Для ROM или нулевого бюджета сохраняется отдельный старый тест физического чтения без TMP: 32 прохода по 32 секторам. Для зарезервированных Floppy/HDD остался случайный порядок этого чтения; реальных драйверов он не добавляет.

## Таймер и память

ВИ53 вызывается через `bios_timerInit`/`bios_timerRead`. Общая библиотека `source/include/timing.inc` содержит накопление U32 тиков, пересчёт в мс и десятичную печать, совместно с LLM80. CLK1 задаётся сборкой: 2 или 2,5 МГц. Между отсчётами должно быть меньше оборота канала 2 (8,39 с при 2 МГц). Цена таймера/обёртки включена; печать, заполнение буферов, контрольное сравнение обычного READ и удаление исключены.

Код ограничен 2000h. Полный исходный буфер — 2000h..7FFFh максимум, временный сектор FAT — 8000h..80FFh, верхнее окно — 8200h..8BFFh. SP=8FDFh; окно не пересекает резерв стека для B=5. Исходный нижний буфер не перезаписывается во время полной проверки или прямого HIGH-чтения.

Проверки: `scripts/emu80/check-diskbench-readback.py` и `scripts/emu80/benchmark-disks.py`. Измерения Emu80 не заменяют измерение платы. Матрица `docs/diskbench/matrix-001` содержит старый HIGH со staging; для прямого HIGH используются отчёты начиная с `matrix-002`.

Изолированная сборка для `docs/diskbench/cache-005` задаёт MAX_FILE_KIB=8, sectorBuffer=1600h, fatBuffer=FE00h, highBuffer=FB00h, HIGH_SECTORS=3. Файл занимает 1600h–35FFh, таблица слотов 1300h–15BFh, кэш 22 КиБ — 3600h–8DFFh. Верхнее окно и сектор FAT используют освобождённые FB00h–FEFFh. Это позволяет вместить файл 8 КиБ и всю FAT/root H: одновременно. В cache-005 измерены только 22 КиБ; прежние 1/4 КиБ взяты из cache-004, с явной оговоркой о различии размещения в сравнительном отчёте. Адреса проверяются ASSERT и сценарием; обычная сборка не меняет свои буферы.

Исправлено вычисление конца буфера после ввода размера: сравнение охватывает ровно файл, без лишнего сектора. Прежний I/O ERROR после успешного чтения возникал из-за сравнения этого лишнего сектора.

Свойства диска выведены таблицей с TAB между параметром и значением:
диск, метка, технология, драйвер, ёмкость в КиБ, байт на сектор,
секторов на кластер, режим, буферы и число проходов.

Для отображаемого диска измеряются File WRITE LOW и HIGH. HIGH создаёт
файл через bios_fileCreatePrepare и передаёт всё его содержимое порциями
из верхнего окна через FileStream; выделение FAT/каталога и окончательный
bios_flushVolume входят в WRITE, заполнение верхнего источника исключено.
Предыдущая тестовая копия удаляется до замера. Все Raw/File используют
одинаковый шаблон и размер; Raw работает с цепочкой последней копии.
Полная проверка файла включается выбранным режимом, её время отдельно
показывается для LOW и HIGH и уже включено в соответствующий WRITE.

Raw HIGH A: использует одно отображение flash и новый bios_memcpy вместо
переключения страниц на каждой паре байтов нижнего буфера. Проверка в Emu80
при 2 МГц: прямой вызов драйвера с обвязкой — 12434 такта/сектор LOW,
5649 HIGH (40,2 / 88,5 КиБ/с). Поэтому 76 КиБ/с в полном Raw HIGH тесте
само по себе не означает ошибку измерения. Это эмуляторные результаты;
для реальной платы отдельно нужны измерения и проверка тактирования ВИ53.

Табуляция BIOS — фиксированный сдвиг на четыре символа. Подписи дополнены
до кратной четырём длины, затем число TAB подобрано до общей колонки:
значения свойств начинаются с колонки 24 (считая с нуля), поле времени —
с колонки 16. Целая часть времени выравнивается вправо в поле шириной 8,
поэтому десятичные точки стоят друг под другом.


С 07.11.2026 скорость выводится в `KiB/s` (1 КиБ = 1024 байта), как в исторических таблицах ченджлога. Размеры файлов и ёмкости уже были в КиБ. Сначала делится исходный числитель на тики, затем дважды делится остаток ×10; напечатанные миллисекунды в расчёте скорости не используются. Два знака округляются вниз. Константа `floor(CLK1/1024)` даёт относительную погрешность менее 0,017% при 2/2,5 МГц.
