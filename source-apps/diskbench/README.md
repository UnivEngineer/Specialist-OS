# DiskBen — дисковый бенчмарк MXOS

Актуальные результаты полной матрицы находятся в разделе [Последняя полная матрица](#последняя-полная-матрица) этого README. Это постоянное место для свежей проверенной версии; при новом прогоне обновляются дата, параметры сборки и таблицы. Сырые результаты, снимки экрана и замороженные входы сохраняются отдельно в локальном отчёте с датой. Незавершённый прогон не заменяет опубликованную матрицу.

## Запуск

В образе H: бенчмарк находится в `H:\BENCH\DISKBEN\DISKBEN.COM`. Контроллер запускается в MAIN с 0000h; измерители DiskMain.dll, DiskDos.dll и DiskBank.dll лежат рядом. Весь каталог BENCH можно перенести на H: без пересборки: контроллер ищет модули на диске своего запуска, независимо от выбранного для измерений диска. Контроллер и DiskMain.dll загружаются с политикой MANAGED. Для BPB и сводки ALL контроллер регистрирует 512 байт в MAIN. Для прохода MAIN он увеличивает этот буфер до запрошенного размера с учётом смещения, сохраняя системную резервацию шрифта. DiskDos.dll резервирует 8 КиБ и байт смещения через поле BSS заголовка. Сборка входит в `scripts/build/build-project.ps1 OS`. Интерактивное меню сначала спрашивает диск, затем исполнителя; для драйвера с PIO также выбирается выравнивание буфера. Способ доступа (RAW, FILE или ALL) и проверка записи задаются отдельно. Затем задаются число проходов, размер и размещение файла. Все поля используют `bios_input`; Enter выбирает значение по умолчанию. После `Press any key to exit` восстанавливаются режим KOI-8 и стек, печатается перевод строки.

```text
H:\BENCH\DiskBen\DiskBen.com
H:\BENCH\DiskBen\DiskBen.com H: -C:ALL -M:ALL -B:UNALIGNED -V=1 -W=1 -S=8 -F=0
H:\BENCH\DiskBen\DiskBen.com B: -C:DOS -M:FILE -V=2 -W=1 -S=8 -F=1
```

| Ключ | Назначение |
|---|---|
| `A:`…`H:` | Диск; без аргумента — интерактивный выбор |
| `-C:MAIN/DOS/BANK/ALL` | Где исполняется измеритель; без аргумента — вопрос, Enter = MAIN; ALL последовательно проверяет все три размещения |
| `-M:RAW/FILE/ALL` | Физические сектора / файловый API / оба. Интерактивно задаётся отдельный вопрос. Enter выбирает FILE для дисковода и ALL для остальных носителей |
| `-B:ALIGNED/UNALIGNED` | Буфер выровнен на 256 байт / смещён на +1; для драйвера с PIO без ключа задаётся вопрос, Enter = ALIGNED; иначе ALIGNED без вопроса |
| `-V=0/1/2` | Без проверки / перечитывание всего записанного блока или файла / посекторная проверка драйвером B=5 |
| `-W=0..9` | Проходы записи и чтения; Enter = 1; 0 — только чтение |
| `-S=1..24` | Размер файла в КиБ; Enter = 8; DOS и ALL ограничены 8 КиБ |
| `-F=0/1` | Последовательное / псевдослучайное выделение кластеров; Enter = 0 |
| `-?` | Справка |

Порядок аргументов и регистр не важны. Для пропущенных параметров остаётся интерактивный вопрос. При `-W=0` либо на ROM вопросы о записи, размере и размещении пропускаются; выполняются три чтения по 8 КиБ без создания файла. FILE READ требует уже существующего DISKBEN.TMP достаточной длины, иначе выводится прочерк. Чужой DISKBEN.TMP никогда не заменяется: перед тестом записи его нужно убрать вручную. Все записи расходуют ресурс flash.

Если запрошенный размер MAIN пересекается с системной резервацией, DISKBEN выводит «NOT ENOUGH MEMORY» до запуска измерителя. Для DOS лимит 8 КиБ задаёт арена банка DOS. ALL использует этот же лимит для всех трёх измерителей, чтобы сравнивать одинаковый объём данных.

На дискете FAT12 с секторами 512 байт режим по умолчанию — FILE. Для теста записи с проверкой запустите `H:\BENCH\DISKBEN\DISKBEN.COM A: -C:MAIN -M:FILE -S=4 -W=1 -V=1 -F=0`. RAW на дисководе передаёт полные физические сектора по 512 байт через RAW_IO в банк DOS. Перед записью DISKBEN получает список LBA собственного временного файла по курсору FILEHANDLE, включая фрагментированные цепочки. Время построения списка исключено из измерения. В модели ВГ93 Emu80 команды SEEK и начало передачи сектора не ждут механического перемещения головки и поворота диска.

## Что измеряется

FILE использует штатный `MXOS_DOS_FILEHANDLE`. Перед запуском теста с записью DOS считает свободные кластеры. DISKBEN проверяет, что их хватит для одного DISKBEN.TMP с выбранным размером и геометрией тома. Это относится и к RAW, который пишет только в цепочку временного файла. При нехватке места выводится «Disk is full» до создания файла. Тест только на чтение пропускает проверку. Ошибки DOS при подготовке и выполнении теста выводятся по [справочнику DOS](../../source/dos/README.md#ошибки-файловых-операций).

Перед замером создаётся DISKBEN.TMP, SEEK к последнему байту и запись байта выделяют всю цепочку; CLOSE сохраняет метаданные. Создание, выделение кластеров и искусственное случайное размещение исключены из таймера. Измеряемая запись открывает готовый файл без CREATE/TRUNCATE, одним WRITE передаёт весь локальный буфер, выполняет FLUSH/CLOSE. Чтение повторно открывает тот же файл и одним READ получает весь буфер. Открытие, обработка FAT/каталога, закрытие и финальный flush входят в FILE; это перезапись подготовленного файла, а не скорость создания нового файла с нуля.

RAW получает список физических секторов той же цепочки до начала отсчёта. Для C:, B: и H: он также получает локальный вход драйвера через RAW_OP_PREPARE. Для дисковода каждый запрос идёт через RAW_IO. Цикл обмена не обращается к DOS за метаданными каждого сектора. Подготовка списка и маршрута не входит в RAW, поэтому RAW показывает скорость готовой физической серии. Для сравнения полного прикладного запроса следует использовать FILE. Неполные файловые сектора остаются под управлением DOS; размер тестового файла кратен физическому сектору.

Заполнение шаблона, обычное сравнение READ, печать, загрузка DLL, пересылка настроек/результатов и удаление файла исключены из измерения. После всех чтений, записей и проверок удаляется только собственный временный файл. В ALL метаданные остаются в общем кэше между MAIN, DOS и BANK; это не три холодных старта.

`F=0/1` описывает размещение цепочки, а не порядок пользовательских seek-запросов: данные всегда передаются по порядку файла. При F=1 штатный распределитель выбирает кластеры от псевдослучайных позиций. F=0 на заполненном томе тоже может использовать дырки; AT2MXF дополнительно чередует чипы, поэтому последовательное размещение логических данных не гарантирует соседние физические LBA.

## Проверка записи и flush

- V=0: B=1 и штатные барьеры завершения записи.
- V=1: обычный WRITE, затем полное чтение и побайтовое сравнение с исходным буфером. Для FILE повторно используется файловый API; для RAW — подготовленный список LBA. Сохраняются и обычный WRITE, и время проверки, поэтому один прогон даёт WRITE и WRITE+VERIFY. RAW-проверка относится к блоку данных, а не к файловой системе.
- V=2: B=5 завершает и проверяет каждый физический сектор. FILEHANDLE включает соответствующую настройку DOS на время измерителя и восстанавливает её при выходе; полные сектора проверяются локальным драйвером у буфера клиента. Поддержка требуется от драйвера. Это также не означает проверки каждого сектора FAT/каталога.

Завершающий flush входит в WRITE; его нельзя прибавлять ещё раз. RAW вызывает физический B=4 один раз после всей серии при DISK_CAP_FLUSH, FILE выполняет штатный FILEHANDLE FLUSH/CLOSE. Отдельная строка FLUSH показывается только при наличии DISK_CAP_FLUSH; для B=5 завершение и проверка сектора уже включены в WRITE. VERIFY для V=1 показывается отдельно и включается в сумму WRITE+VERIFY.

## Исполнитель, буферы и таймер

MAIN, DOS и BANK — расположение вызывающего кода и полного буфера, а не способ доступа к файлу. FILE во всех трёх случаях использует общий MXOS_CALL_REGS; ядро DOS пакетирует полные сектора и передаёт их локальному обработчику банка буфера. C: использует отображённое системное ROM/flash, B: — общий CPM32, H: — установленный локальный PIO-драйвер. RAMDISK.COM подготавливает B:, самостоятельный старый резидент R4 не устанавливается. Исторические копировщики сравниваются в COPYBEN.

| Исполнитель | Код и буфер |
|---|---|
| MAIN | DiskMain.dll с 21C0h, буфер с 2B00h. До 24 КиБ при доступной MAIN, до 14 КиБ со штатным 6×8/Fast |
| DOS | DiskDos.dll в арене DOS, полный буфер 8 КиБ и байт для смещения; файл до 8 КиБ |
| BANK | DiskBank.dll в отдельном EXEC-банке, полный буфер с 2000h; файл до 24 КиБ |

DOS-модуль запрашивает свой интервал через MODULE_TARGET_DOS. Его можно запустить из BAT. Если интервал занимает кэш сценария, DOS освобождает его и сохраняет смещение следующей строки. Пересечение с закреплённой DLL или активным установщиком драйвера возвращает ошибку. ALL использует общий предел 8 КиБ. После MODULE_UNLOAD область освобождается; RETAIN не используется. Пакет результатов 3×88 байт хранится в MAIN с 21C0h после выгрузки MAIN-модуля.

Для драйвера с отображаемым окном (штатно C:) RAW MAIN отдельно измеряет HIGH и LOW. HIGH использует первые 256 байт экрана с 9000h и дополнительный байт для UNALIGNED. Снимок хранится в начале LOW-буфера, отдельно от списка LBA. LOW использует буфер в нижней половине MAIN, перекрываемой ROM. Подготовка порций HIGH и контрольное сравнение вне таймера. FILE MAIN для того же драйвера автоматически измеряет LOW и HIGH на том же подготовленном файле. HIGH — целый буфер до 8 КиБ в экране 9000h–AFFFh (для UNALIGNED — до B000h включительно); экран сохраняется в уже отработавший LOW-буфер и восстанавливается вне таймера, включая ошибочный выход. Перед FILE HIGH выводится `HIGH USES SCREEN BUFFER`. Перед заполнением экранного буфера в IO_COLOR записывается 0, чтобы тестовые данные не выглядели как мусор на экране; перед восстановлением байтов возвращается COLOR_BIOS. Открытие и обмен выполняются обычным FILEHANDLE одним запросом на весь буфер. Для файла больше 8 КиБ HIGH пропускается, LOW сохраняет прежний предел 24 КиБ. DOS/BANK используют свой полный локальный буфер. Выравнивание применяется ко всему файлу, а на C: также к HIGH-окну. В матрице отдельные варианты выравнивания нужны только для H:; явный UNALIGNED на C:/B: оставлен для диагностики.

Контроллер получает `TIMER_RAW` на время вызова модуля измерений и освобождает его после возврата. Исполнитель задаёт делитель через `timing-pit.inc` и ждёт начала счёта перед серией обменов. Прямой вызов `io_pitRead` занимает 71 такт 8080 в MAIN, DOS и EXEC. Разности накапливает `timing-counter.inc`, пересчёт и печать используют `timing.inc`. Время выводится в миллисекундах с тремя знаками после точки, скорость в КиБ/с (1024 байта/с). При 2 МГц полный оборот счётчика 2 занимает около 8,39 с с делителем 256 и 33,55 с с делителем 1024 для дискет и разбросанных цепочек. Расширенный диапазон пересчитывается в эквивалентные тики по 128 мкс. [Интерфейс измерительного таймера](../../sdk/asm/lib/timing.md)

## Воспроизведение матрицы

Для сценариев `check-diskbench-alignment.py` и `check-diskbench-selective.py` соберите отдельный H: командой `scripts/images/build-image.ps1 Games2M -ManifestFile scripts/emu80/fixtures/DiskBench-H.txt`. В `images/DiskBench-H.bin` есть свободная запись корня для `DISKBEN.TMP`. Сценарий выравнивания пропускает загрузку службы дисковода в копии системного образа, чтобы освободить область DOS для DiskDos.dll.

`check-matrix.py` сохраняет замороженные бинарники, образы и SHA-256 до запуска. Ввод идёт обычными клавишами через NC в собственный видимый Emu80 с отключённым звуком. Порт и runtime задаются явно. Один flash-экземпляр используется для всей серии A:/B:/H:, драйвер H: заменяется запуском COM. ROM проверяется на двух отдельных образах с заранее подготовленным DISKBEN.TMP и без установки AT512KS. После тестов проверяются возврат в NC, восстановление FAT A:/H: и неизменность ROM. В finally закрывается только собственный эмулятор. `--resume` продолжает незавершённую матрицу по сохранённым входам с проверкой SHA-256.

```powershell
python source-apps/diskbench/check-matrix.py --runtime .local/rom-pio-19782 --port 19782 --output docs/diskbench/full-matrix-YYYY-MM-DD
```

После успешного прогона таблицы в постоянном разделе README обновляются командой `python source-apps/diskbench/publish-matrix.py docs/diskbench/full-matrix-YYYY-MM-DD/matrix.json`. Публикация отклоняет незавершённый JSON и проверяет полноту строк.

Матрица охватывает ROM-SYS и AT512KS на A:, CPM32 на B:, AT2MX и AT2MXF на H:, исполнителей MAIN/DOS/BANK, последовательное/случайное размещение, V=0/1/2 и оба выравнивания H:. Размер — 8 КиБ, по одному проходу записи, ROM — три чтения. RAW READ повторяется как контроль; основной результат V=1 сразу содержит WRITE и WRITE+VERIFY. Сырые строки сохраняются без сведения близких результатов; таблицы ниже могут объединять их явно указанной медианой. Результаты эмулятора не заменяют измерения платы.

FILE: READ — медиана повторов режимов проверки; WRITE — V=0; секторная проверка — V=2; полное чтение и сравнение файла — V=1. В READ A: два числа означают ROM-SYS / AT512KS; запись относится только к AT512KS. Они читают разные заранее подготовленные цепочки, поэтому различие FILE READ не приписывается только коду физического драйвера. MAIN A: включает отдельные LOW и HIGH. Для FILE HIGH целый буфер 8 КиБ находится в экране с 9000h; его сохранение/восстановление исключены из таймера. MAIN, DOS и BANK показаны отдельно, без скрытого усреднения между страницами.

Последовательное/случайное означает способ выделения кластеров; во всех случаях читается и записывается весь файл по порядку. Создание и размещение цепочки, удаление и подготовка RAW исключены из замера; FILE включает открытие, передачу целого буфера, метаданные и закрытие, WRITE — также финальный flush. Для V=1 один запуск сохраняет и обычный WRITE, и WRITE+VERIFY; таблица использует V=0 как независимую контрольную скорость обычной записи. Подробные временные интервалы, отдельный flush и все исходные значения остаются в matrix.json локального отчёта.

Дополнение MAIN HIGH для A: измерено отдельным прогоном той же даты. Все строки A: обновлены; результаты B:/H: сохранены из исходной полной матрицы. BIOS, DOS, IO, MEM и физические драйверы в обоих прогонах побайтно совпадали. Изменён только измеритель и его вывод.
