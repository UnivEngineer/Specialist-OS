# DISKBEN — файловый и прямой доступ к дискам MXOS

`DISKBEN.COM` запускается с 0000h. Параметры вводятся штатным `bios_input`,
выход — `Press any key to exit` через `bios_getch`. Сборка входит в `build: OS`.

Для сравнения RAM-драйверов загрузитесь с пропуском AUTOEXEC (Shift при старте)
и сначала измерьте B: со встроенным `RAMD / Per-byte`,
затем вручную запустите `A:RAMD.COM` и повторите с `RAMD / R4 banked`.
Параметры обоих прогонов должны совпадать. При обычной загрузке RAMD.COM
устанавливается автоматически из AUTOEXEC.

## Параметры

Технология и возможности берутся из B=FFh физического драйвера. Для записи
выбираются число проходов 0–9 и размер 1–24 КиБ (Enter = 8). Размер задаёт
число кластеров и объём расчёта скорости. Текущий формат: кластер = сектор =
256 байт; число кластеров равно КиБ × 4. FAT12/FAT32 не добавляются.

Режимы записи:

- 0: обычный B=1; завершение записи — штатные барьеры драйвера/DOS.
- 1: весь файл записывается B=1, затем читается и побайтово сравнивается с
  оригинальным буфером. Проверка реализована в приложении и не прерывает
  конвейер записи. Режим доступен также RAMD, без физического B=5.
- 2: посекторный B=5, только при DISK_CAP_VERIFY. Драйвер завершает и
  проверяет каждый сектор до следующей записи. Для File WRITE проверяются
  также записываемые секторы метаданных. Это исходный режим сравнения.

Режим 1 проверяет данные файла через DOS либо Raw; он не сравнивает каждый
физический сектор FAT/каталога как B=5. Оригинал остаётся в ОЗУ до завершения
проверки. Оба варианта проверки входят в итог WRITE. Для режима 1 отдельно
показывается VERIFY — часть WRITE, а не добавочное время.

## Порядок операций

Каждый проход создаёт настоящий `DISKBEN.TMP` через `bios_fileCreate`, измеряет
чтение того же файла через DOS, затем прямые запись и чтение тех же кластеров.
Удаление выполняется только после всех чтений и сравнений, вне замеров.
File WRITE включает распределение кластеров, данные, FAT, каталог и flush.
Raw использует готовую FAT-цепочку; построение списка секторов вне замера.

Перед каждым проходом печатается `Pass i/N`, после удаления — `done`.
Сводка показывает диск, метку, технологию, драйвер, режим, размер и кластеры.
Существующий DISKBEN.TMP не заменяется: его надо удалить или переименовать.
При ошибке делается попытка удалить только собственный временный файл.
Все записи расходуют ресурс flash.

## LOW и прямой HIGH на A:

На A: измеряются READ LOW/HIGH и Raw WRITE LOW/HIGH. Для WRITE HIGH
источник действительно находится в 8200h..8DFFh; подготовка порций из нижнего
оригинала исключена из WRITE. Файловая запись DOS пока выполняется из LOW.
Для B:–H: остаются обычные READ и WRITE, без подписей Buffer LOW/HIGH.

LOW — полный буфер от 2000h до 7FFFh максимум (24 КиБ). Для чтения ROM в
нижнюю память драйвер переключает ROM/RAM; текущий FlashSys переносит пары
байтов через регистры. HIGH — прямое чтение в 8200h..8DFFh порциями до 3 КиБ.
ROM-источник и верхнее назначение одновременно видны CPU; FlashSys использует
`bios_memcpy_bc_hl`. Дополнительной копии HIGH → LOW в замере нет.

Файловый HIGH читает описание через `bios_fileLoadInfo`, затем передаёт
порции через штатный `bios_fileTransfer` (B=2). Raw читает те же секторы
непосредственно драйвером. Порции сравниваются с оригинальным нижним буфером,
после чего верхнее окно используется повторно. Сравнение исключено из READ.
Так весь выбранный файл измеряется без размещения его поверх экрана,
системных переменных или DOS. HIGH — потоковый верхний буфер; полный файл
одним вызовом `bios_fileLoad2` в верхнее ОЗУ не загружается.

Полная проверка записи использует этот же верхний потоковый буфер. При ней
побайтовое сравнение с сохранённым оригиналом включено во время VERIFY/WRITE.
Перед чтением верхнее окно заполняется противоположными данными вне замера,
чтобы старое содержимое не могло скрыть отсутствие реального чтения.
Время VERIFY в сводке относится к записи из LOW; полное WRITE HIGH уже
включает собственную проверку при выборе режима 1.

## Вывод и flush

```text
Raw access: direct writing/reading of sectors
READ:  ... ms   ... kB/s
WRITE: ... ms   ... kB/s
VERIFY: ... ms (included in WRITE)
FLUSH: ... ms   ... times

File access: writing and reading file with DOS
READ:  ... ms   ... kB/s
WRITE: ... ms   ... kB/s
VERIFY: ... ms (included in WRITE)
FLUSH: ... ms   ... times
```

На A: сначала идут READ LOW / READ HIGH, затем WRITE LOW. VERIFY показывается
только для полной проверки файла. FLUSH — только при DISK_CAP_FLUSH. Между
столбцами выводится TAB, поле времени дополнено до 8 знаков. Скорость —
десятичные кБ/с (1000 байт/с), время — целые мс.

`bios_fileCreate` вызывает физический барьер после данных и после сброса
FAT/каталога: два B=4 на файл у FlashFst. Raw вызывает один B=4 после всего
пакета. Внутри секторного цикла B=4 не вызывается. Общий `bios_fileTransfer`
с B=1 завершает барьером каждую переданную партию; NC сейчас пишет партиями
до 32 КиБ. B=5 синхронно ждёт каждый сектор, но это не дополнительные B=4.
FLUSH уже включён в WRITE, повторно прибавлять его не нужно.

Для ROM или нулевого бюджета сохраняется отдельный старый тест физического
чтения без TMP: 32 прохода по 32 секторам. Для зарезервированных Floppy/HDD
остался случайный порядок этого чтения; реальных драйверов он не добавляет.

## Таймер и память

ВИ53 вызывается через `bios_timerInit`/`bios_timerRead`. Общая библиотека
`source/include/timing.inc` содержит накопление U32 тиков, пересчёт в мс и
десятичную печать, совместно с LLM80. CLK1 задаётся сборкой: 2 или 2,5 МГц.
Между отсчётами должно быть меньше оборота канала 2 (8,39 с при 2 МГц).
Цена таймера/обёртки включена; печать, заполнение буферов, контрольное
сравнение обычного READ и удаление исключены.

Код ограничен 2000h. Полный исходный буфер — 2000h..7FFFh максимум,
временный сектор FAT — 8000h..80FFh, верхнее окно — 8200h..8DFFh.
SP=8FDFh; окно не пересекает резерв стека для B=5. Исходный нижний буфер
не перезаписывается во время полной проверки или прямого HIGH-чтения.

Проверки: `scripts/emu80/check-diskbench-readback.py` и
`scripts/emu80/benchmark-disks.py`. Измерения Emu80 не заменяют измерение платы.
Матрица `docs/diskbench/matrix-001` содержит старый HIGH со staging; для
прямого HIGH используются отчёты начиная с `matrix-002`.

Изолированная сборка для `docs/diskbench/cache-005` задаёт MAX_FILE_KIB=8,
sectorBuffer=1600h, fatBuffer=FE00h, highBuffer=FB00h, HIGH_SECTORS=3.
Файл занимает 1600h–35FFh, таблица слотов 1300h–15BFh, кэш 22 КиБ —
3600h–8DFFh. Верхнее окно и сектор FAT используют освобождённые FB00h–FEFFh.
Это позволяет вместить файл 8 КиБ и всю FAT/root H: одновременно.
В cache-005 измерены только 22 КиБ; прежние 1/4 КиБ взяты из cache-004,
с явной оговоркой о различии размещения в сравнительном отчёте.
Адреса проверяются ASSERT и сценарием; обычная сборка не меняет свои буферы.
