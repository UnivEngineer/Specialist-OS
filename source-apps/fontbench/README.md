# Бенчмарки рендера шрифтов

## FontBen.com: общая сетка ABI/API

FontBen.com, FontBank.com, TextBen.com, TextBank.com, справка Readme.txt в KOI8-R и DLL движков находятся в `A:\Bench\FontBen\`. FontBank.com — самостоятельная банковая программа, которая создаёт свой текстовый буфер и выполняет измеряемые вызовы через MXOS_CALL. Движки Engine6.dll, EngineP.dll, EngineM.dll, EngineB.dll, Engine4.dll и EngineS.dll загружаются штатным MODULE_LOAD в MAIN; самостоятельно они не запускаются.

Каждый выбранный standalone-движок испытывается через одну и ту же сетку из пяти функций: `printChar`, `printCharRaw`, `printStringZ`, `printStringRawZ`, `printStringRawLim`. Перед этапом FontBen подменяет пять публичных JMP BIOS и восемь адресов в таблице MXOS_CALL, включая MAIN-варианты строковых функций. Общие строковые обёртки вызывают выбранное локальное пиксельное ядро; они обрабатывают терминатор, длину, управляющие коды и неполные группы. Поэтому измеряется весь публичный вызов, а не один пиксельный цикл. После этапа, перед отчётом, при ошибке и перед выгрузкой DLL исходные адреса восстанавливаются. Вариант BIOS использует установленный системный движок без подмены.

MAIN вызывает публичный BIOS ABI напрямую. BANK выполняет MXOS_CALL: посимвольно с исходным протоколом COMMAND или TEXT; строкой через автоматическую нарезку Win20, общий 256-байтный буфер BIOS либо собственный MAIN-буфер, выделенный через ARENA/ALLOC. Переходники Win20/Far256 вызывают публичные входы и поэтому используют тот же выбранный движок. Переносы и накладные расходы MXOS_CALL входят в измерение. На один движок приходится 18 измерений для одного состояния пререндера или 36 для обоих; неприменимые клетки обозначаются прочерком.

Корпус — 24 блока по 46 печатных байтов из `A:\README.TXT` и CRLF: 1152 байта, затем NUL. Обычный вывод обрабатывает CRLF; Raw рисует их как глифы и переносится по краю экрана. RawChar выводит и код 00h; RawZ останавливается на NUL; RawLim печатает ровно BC байт. 6×8 и 8×8 используют все 256 глифов установленного FONT.FNT, скопированного в локальную раскладку движка. 4×8 использует знакогенератор порта CP/M. В компактных PACKED/BLOCK32 отсутствующие глифы обслуживает локальный полный посимвольный путь: корпус ради компактного формата не изменяется. По умолчанию используется KOI8 без инверсии. Опция -I включает инверсию для штатного BIOS во всех MAIN/BANK вызовах, заголовок отчёта содержит I (обычный режим — N). После каждого измерения перед печатью отчёта и при выходе инверсия сбрасывается. Standalone-варианты с -I не поддерживаются: их пакетные ядра не гарантируют инверсию; штатный BIOS обслуживает управляющие последовательности, испытания переключения KOI/ESC не входят в эту сетку.

| Параметр | Назначение |
|---|---|
| `-E=BIOS` или `-K` | Установленный BIOS без подмены; выбор по умолчанию |
| `-E=STANDALONE` | Все 22 standalone-варианта |
| `-E=ALL` | BIOS и все standalone-варианты |
| `-E=имя[,имя]` | Один движок или список; повторные `-E` добавляют выбор |
| `-P=OFF`, `-P=ON`, `-P=BOTH` | Пререндер выключен, включён или оба состояния; по умолчанию BOTH |
| `-S` | Только printChar/printCharRaw: MAIN, BANK CMD и BANK TEXT; 6 этапов на состояние пререндера |
| `-I` | Инверсный вывод штатным BIOS; пример FontBen.com -I -P=ON |
| `-N` | Не сохранять файл |
| `-Q` | Пропустить показ итоговой таблицы и ожидание Enter |
| `-?` | Справка |

Вместо `=` допустим пробел; регистр имён не важен. Первый `-E` заменяет выбор BIOS по умолчанию. Для каждого движка выводится своя таблица; результаты всех выбранных движков последовательно записываются в один `B:\FONTBEN.TXT` через DOS OPEN/WRITE/CLOSE. При обычном запуске после каждой таблицы ожидается Enter; `-Q` выполняет всю выбранную серию подряд.

| Имена движков | Реализация |
|---|---|
| MXOS1 | Копия исторического скаляра MXOS-1 (прежнее имя MONITOR) |
| OPT | Оптимизированный пакетный посимвольный путь |
| FULL | Посимвольный пререндер 12 КиБ |
| FULLFAST | То же ядро 12 КиБ, прямой glyphBody без повторных PUSH/POP |
| COLPRE | Готовые плоскости 10 КиБ, последовательная запись одного/двух столбцов |
| ROTLINE | Развёрнутый скаляр без пререндера, линейный шрифт |
| MON2 | Двухпроходное стековое пиксельное ядро Monitor-2, очистка и XOR |
| RAMFOS | Очистка знакоместа и потоковый XOR глифа, сдвиг 16-битным ADD HL,HL |

| CACHE | Посимвольный кэш сдвинутых глифов |
| QUAD | Четвёрки с полным пререндером 12 КиБ |
| COLD, WARM | Четвёрки с холодным/предварительно прогретым кэшем |
| ROTATE, HALF | Четвёрки с вращением на месте / сохранённым сдвигом на четыре |
| PACKED | Четвёрки с компактным FONTKOI |
| PAGED | Построчный шрифт, четвёрки с вращением / пререндером 10 КиБ |
| REMAP32 | Построчный полный шрифт с восьмибайтной таблицей блоков |
| BLOCK32 | Компактные блоки по 32 глифа без Ёё, с полным локальным fallback |
| 8X8 | Выровненное копирование восьми строк полного шрифта |
| 4RAW, 4PACK, 4DUP | 4×8: байт на строку, два глифа в байте, повторённый полубайт |

OFF отключает ускоряющие таблицы FULL/CACHE/QUAD/COLD/WARM/HALF/PACKED и PAGED/REMAP32/BLOCK32: остаётся локальный посимвольный или вращающий четвёрки путь. MXOS1, MON2, RAMFOS, ROTLINE, OPT, ROTATE, 8X8 и три формата 4×8 не меняют алгоритм от этого флага. При WARM полный проход по тому же корпусу выполняется вне таймера перед каждым этапом; COLD очищает кэш перед этапом.

```text
FontBen.com
FontBen.com -E=PAGED -P=ON
FontBen.com -E=FULL,QUAD,BIOS -P=BOTH
FontBen.com -E 4DUP -P ON -Q
FontBen.com -E=ALL -N -Q
```

Внутренние одиночные callbacks PAGED/REMAP32/BLOCK32 и 4×8 могут разрушать регистры: их сохраняет общий публичный Char/Raw-вход, а строковые головы/хвосты сохраняют только ещё нужный указатель текста. Пакетные callbacks сохраняют BC/DE/HL; обёртка не дублирует это сохранение. Отдельные входы raw6/pre6/raw8 пиксельного ядра сохраняют прежний контракт, а вложенный DLL-адаптер использует их внутренние helpers без второго набора PUSH/POP. Для 8×8 указатель текста хранится в BC; восьмая строка глифа обходится без ненужного продвижения указателей. Для 6×8 вращения и пререндер имеют самостоятельные циклы чтения и рисования четвёрок; нужный scalar/batch-вход устанавливается при инициализации DLL. В измеряемом пути нет проверки variant/preEnabled и перенастраиваемого перехода между ядрами. В 4DUP продолжение цикла расположено сразу после пары, исключая безусловный переход на каждой итерации.

Контроллер находится ниже 2000h. DLL и их таблицы занимают собственный блок MAIN от 2000h до конца образа, выделенный менеджером памяти; области разных движков перекрываются только после выгрузки предыдущего модуля. Для нативного пререндера BIOS резервируется 3000h–57FFh внутри выделенного блока. Загрузка, подготовка шрифта/пререндера, очистка экрана, выделение буферов и отчёт исключены из времени. ВИ53 читается локально в MAIN и BANK.

Сборка: `powershell.exe -NoProfile -File scripts/build/build-project.ps1 OS`, затем `powershell.exe -NoProfile -File scripts/images/build-image.ps1 SystemEmuWritable`. CPU-проверка всех DLL: `python source-apps/fontbench/check-engines.py`. Проверка полной сетки в собственном видимом Emu80: `python source-apps/fontbench/check-grid.py`; для DLL — например `--engine PAGED` или `--engine 4DUP --pre ON`. Отчёты находятся в docs/bench/native-grid и docs/bench/engine-grid.

## FontLab.com: коллекция standalone-движков

Прежняя коллекция сохранена в `A:\Bench\FontBen\FontLab.com` (bin/FONTLAB.i80); исходник LEGACY.asm/legacy-main.inc. Параметры и исторические результаты ниже относятся к FontLab. FontBank.com обслуживает оба теста и остаётся самостоятельным банковым COM.

### Параметры FontLab

Без ключей выбираются standalone и системные движки, main и BANK: 86 строк, 172 измерения. `-E=STANDALONE` сохраняет прежнюю коллекцию экспериментальных ядер; `-E=KERNEL` или `-K` проверяет только публичные системные API. Системные строки включают PRINT_CHAR, PRINT_CHAR_REAL, обычный и прямой строковые API с Win20, Far48 и Far1152. Регистр ключей не важен; повторный ключ заменяет предыдущее значение. Неверный ключ или пустой отбор показывает справку.

| Ключ | Значения | Назначение |
|---|---|---|
| `-E=` | `STANDALONE`, `KERNEL`, `PAGED`, `ALL` | Коллекция движков; по умолчанию ALL |
| `-K` | — | Краткая форма `-E=KERNEL` |
| `-F=` | `4`, `6`, `8`, `ALL` | Геометрия; текущий системный API относится к 6×8 |
| `-P=` | `RAW`, `PACK`, `DUP`, `ALL` | Формат 4×8 |
| `-B=` | `MAIN`, `BANK`, `BOTH` | Где исполняется цикл; DOS сохранён как псевдоним BANK |
| `-C=` | `CHAR`, `SERIAL`, `GROUP`, `WIN20`, `FAR48`, `FAR1152`, `ALL` | Способ вызова; WIN256 сохранён как псевдоним WIN20 |
| `-S` | Только printChar/printCharRaw: MAIN, BANK CMD и BANK TEXT; 6 этапов на состояние пререндера |
| `-I` | Инверсный вывод штатным BIOS; пример FontBen.com -I -P=ON |
| `-N` | — | Не сохранять отчёт |
| `-Q` | — | Пропустить таблицу и ожидание Enter |
| `-?` | — | Справка |

Примеры: `FONTLAB -K` — только системные API из main и BANK; `FONTLAB -K -B=BANK -C=WIN256 -Q` — один штатный банковый строковый путь; `FONTLAB -E=STANDALONE -F=4 -P=DUP -C=SERIAL -Q` — сохранённый движок 4×8. Неизмеренные сочетания помечаются прочерком. Все standalone-движки доступны из банка через штатный строковый API.

Реализации сгруппированы в [engines/](engines/README.md). Monitor — локальная копия исторического пиксельного ядра; Opt меняет её локальный вход. На время standalone-этапа тест заменяет адреса PRINT_CHAR/PRINT_STRING в таблице MXOS_CALL и старых JMP-входах BIOS. После этапа, перед инфострокой и при ошибке они восстанавливаются. Системные строки с префиксом API используют установленный BIOS. PRINT_CHAR_REAL/PRINT_STRING_REAL получают только печатные байты; CRLF обслуживает обычный BIOS.

FontLab.com имеет IMAGE_FLAG_MAIN. На каждое банковое измерение он штатно запускает FontBank.com с IMAGE_FLAG_BANK через FILE_EXEC_NATIVE. Банковое приложение получает согласованный адрес блока параметров в аргументах, готовит собственный текстовый буфер и ведёт таймер внутри себя. Вход/возврат, чтение файлов, подготовка текста и выгрузка исключены из времени. RET освобождает EXEC-банк и его дочерние ресурсы средствами DOS. Без служебного аргумента FONTBANK показывает подсказку запуска FONTBEN.

FontBank.com печатает поток из собственного банка через MXOS_CALL. SERIAL/GROUP и Win20 используют один PRINT_STRING_BANK на весь поток; штатный адаптер переносит порции до 20 байт в аппаратное окно. Отдельный TEXT_PRINT в новой сетке использует 256-байтный main-буфер BIOS. Far48 переносит 48 печатных байт + CRLF (50 байт), добавляет локальный NUL и вызывает PRINT_STRING_MAIN для каждой строки. Far1152 переносит весь поток с NUL (1201 байт) одним memcpy_far и вызывает PRINT_STRING_MAIN один раз. FbMain.dll и вложенные MODULE_CALL больше не нужны.

В MAIN цикл и текст находятся в основной памяти; в BANK цикл выполняется в отдельном EXEC-банке. CHAR вызывает PRINT_CHAR через MXOS_CALL для каждого байта. Остальные MAIN-прогоны вызывают PRINT_STRING_MAIN один раз на весь поток; выбранный standalone-фронтенд обрабатывает его пакетами. Передача текста и вызовы API входят в замер BANK. MAIN у транспортных вариантов — контрольный повтор без копирования. ВИ53 читается локально после полного вывода; интервал должен быть короче периода счётчика (8,388608 с). Подготовка, очистка, проверка изображения, инфострока и запуск/выгрузка BANK COM исключены из времени.

Автономный тест сравнивает штатный BIOS 5×7, полный набор готовых сдвигов 12 КБ и настоящий ограниченный кеш с генерацией сдвигов при промахе. Рендеры 6×8 и 8×8 используют один встроенный линейный FONT.FNT; 4×8 — отдельный знакогенератор CP/M Syabr. Все варианты получают одинаковые 1152 байт реального `A:\README.TXT`, прочитанного при запуске через FILE_HANDLE. CR/LF заменяются пробелами (пара CRLF даёт один пробел, в том числе на границе блока чтения), остальные управляющие коды также заменяются пробелом, старшие байты KOI-8 не перекодируются. При коротком файле остаток заполняется пробелами; ошибка чтения явно останавливает тест. Загрузка, фильтрация, переход к корню A: и восстановление исходного каталога/диска выполняются вне замеров. Текст размещается в сетке **48×24** без прокрутки, пригодной для последующего сравнения с 8×8. Прежняя строка 20h–4Fh больше не используется: её 48 кодов целиком помещались в 53 слота и давали идеальный hit-only второй проход.

Внутри COM результат сравнивается с исходными глифами и корпусом: 36 экранных столбцов для 6×8, 48 для 8×8 и 24 для 4×8, по 24 знакоместа с шагом 10 пикселей; общий результат — `Bitmap: PASS/FAIL`. Полная таблица 12 КБ формируется при сборке. Для кеша отдельно измеряются первый экран (cold) и повторный (warm), из main и отдельного EXEC-банка. В cold входят Query BIOS, инициализация индекса и генерация глифов; предзаполнения нет. В warm не выполняется даже очистка индекса, но промахи и вытеснения по-прежнему возможны: повторный проход не означает попадания всех символов. Выровненный 8×8 включён в COM: он копирует исходные восемь байт глифа в ячейку шириной восемь пикселей без растягивания, пререндера, масок и чтения экрана. Восемь строк развёрнуты, пакет не вызывает подпрограмму на каждый глиф. Пиксельное ядро выводит коды напрямую; общий фронтенд обслуживает CRLF через BIOS. Его экран занимает 48 столбцов вместо 36 и проверяется отдельно по исходным глифам.

### Общая таблица и сериализованные варианты

`matrix-main.inc` задаёт 86 строк MAIN/BANK (172 этапа при полном отборе). Мониторный движок сохранён локально; развёрнутые циклы, повторное использование поворотов и пакетные пути самостоятельных ядер сохранены.

После каждого измерения снизу показаны номер этапа, MAIN/BANK, геометрия, режим и время. Паузы нет; очистка области текста и инфострока находятся вне замеров. Отчёт сохраняется в B:\FONTBEN.TXT через FILE_HANDLE OPEN/WRITE/CLOSE с усечением прежнего файла. Итоговая таблица выводится постранично; переход и возврат — Enter. Перед выходом модули выгружаются, режим текста восстанавливается. Интеграционная проверка: `python source-apps/fontbench/check-emulator.py --report docs/bench/engines/full`.

Входы `serialBIOS`, `serialFull`, `serialCache` принимают HL=текст, C=0..48 и сохраняют A/BC/DE/HL один раз на пакет; CF=1 при длине больше 48. Строка должна помещаться на экране. Monitor serial вызывает локальную копию обработчика печатных символов без внешнего сохранения регистров каждого символа. Full/cache переходят непосредственно в тело рендера и общее продолжение, без посимвольного CALL/сохранения общего набора регистров. На пакет три первых POP общего эпилога временно заменяются JP продолжения, затем исходные POP восстанавливаются; посимвольный путь не платит за дополнительный JMP. Стенд работает с DI, входы нерекурсивны. При недостатке кеша пакетный fallback использует внутренний обработчик BIOS, не пытаясь снять отсутствующий посимвольный стек. Сырые full/cache, как прежние варианты, не интерпретируют управляющие коды. Их cold/warm следуют друг за другом отдельно для main и BANK.

Текст для всех режимов одинаков: 1152 печатных байта README, CRLF после каждой из 24 строк и завершающий NUL, итого 1201 байт. Курсор задаётся один раз до замера; межстрочных SET_CURSOR_POS нет. Шаг строк — штатные 10 пикселей, текст занимает строки экрана 0–237, инфострока — 248–255. Общий ASCIIZ-фронтенд отдаёт полные четвёрки выбранному ядру 6×8, а невыровненные головы и хвосты — штатному посимвольному рендеру. Этот расход входит в BANK Win20, где границы порций могут разрезать четвёрку.

Полный набор готовых фаз остаётся самостоятельным вариантом для банковых программ. Канонический `FONTBEN.shifts.bin` по-прежнему содержит все четыре фазы в 12-КБ формате и пригоден старым стендам. В текущем standalone исходные 2048 байт уже находятся по 2800h, поэтому их дубликат 3800h–3FFFh переиспользован под дополнительные тестовые процедуры: 10 КБ готовых сдвигов + 2 КБ исходной фазы дают тот же полный набор 12 КБ без генерации в рендере. Старый внешний SHIFT без STANDALONE_SERIAL сохраняет прежнее размещение всех четырёх фаз. Полный набор не ограничен алфавитом README, содержит все 256 кодов и не зависит от кеш-арены. Если верхняя арена текущей BIOS меньше 4072 байт, упакованный FONTKOI временно занимает 4000h–4FE7h в main; фаза 4 полного пререндера восстанавливается из FONT.FNT перед следующим этапом, вне замера. Это нативный резерв стенда, без API менеджера памяти.

Прогон с новым потоковым протоколом — `docs/bench/remap32/stream-full/`. `report-matrix.py` строит таблицу из его results.json. Старые прогоны с построчной установкой курсора и MODULE_CALL имеют другую методику; их числа не являются замером нового пути.

### Три формата 4×8

Шрифт извлечён из CP/M Syabr 0.1 без изменения битмап: источник и раскладка описаны в [FONT4CPM.md](FONT4CPM.md). Внутренние форматы: `4raw` — 2048 байт, полезен младший полубайт строки; `4pack` — 1024 байта, два последовательных кода в одной восьмибайтной записи; `4dup` — 2048 байт, один и тот же полубайт повторён в обеих половинах. У RAW и DUP строки глифов разложены по восьми 256-байтным страницам, как в BIOS CP/M; код символа сразу задаёт младший байт адреса. Плотный формат сохраняет восьмибайтные записи и размер 1024 байта. Подготовка форматов выполняется вне измерения в 3000h–37FFh; перед новым направлением main/BANK восстанавливается прежняя фаза 0 полного пререндера. Подготовка таблиц остаётся локальной, без динамического выделения памяти под шрифт.

Для каждого формата измеряются CHAR, SERIAL, FAR48 и FAR1152 из main и BANK. Serial читает строку публичным GET8 и вызывает пакетный рендер; Char вызывает main-модуль на каждый символ. Строки Win20 остаются только как контрольный main-повтор, банковое значение отсутствует: публичный PRINT_STRING_BANK не принимает экспериментальное ядро 4×8.

Формат и продолжение цикла выбираются при подготовке таблицы, вне замеров. Полные пары читаются POP из текста, SP сохраняется и восстанавливается один раз на пакет; до его восстановления нет CALL/PUSH/RET. Экранный указатель вычисляется один раз на пакет, далее используется INC D; курсор публикуется после пакета. Входы нерекурсивны и требуют DI, как остальной standalone. Голова и хвост работают с нормальным стеком.

Полные выровненные пары записываются без чтения экрана; начало с правого полубайта и нечётный хвост используют развёрнутый маскированный путь. У плотного формата выбор ядра учитывает чётность обоих кодов, а не позицию символа в строке. Все три формата дают одинаковый экран. Количество символов сохраняется: 48×24, то есть занятая ширина составляет 192 пикселя. Сырые рендеры не разбирают управляющие коды, инверсию и прокрутку.

`python source-apps/fontbench/check-font4.py` проверяет 256 кодов во всех форматах, пары, непустой фон, начало/хвосты, границы, сохранение регистров, подготовку и восстановление таблиц. Независимые компараторы 4×8 и 6×8 проверяются также намеренной порчей последнего байта. Память экранного эталона больше не требуется: 6×8 сравнивается непосредственно с исходным шрифтом и корпусом, освободившееся место занято кодом и таблицей режимов.

### Четверки без чтения экрана

`quad.inc` добавляет отдельные входы `quadRender` (ограниченный кеш) и `quadFullRender` (полная таблица 12 КБ). HL указывает текст в основной памяти, C задаёт 0..48 кодов, длина кратна четырём. Начальный X должен быть кратен восьми пикселям, вся строка должна помещаться на экране; неполная четверка и неверные параметры возвращают CF=1 до записи экрана. A/BC/DE/HL сохраняются, остальные флаги разрушены. Это сырой normal KOI-8 интерфейс без управляющих команд, инверсии и прокрутки. Хвосты с чтением экрана пока отсутствуют; прежний посимвольный путь сохранён отдельно.

Каждая четверка шириной 24 пикселя собирается прямо при записи трёх экранных байтов: фазы 0 и 6 образуют первый байт, остаток 6 и фаза 4 — второй, остаток 4 и исходный глиф — третий. На восемь строк приходится 24 записи, ни одного чтения видеопамяти и ни одной сохраняющей маски. Пиксельный цикл кеша/полной таблицы развёрнут и пишет восемь строк каждого столбца подряд. BC указывает экран, DE/HL удерживают два источника; между столбцами меняются только источники, восстанавливается Y и выполняется `INC B`, то есть +100h. Все три столбца записываются целиком, поэтому порядок столбцов не требует чтения фона. В рабочей памяти хранятся четыре указателя, промежуточной битмапы и копии четырех входных кодов нет. Общий блок четверок занимает 526 байт, из них 196 байт — пиксельное ядро кеша/полной таблицы; новые бескешевые ядра и подготовка таблицы вынесены в `quad-direct.inc`.

При выборе каждого кешированного сдвига он защищается от вытеснения на два следующих получения указателя. Для фиксированной тройки кешируемых фаз это реализовано двумя байтами последних номеров слотов: FIFO пропускает оба защищённых номера. После выбора третьего указателя выделений до завершения рисования больше нет, четвёртый глиф берётся непосредственно из шрифта. Это эквивалент прибавки времени жизни на два шага без таблицы времён для всех слотов. Защита сбрасывается между четверками, перед возвратом восстанавливается обычный FIFO. Требуется минимум три слота; при меньшей ёмкости вход возвращает CF=1. Самостоятельный вход нерекурсивен.

FONTBEN дополнительно показывает шесть замеров: полная таблица и cold/warm кеш для четверок из main и DOS. В обоих случаях один вызов получает ровно четыре кода. Из страницы DOS они передаются через BC/DE и помещаются в четырёхбайтный буфер кодов в main, а рендер сразу пишет экран. Копирование кодов и один межстраничный вызов на четверку входят во время; посимвольные замеры сохранены. Независимая проверка `python source-apps/fontbench/check-quad.py` проверяет 556 случаев, включая все коды, непустой фон, отказ для хвостов/выравнивания и вытеснение при трёх слотах; дополнительно проверяется отсутствие экранных чтений и стековых команд в пиксельном ядре. Результаты эмуляторных замеров и ограничения находятся в `docs/bench/quad-001/`.

В оптимизированном варианте hit четверки не сохраняет AF на стек и не вызывает отдельный декодер номера слота; защита указателей обновляется в регистрах. Генерация восьми строк каждой фазы развёрнута. Исходная фаза посимвольного пути проходит до проверки инвалидирования: она не запрашивает и не инициализирует кеш вообще. Управляющие коды фильтруются один раз при загрузке README; сырой цикл рендера не повторяет разбор. Актуальные замеры — `docs/bench/quad-opt-001/`.

### Четверки со сдвигами на лету

`quadDynamicRender` и `quadHalfRender` используют тот же интерфейс/проверки и выводят те же четверки без поиска, промахов, вытеснения и защиты кеша. Первый вход читает исходный шрифт и не использует кеш-арену. Второму нужна одна постоянная таблица циклического поворота на четыре бита, восемь байт на глиф: 2048 байт для всех 256 кодов. `quadPrepareHalf` получает арену BIOS и заполняет её вне измерения, помечая прежний кеш недействительным; на каждый символ служба BIOS не вызывается. При отсутствии подготовленной таблицы `quadHalfRender` возвращает CF=1 без вывода. Требуются 2048 доступных байт и начало арены, выровненное на восемь; при отказе подготовки таблица недоступна. Это нормализованный линейный шрифт standalone, не прямой разбор MXFN.

Для шестибитных строк `a,b,c,d` результат — `(a<<2)|(b>>4)`, `((b<<4)&0F0h)|(c>>2)`, `((c<<6)&0C0h)|d`. На 8080 вычисляются `r4=ROR8(b,4)` и `r2=ROR8(c,2)`: первый результат используется дважды через `r4 AND 03h` / `r4 AND 0F0h`, второй — через `r2 AND 0Fh` / `r2 AND 0C0h`. Поэтому вытолкнутые части переходят в следующий байт, повторных поворотов для левой части нет. В бескешевом варианте на строку приходятся два ADD A для `a`, четыре RRCA для `b` и два RRCA для `c`; в варианте с таблицей RRCA для `b` исключены. Маски выделяют части глифов, экран не читается.

Новые ядра идут по строкам четверки: DE указывает экран, B/C удерживают части текущей строки. Четыре исходных указателя читаются POP HL из рабочей памяти и обновляются для следующей строки. SP сохраняется один раз на четверку, до восстановления SP нет CALL/PUSH/RET. Временного пиксельного буфера нет, используется только восемь байт указателей. По четыре строки развёрнуты, две итерации завершают глиф. Публичные регистры сохранены. Прежний результат микротеста против посимвольного чтения битмапы стеком к этому алгоритму не относится.

FONTBEN показывает `Main/DOS quad raw` и `Main/DOS quad rot4`, сохраняя прежние режимы. Методика та же: четыре кода на вызов, подготовка таблицы вне замера, 1200 байт README, проверка всех 9216 байт изображения. Полный новый прогон и снимки — `docs/bench/quad-direct-001/`. На этом корпусе бескешевый вариант немного медленнее прогретого кеша, но не занимает 4-КБ арену; вариант rot4 использует 2 КБ без lookup/FIFO.

### Готовые сдвиги компактного FONTKOI

`python source-apps/fontbench/analyze-fontkoi.py` читает MXFN и создаёт проверочный образ и расчёт в `docs/bench/quad-opt-001/fontkoi/`; системный шрифт и рендер не меняются. Текущий FONTKOI содержит 162 кода: 20h–7Fh, C0h–FFh и A3h/B3h, всего 147 различных восьмибайтных битмап. Полностью разложенные три сдвига занимают 40 байт на уникальный глиф, то есть 5880 байт без поиска. Исходная фаза остаётся в уже загруженном шрифте. Такой формат в 4 КБ не помещается даже после объединения одинаковых глифов.

В 4 КБ помещается другой формат: три готовых поворота по восемь байт на глиф, 147×24 = 3528 байт; две части фаз 4/6 сохраняются в одном байте и выделяются масками при выводе, без вращений. Прямой поиск по всем 256 кодам через 16-битный относительный указатель занимает 512 байт, всего 4040; с 32-байтным заголовком — **4072 байта**, остаётся 24. Непредставленные коды ссылаются на пробел, одинаковые битмапы разделяют запись. Заголовок/таблица/данные располагаются плотно, без округления начала к странице; выравнивание может съесть оставшийся запас. Таблица указателей внутри образа содержит смещения, при загрузке их можно заменить абсолютными адресами без роста размера. Альтернатива с байтовым номером глифа занимает 3784 байта без заголовка, но требует умножения номера на 24 при поиске. Формат подключён к standalone через `quadPackedRender` и измеряется вместе с остальными вариантами. Указатели превращаются в абсолютные вне замера, поиск остаётся прямым по всем 256 кодам. Четыре строки развёрнуты; вывод идёт сразу в экран без чтения VRAM. Исходная фаза четвёртого символа получается двумя RRCA из готовой фазы 0, поэтому при самом рендере отдельный исходный FONTKOI не нужен. Конструктор стенда использует 403 байта служебных индексов и встроенный FONT.FNT; сборка проверяет совпадение всех представленных глифов с FONTKOI. Эти данные конструктора не входят в 4072 байта резидентной таблицы, подготовка исключена из времени. Схема зависит от фактических битмап текущего файла, а не подходит автоматически любому MXFN. Штатный системный рендер не меняется.

Полная матрица 69 пар, снимки трёх страниц, проверка битмап, чтения и усечения файла отчёта сохраняются в `docs/bench/font4-opt/full/`. Общая таблица строится командой `python source-apps/fontbench/report-matrix.py --results docs/bench/font4-opt/full/results.json --out docs/bench/font4-opt/full/table.md`.

### Устройство ограниченного кеша

`cache.inc` получает границы, размер и эпоху через `MXOS_CALL MXOS_BIOS_GLYPH_CACHE` с A=0. Перед каждым глифом проверяется опубликованный `GLYPH_CACHE_INVALID`. При инвалидировании границы запрашиваются снова, индекс очищается, указатели и число слотов пересчитываются; старый хвост после сужения не затрагивается. После подготовки движок сбрасывает флаг, при добавлении записей обновляет `GLYPH_CACHE_ENTRIES`. Расширение без инвалидирования сохраняет старую ёмкость до следующей подготовки — уже существующие записи продолжают работать. Это временный единственный владелец формата кеша, не интеграция кешированного вывода в BIOS. Источник глифов в этом стенде — линейный шрифт charGen, режим normal KOI-8; при его замене вызывающая сторона должна инвалидировать кеш. Разбор MXFN, KOI-7 и инверсии остаётся задачей будущего фронтенда BIOS.

Ключ кеша — **код символа и конкретная фаза сдвига**, а не весь глиф с четырьмя вариантами. Шесть бит исходного FONT.FNT выровнены вправо, поэтому физическая фаза `X mod 8 = 2` уже готова: она рисуется непосредственно из charGen, без выделения слота, промаха или генерации. При недостатке кеша этот прямой путь также доступен. Для остальных фаз при промахе создаётся только один запрошенный вариант: 8 байт для фазы 0, 16 байт для фаз 4 и 6.

Lookup занимает **768 байт**, по одной странице на каждую кешируемую фазу (0/4/6). Код символа прямо индексирует нужную страницу; байт 0 означает промах, 1..255 — номер слота. На hit адрес декодируется из номера за фиксированное число инструкций 8080: `pool + token*16`, через перестановку полубайтов и маски. Участок от добавления базовой страницы индекса до готового HL занимает 95 тактов, включая проверку промаха, без выбора фазы и проверки инвалидирования. Три таблицы полных указателей заняли бы 1536 байт и уменьшили бы число доступных слотов. Поиска по диапазонам, обхода тегов и LRU на hit нет.

Слот занимает **16 байт** и содержит только один сдвиг. Для фазы 0 используются первые восемь байт; оставшиеся восемь не заполняются. Выравнивание сохраняет быстрые развёрнутые пиксельные ядра, общие с таблицей 12 КБ, без переходов через страницу внутри глифа. Общая FIFO-очередь обслуживает пары (код, фаза); две обратные страницы по 256 байт хранят код и фазу владельца каждого номера. При стандартной области DB90h–EB90h: 112 байт выравнивания, 768 байт lookup DC00h–DEFFh, 512 байт владельцев DF00h–E0FFh, запрещённый нулевой блок E100h–E10Fh, **168 слотов** E110h–EB8Fh. Всё это находится внутри выделенных BIOS 4096 байт; служебное состояние находится в программе. При недостатке места для сдвинутой фазы используется BIOS. Счётчики обновляются только на промахе/вытеснении. В прежнем варианте каждый miss строил 48 байт четырёх фаз и занимал слот 64 байта; прежние результаты сохранены в локальных отчётах для сравнения.

Независимая проверка: `python source-apps/fontbench/check-cache.py`. Она использует z88dk-ticks в режиме 8080 и проверяет все 256 кодов во всех четырёх фазах, границы экрана, сохранение регистров/флагов, FIFO, нулевую/малую ёмкость, переменное начало области, сужение и замену шрифта. Реальный Query IO.SYS вызывается через тестовый переходник, транспорт проверяется отдельным запуском из NC в Emu80.

## Перенос в BIOS

Штатный BIOS теперь использует четверки 6×8 с вращением на месте и, при явном включении FONT_RENDER, три предварительно построенные фазы в main. Системные строки API измеряют установленный BIOS; Monitor и остальные standalone-движки сохраняют свои реализации. Старая коллекция FontLab автоматически не выделяет 10-КБ буфер для системного рендера; новая штатная сетка FontBen включает и выключает его явно. Контракт включения приведён в [BIOS](../../source/bios/README.md#fontrender-0130h).

Адресация по 256-байтным страницам уже используется и проверяется в RAW/DUP 4×8. Текущие standalone 6×8 и 8×8 хранят глифы подряд по восемь байт; прямого сравнения построчной раскладки 6×8 с ними пока нет. Выравнивание начала таблицы на 256 байт само по себе не отменяет умножение кода на восемь.

## Сборка и проверки

Текущие входы программ — `STANDALONE.asm` в fontbench и textbench. `bank-loop.asm`, `native-entry.inc`, `module-timing.inc` и общая оболочка находятся в textbench и используются обоими тестами; `stream.inc` подключает standalone-фронтенд к BIOS на время этапа. Движки FONTBEN находятся только в `engines/`. Старые отдельные стенды с частными GATE/BUFFERGATE и их сборщики удалены; исторические результаты остаются в локальных отчётах `docs/bench/`.

Сборка обоих тестов: `powershell.exe -NoProfile -File scripts/build/build-project.ps1 OS`. Образ: `powershell.exe -NoProfile -File scripts/images/build-image.ps1 SystemEmuWritable`.

CPU-проверки запускаются после сборки:

- `python source-apps/fontbench/check-monitor.py` — Monitor и Opt в сравнении с BIOS.
- `python source-apps/fontbench/check-cache.py` — кеш, фазы, границы и инвалидирование.
- `python source-apps/fontbench/check-quad.py` — четверки и варианты пререндера.
- `python source-apps/fontbench/check-aligned8.py` — текущее ядро 8×8.
- `python source-apps/fontbench/check-font4.py` — три формата 4×8.
- `python source-apps/fontbench/check-options.py` — параметры запуска и отбор режимов.

Запуск через NC, банковые вызовы, сохранение отчёта и возврат проверяют `source-apps/fontbench/check-emulator.py` и `scripts/emu80/check-textbench.py`. Они запускают собственный видимый эмулятор без звука и закрывают его после проверки.


## Эксперимент с построчным шрифтом

`engines/paged.inc` содержит отдельные ядра 6×8 с вращениями, 6×8 с пререндером и 8×8. Шрифт полный: восемь страниц по 256 байт, младший байт адреса — код символа, старший — строка глифа. Пререндер 6×8 занимает 10 КБ: три дополнительные фазы, исходная берётся из шрифта. Каждый экранный байт собирается из двух глифов и записывается целиком; чтения VRAM нет. Форматы готовятся вне измерения.

Ядра включены в COM-матрицу с фильтром `-E=PAGED`; для каждого есть Serial, Far48 и Far1152 из MAIN/BANK. Отдельный CPU-стенд — `python source-apps/fontbench/check-paged.py`. Он сравнивает ядра с прежними standalone-реализациями на одном корпусе README из 1152 символов; дополнительно проверяет все 256 кодов, всю VRAM, сохранение регистров и неизменность таблиц. В модели 8080 при 2 МГц: 6×8 с вращениями 493,526 → 350,246 мс, с пререндером 300,998 → 187,838 мс, 8×8 244,262 → 175,094 мс. Это времена автономных ядер; полный фронтенд BIOS измеряется отдельно. Отчёт: `docs/bench/paged-font/results.json`.

Таймер настраивается и читается локально через общую библиотеку [timing-pit.inc](../../source/include/timing-pit.inc), без вызовов BIOS/DOS и переключений банка. Чтение занимает 10 байт и 54 такта 8080 с RET, без входного CALL; аппаратные требования и интерфейс описаны в [документации таймера](../../source/include/timing.md).

## Сравнение компактного шрифта: FontBlk.com

`A:\Bench\FontBen\FontBlk.com` — альтернативная сборка того же FONTBEN, заменяющая только движки PageRaw/PagePre экспериментальными `block32.inc` и `block32-support.inc`. Прежний `FontLab.com` сохранён. Отдельный исполняемый файл позволяет сравнивать оба ядра при фиксированной раскладке стенда, не добавляя второй комплект ядер в его ограниченную main-память. Для FontBlk по умолчанию выбраны `-E=PAGED -F=6`; доступны MAIN/BANK и Win20, Far48, Far1152. Вариант Page8 исключён.

Шрифт содержит 160 глифов: 20h–7Fh и C0h–FFh. Восьмибайтная таблица задаёт старший байт адреса каждого блока из 32 символов. Восемь строк глифа идут подряд, ядро увеличивает младший байт указателя. Шрифт занимает 1280 байт, пять плоскостей пререндера — 6400 байт; в стенде они используют прежние раздельные арены, поэтому размер COM и резерв стенда не равны полезному размеру этих данных. Четыре указателя готовятся один раз на четвёрку, до развёрнутой пиксельной части.

Ёё и остальные коды 80h–BFh заменяются в корпусе пробелами до начала измерений. Внутреннее ядро принимает только сохранённые диапазоны. Для KOI-7 достаточно заменить `blockPages+3` на страницу блока E0h; этот вариант проверяется CPU-тестом, переключение битмапы не меняет. Пользовательское переключение KOI внутри FONTBEN пока не добавлено; ядро BIOS остаётся прежним.

Примеры: `FontLab.com -E=PAGED -F=6 -N -Q` и `FontBlk.com -N -Q`. Для полностью одинакового корпуса автоматический сравнительный прогон прежней сборки использует `check-emulator.py --block32-corpus`; новая сборка выбирается `--block32`. `check-block32.py` проверяет пиксели и сравнивает ядра в модели 8080.

## Построчная раскладка с перекодировкой: FontMap.com

`A:\Bench\FontBen\FontMap.com` сохраняет полный построчный шрифт и прежние пиксельные ядра, но при чтении каждой четвёрки перекодирует символы восьмибайтной таблицей блоков. Три RLC и маска 07h выбирают блок; младшие пять бит исходного кода сохраняются. Таблица применяется и к вращению на лету, и к пререндеру. Данные шрифта и фаз при смене таблицы не переставляются. В отличие от FontBlk, все 256 глифов, включая Ёё, остаются доступны; размер данных не сокращается.

По умолчанию выбраны `-E=PAGED -F=6`, MAIN/BANK, Win20/Far48/Far1152. Прежний вариант запускается как `FontLab.com -E=PAGED -F=6`. Внутренние имена строк PageRaw/PagePre сохранены, конкретную реализацию выбирает исполняемый файл. Для эмуляторной проверки служит `check-emulator.py --remap32`. CPU-тест `check-block32.py` сравнивает все три раскладки и проверяет KOI-7 заменой одной записи таблицы. Он проверяет отображение кодов, а не полный BIOS-фронтенд с управляющими кодами и запретом старших диапазонов в KOI-7.

Штатный BIOS с P=ON использует пререндер и для скалярных символов, голов и хвостов строк. OFF отключает его для всех путей. Скалярный пререндер BIOS использует COLPRE; сравнительные числа и параметры повторного прогона приведены в docs/bench/colpre-bios/README.md.

## Сравнение скалярных ядер 6×8

FontBen.com -S -E=BIOS,MXOS1,MON2,RAMFOS,OPT,ROTLINE,PAGED,FULL,FULLFAST,COLPRE запускает два символных API через одинаковые публичные обёртки и MAIN/BANK-переходники. Для воспроизводимого отдельного варианта: FontBen.com -S -E=COLPRE -P=ON. Для BIOS имеет смысл BOTH; FULL/FULLFAST/COLPRE с OFF используют путь без готовых сдвигов. Прочие скалярные варианты не зависят от P. EngineS.dll содержит исторические пиксельные механизмы, линейный развёрнутый скаляр и новые варианты пререндера.

MON2 и RAMFOS адаптированы к полному установленному 256-символьному FONT.FNT и общим координатам 6×8. Управляющие коды исполняет общая обёртка FontBen. Это сравнение механизмов рисования, а не запуск неизменённой прошивки монитора. Очистка и наложение сохранены, специальный исторический код очистки 7Fh заменён внутренним флагом, чтобы Raw мог печатать все 256 глифов. Пробел завершает вывод после очистки, как в исторических обработчиках. Монитор SP580 использует такой же стековый механизм, отдельное дублирование одинакового пиксельного цикла не добавлено. Оконный монитор имеет выровненное 8×8-ядро и рассматривается отдельно от 6×8.

Новые ядра проверяются check-engines.py ENGINES. Штатный Emu80-прогон: python source-apps/fontbench/check-grid.py --engine COLPRE --pre ON --scalar. Счётчики и снимки сохраняются в docs/bench/scalar-grid/<engine>/. Все вызовы идут из MAIN-ядра, банковый клиент исполняет штатный MXOS_CALL, а не код рисования внутри банка.

Результаты сопоставимых скалярных прогонов и ограничения исторических сравнений: docs/bench/scalar-grid/README.md. После удаления проверок KOI BIOS измерен повторно; прежняя серия сохранена отдельно.

Стенд check-grid.py принимает --out <каталог> для сохранения отдельной серии без перезаписи прежних отчётов.
