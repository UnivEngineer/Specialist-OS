# Бенчмарки рендера шрифтов

## Автономный FONTBEN.COM

`powershell.exe -NoProfile -File scripts/build/build-project.ps1 OS` собирает также автономный `bin/FONTCOM.i80` с метаданными `FONTCOM.cpu`. Сборщик системного диска упаковывает его в `A:FONTBEN.COM`; запуск из NC — `FONTBEN.COM`. Старые управляемые Python стенды ниже сохраняются отдельно.

Автономный тест сравнивает штатный BIOS 5×7, полный набор готовых сдвигов 12 КБ и настоящий ограниченный кеш с генерацией сдвигов при промахе. Все варианты используют один встроенный линейный FONT.FNT и одинаковые 1152 байт реального `A:\README.TXT`, прочитанного при запуске через FILE_HANDLE. CR/LF заменяются пробелами (пара CRLF даёт один пробел, в том числе на границе блока чтения), остальные управляющие коды также заменяются пробелом, старшие байты KOI-8 не перекодируются. При коротком файле остаток заполняется пробелами; ошибка чтения явно останавливает тест. Загрузка, фильтрация, переход к корню A: и восстановление исходного каталога/диска выполняются вне замеров. Текст размещается в сетке **48×24** без прокрутки, пригодной для последующего сравнения с 8×8. Прежняя строка 20h–4Fh больше не используется: её 48 кодов целиком помещались в 53 слота и давали идеальный hit-only второй проход.

Внутри COM сравниваются 6912 байт занятых пиксельных строк (36 столбцов по 192 байта); эмуляторный стенд дополнительно проверяет незанятые области экранных колонок, исключая нижнюю строку результата; общий результат — `Bitmap: PASS/FAIL`. Полная таблица 12 КБ формируется при сборке. Для кеша отдельно измеряются первый экран (cold) и повторный (warm), из main и страницы DOS. В cold входят Query BIOS, инициализация индекса и генерация глифов; предзаполнения нет. В warm не выполняется даже очистка индекса, но промахи и вытеснения по-прежнему возможны: повторный проход не означает попадания всех символов. Выровненный 8×8 включён в COM: он копирует исходные восемь байт глифа в ячейку шириной восемь пикселей без растягивания, пререндера, масок и чтения экрана. Восемь строк развёрнуты, пакет не вызывает подпрограмму на каждый глиф. Это прямой вывод кодов, без управляющих кодов, KOI7, инверсии и прокрутки; ни bios_printChar, ни bios_printCharReal не вызываются. Его экран занимает 48 столбцов вместо 36 и проверяется отдельно по исходным глифам.

Для всех рендеров измеряется также вызывающий цикл в физической странице DOS 0. Временный шлюз FFC0h переводит аппаратную страницу в main, вызывает выбранный рендер и возвращает страницу/стек/регистры. Перед тестом сохраняются 2048 байт C000h–C7FFh страницы DOS и все 32 байта окна; перед возвратом они восстанавливаются. В резерве находятся цикл, копия тех же 1152 байт с C200h и стек с C800h. Файловые вызовы во время подмены окна запрещены. Требуются текущая сборка MEM и основная память до 8AAFh; область 6000h–67FFh сохраняет резерв DOS, 6800h–82FFh хранит уплотнённый эталон экрана, отдельный стек услуг начинается с 8500h, подготовленный текст лежит в 8600h–8A7Fh. Только варианты Opt временно заменяют три первых байта пиксельного бэкенда BIOS переходом в экспериментальный код; перед другими вариантами и возвратом исходные байты восстанавливаются. Штатный printChar в строке BIOS char неизменён. Системный шрифт не изменяется. Кеш стенда занимает предоставленную BIOS область; при выходе его индекс помечается недействительным, прежние настройки вывода восстанавливаются после Enter. TEXTBEN сохраняет свой прежний резерв 512 байт и собственный штатный MXCALL-сценарий.

Время показывает ВИ53 при CLK1=2 МГц. Оно включает цикл и обслуживание таймера; для DOS включает временный шлюз, установку позиции строк и переходы страниц. Это измерение в эмуляторе или на конкретной машине, не универсальное аппаратное значение.

### Общая таблица и сериализованные варианты

`matrix-main.inc` задаёт все пары main/DOS и печатает 54 пары main/DOS (108 этапов) на трёх экранах с ожиданием Enter между ними. Штатный `bios_printChar` сохранён как неизменённая база. Opt использует тот же настоящий фронтенд printChar (управляющие коды, KOI-7/8, шрифт, курсор, принтер, инверсия), меняя только пиксельный бэкенд. В нём обе части двухбайтного глифа уже получаются из одного поворота; там, где нужен чистый сдвиг влево двух нулевых старших битов, RLCA заменены ADD A. Копирование исходной фазы в полной таблице также исключено в standalone: источник берётся из исходного FONT.FNT. У генератора кеша убрана избыточная AND после двух ADD A, исходная фаза сохраняет ранний обход Query. Уже развёрнутые циклы и повторное использование поворотов в остальных путях сохранены.

После каждого измерения снизу показаны номер этапа (например, `12/108`), main/DOS, название режима и время в миллисекундах. Паузы нет; результат остаётся до следующего завершённого экрана. Очистка только текстовой области и строка результата реализованы локально в `progress.inc`, вне замеров. После восстановления DOS отчёт сохраняется в корень `B:\FONTBEN.TXT` через FILE_HANDLE OPEN/WRITE/CLOSE (fopen/fwrite/fclose); прежний файл перезаписывается с усечением. Ошибка сохранения показывается отдельно и не мешает просмотру. Для текстового отчёта повторно используется память эталона экрана после завершения всех сравнений. Итоговая таблица выводится на трёх страницах; переход и возврат — Enter. Другие клавиши не завершают тест. Непрерывный прогон без остановок внутри измерений, результаты и проверка сохранения — `docs/bench/font-matrix-004/`.

Входы `serialBIOS`, `serialFull`, `serialCache` принимают HL=текст, C=0..48 и сохраняют A/BC/DE/HL один раз на пакет; CF=1 при длине больше 48. Строка должна помещаться на экране. BIOS serial вызывает внутренний полный обработчик BIOS без внешнего сохранения регистров каждого символа. Full/cache переходят непосредственно в тело рендера и общее продолжение, без посимвольного CALL/сохранения общего набора регистров. На пакет три первых POP общего эпилога временно заменяются JP продолжения, затем исходные POP восстанавливаются; посимвольный путь не платит за дополнительный JMP. Стенд работает с DI, входы нерекурсивны. При недостатке кеша пакетный fallback использует внутренний обработчик BIOS, не пытаясь снять отсутствующий посимвольный стек. Сырые full/cache, как прежние варианты, не интерпретируют управляющие коды. Их cold/warm следуют друг за другом отдельно для main и DOS.

Для DOS сравниваются четыре способа передачи: базовая строка 48 байт через побайтовый шлюз в локальный буфер; `Win20` — 12 байт кода в общем аппаратном окне и 20 байт текста, пакеты 20+20+8; `Far48` — целые строки по 48 байт через настоящий `memcpy_far` в отдельный main-буфер; `Far1152` — один `memcpy_far` всего подготовленного корпуса 1152 байта и затем вывод строк из main-буфера. В Win20 рендер читает текст непосредственно из FFCCh–FFDFh, промежуточного копирования в main нет; источник DOS всё равно сначала копирует пакет в окно. В Far48 на экран приходится 24 копирования по 48 байт. Время копирования, подготовки запроса и сохранения/восстановления окна внутри memcpy_far включено. Общая установка/восстановление испытательного шлюза и банкового цикла исключена. Far1152 копирует до установки шлюза, Far48 вызывает атомарный копировщик из main-службы: тот временно занимает аппаратное окно и восстанавливает его до возврата в DOS. Вложенных банковых вызовов и IRQ нет. Четверки с полным пререндером, холодным/прогретым кешем, динамическими сдвигами, таблицей поворота на 4 и упакованным FONTKOI измеряются через все три пакетных транспорта. Вход принимает 20/8/48 байт и сохраняет регистры один раз на пакет. Main в этих строках — повторный замер соответствующего входа на 48 байт, DOS различается транспортом. Результаты не смешиваются с отдельным TEXTBEN, где другой корпус и прокрутка.

Полный набор готовых фаз остаётся самостоятельным вариантом для банковых программ. Канонический `FONTBEN.shifts.bin` по-прежнему содержит все четыре фазы в 12-КБ формате и пригоден старым стендам. В текущем standalone исходные 2048 байт уже находятся по 2800h, поэтому их дубликат 3800h–3FFFh переиспользован под дополнительные тестовые процедуры: 10 КБ готовых сдвигов + 2 КБ исходной фазы дают тот же полный набор 12 КБ без генерации в рендере. Старый внешний SHIFT без STANDALONE_SERIAL сохраняет прежнее размещение всех четырёх фаз. Полный набор не ограничен алфавитом README, содержит все 256 кодов и не зависит от кеш-арены.

Актуальный единый прогон — `docs/bench/font-matrix-003/`; `python source-apps/fontbench/report-matrix.py` строит общую Markdown-таблицу из JSON этого прогона. Все варианты используют одинаковые 1152 байт README и проверяются по одному эталону BIOS. Значения прежних отчётов на повторяющейся букве A или с прокруткой не примешиваются к этой таблице. На реальном редакторе дополнительный выигрыш зависит от размеров перерисовываемых фрагментов, размещения буферов и частоты смены шрифта; здесь измерен только заданный корпус.

### Четверки без чтения экрана

`quad.inc` добавляет отдельные входы `quadRender` (ограниченный кеш) и `quadFullRender` (полная таблица 12 КБ). HL указывает текст в основной памяти, C задаёт 0..48 кодов, длина кратна четырём. Начальный X должен быть кратен восьми пикселям, вся строка должна помещаться на экране; неполная четверка и неверные параметры возвращают CF=1 до записи экрана. A/BC/DE/HL сохраняются, остальные флаги разрушены. Это сырой normal KOI-8 интерфейс без управляющих команд, инверсии и прокрутки. Хвосты с чтением экрана пока отсутствуют; прежний посимвольный путь сохранён отдельно.

Каждая четверка шириной 24 пикселя собирается прямо при записи трёх экранных байтов: фазы 0 и 6 образуют первый байт, остаток 6 и фаза 4 — второй, остаток 4 и исходный глиф — третий. На восемь строк приходится 24 записи, ни одного чтения видеопамяти и ни одной сохраняющей маски. Пиксельный цикл кеша/полной таблицы развёрнут и пишет восемь строк каждого столбца подряд. BC указывает экран, DE/HL удерживают два источника; между столбцами меняются только источники, восстанавливается Y и выполняется `INC B`, то есть +100h. Все три столбца записываются целиком, поэтому порядок столбцов не требует чтения фона. В рабочей памяти хранятся четыре указателя, промежуточной битмапы и копии четырех входных кодов нет. Общий блок четверок занимает 526 байт, из них 196 байт — пиксельное ядро кеша/полной таблицы; новые бескешевые ядра и подготовка таблицы вынесены в `quad-direct.inc`.

При выборе каждого кешированного сдвига он защищается от вытеснения на два следующих получения указателя. Для фиксированной тройки кешируемых фаз это реализовано двумя байтами последних номеров слотов: FIFO пропускает оба защищённых номера. После выбора третьего указателя выделений до завершения рисования больше нет, четвёртый глиф берётся непосредственно из шрифта. Это эквивалент прибавки времени жизни на два шага без таблицы времён для всех слотов. Защита сбрасывается между четверками, перед возвратом восстанавливается обычный FIFO. Требуется минимум три слота; при меньшей ёмкости вход возвращает CF=1. Самостоятельный вход нерекурсивен.

FONTBEN дополнительно показывает шесть замеров: полная таблица и cold/warm кеш для четверок из main и DOS. В обоих случаях один вызов получает ровно четыре кода. Из страницы DOS они передаются через BC/DE и помещаются в четырёхбайтный буфер кодов в main, а рендер сразу пишет экран. Копирование кодов и один межстраничный вызов на четверку входят во время; посимвольные замеры сохранены. Независимая проверка `python source-apps/fontbench/check-quad.py` проверяет 556 случаев, включая все коды, непустой фон, отказ для хвостов/выравнивания и вытеснение при трёх слотах; дополнительно проверяется отсутствие экранных чтений и стековых команд в пиксельном ядре. Результаты эмуляторных замеров и ограничения находятся в `docs/bench/quad-001/`.

В оптимизированном варианте hit четверки не сохраняет AF на стек и не вызывает отдельный декодер номера слота; защита указателей обновляется в регистрах. Генерация восьми строк каждой фазы развёрнута. Исходная фаза посимвольного пути проходит до проверки инвалидирования: она не запрашивает и не инициализирует кеш вообще. Управляющие коды фильтруются один раз при загрузке README; сырой цикл рендера не повторяет разбор. Проверенный отдельно `check-stack.py` показал, что чтение битмапы через POP с корректным переключением/возвратом SP дороже обычного на 53 такта для однобайтного глифа и на 39 для двухбайтного, поэтому в рабочем рендере оно не используется. Актуальные замеры — `docs/bench/quad-opt-001/`.

### Четверки со сдвигами на лету

`quadDynamicRender` и `quadHalfRender` используют тот же интерфейс/проверки и выводят те же четверки без поиска, промахов, вытеснения и защиты кеша. Первый вход читает исходный шрифт и не использует кеш-арену. Второму нужна одна постоянная таблица циклического поворота на четыре бита, восемь байт на глиф: 2048 байт для всех 256 кодов. `quadPrepareHalf` получает арену BIOS и заполняет её вне измерения, помечая прежний кеш недействительным; на каждый символ служба BIOS не вызывается. При отсутствии подготовленной таблицы `quadHalfRender` возвращает CF=1 без вывода. Требуются 2048 доступных байт и начало арены, выровненное на восемь; при отказе подготовки таблица недоступна. Это нормализованный линейный шрифт standalone, не прямой разбор MXFN.

Для шестибитных строк `a,b,c,d` результат — `(a<<2)|(b>>4)`, `((b<<4)&0F0h)|(c>>2)`, `((c<<6)&0C0h)|d`. На 8080 вычисляются `r4=ROR8(b,4)` и `r2=ROR8(c,2)`: первый результат используется дважды через `r4 AND 03h` / `r4 AND 0F0h`, второй — через `r2 AND 0Fh` / `r2 AND 0C0h`. Поэтому вытолкнутые части переходят в следующий байт, повторных поворотов для левой части нет. В бескешевом варианте на строку приходятся два ADD A для `a`, четыре RRCA для `b` и два RRCA для `c`; в варианте с таблицей RRCA для `b` исключены. Маски выделяют части глифов, экран не читается.

Новые ядра идут по строкам четверки: DE указывает экран, B/C удерживают части текущей строки. Четыре исходных указателя читаются POP HL из рабочей памяти и обновляются для следующей строки. SP сохраняется один раз на четверку, до восстановления SP нет CALL/PUSH/RET. Временного пиксельного буфера нет, используется только восемь байт указателей. По четыре строки развёрнуты, две итерации завершают глиф. Публичные регистры сохранены. Прежний результат микротеста против посимвольного чтения битмапы стеком к этому алгоритму не относится.

FONTBEN показывает `Main/DOS quad raw` и `Main/DOS quad rot4`, сохраняя прежние режимы. Методика та же: четыре кода на вызов, подготовка таблицы вне замера, 1200 байт README, проверка всех 9216 байт изображения. Полный новый прогон и снимки — `docs/bench/quad-direct-001/`. На этом корпусе бескешевый вариант немного медленнее прогретого кеша, но не занимает 4-КБ арену; вариант rot4 использует 2 КБ без lookup/FIFO.

### Готовые сдвиги компактного FONTKOI

`python source-apps/fontbench/analyze-fontkoi.py` читает MXFN и создаёт проверочный образ и расчёт в `docs/bench/quad-opt-001/fontkoi/`; системный шрифт и рендер не меняются. Текущий FONTKOI содержит 162 кода: 20h–7Fh, C0h–FFh и A3h/B3h, всего 147 различных восьмибайтных битмап. Полностью разложенные три сдвига занимают 40 байт на уникальный глиф, то есть 5880 байт без поиска. Исходная фаза остаётся в уже загруженном шрифте. Такой формат в 4 КБ не помещается даже после объединения одинаковых глифов.

В 4 КБ помещается другой формат: три готовых поворота по восемь байт на глиф, 147×24 = 3528 байт; две части фаз 4/6 сохраняются в одном байте и выделяются масками при выводе, без вращений. Прямой поиск по всем 256 кодам через 16-битный относительный указатель занимает 512 байт, всего 4040; с 32-байтным заголовком — **4072 байта**, остаётся 24. Непредставленные коды ссылаются на пробел, одинаковые битмапы разделяют запись. Заголовок/таблица/данные располагаются плотно, без округления начала к странице; выравнивание может съесть оставшийся запас. Таблица указателей внутри образа содержит смещения, при загрузке их можно заменить абсолютными адресами без роста размера. Альтернатива с байтовым номером глифа занимает 3784 байта без заголовка, но требует умножения номера на 24 при поиске. Формат подключён к standalone через `quadPackedRender` и измеряется вместе с остальными вариантами. Указатели превращаются в абсолютные вне замера, поиск остаётся прямым по всем 256 кодам. Четыре строки развёрнуты; вывод идёт сразу в экран без чтения VRAM. Исходная фаза четвёртого символа получается двумя RRCA из готовой фазы 0, поэтому при самом рендере отдельный исходный FONTKOI не нужен. Конструктор стенда использует 403 байта служебных индексов и встроенный FONT.FNT; сборка проверяет совпадение всех представленных глифов с FONTKOI. Эти данные конструктора не входят в 4072 байта резидентной таблицы, подготовка исключена из времени. Схема зависит от фактических битмап текущего файла, а не подходит автоматически любому MXFN. Штатный системный рендер не меняется.

Полная матрица 54 пар, снимки трёх страниц, проверка битмап, чтения и усечения файла отчёта сохраняются в `docs/bench/font-matrix-004/`. Общая таблица строится командой `python source-apps/fontbench/report-matrix.py --results docs/bench/font-matrix-004/results.json --out docs/bench/font-matrix-004/table.md`.

### Устройство ограниченного кеша

`cache.inc` получает границы, размер и эпоху через `MXCALL MX_BIOS_GLYPHCACHE` с A=0. Перед каждым глифом проверяется опубликованный `GLYPH_CACHE_INVALID`. При инвалидировании границы запрашиваются снова, индекс очищается, указатели и число слотов пересчитываются; старый хвост после сужения не затрагивается. После подготовки движок сбрасывает флаг, при добавлении записей обновляет `GLYPH_CACHE_ENTRIES`. Расширение без инвалидирования сохраняет старую ёмкость до следующей подготовки — уже существующие записи продолжают работать. Это временный единственный владелец формата кеша, не интеграция кешированного вывода в BIOS. Источник глифов в этом стенде — линейный шрифт charGen, режим normal KOI-8; при его замене вызывающая сторона должна инвалидировать кеш. Разбор MXFN, KOI-7 и инверсии остаётся задачей будущего фронтенда BIOS.

Ключ кеша — **код символа и конкретная фаза сдвига**, а не весь глиф с четырьмя вариантами. Шесть бит исходного FONT.FNT выровнены вправо, поэтому физическая фаза `X mod 8 = 2` уже готова: она рисуется непосредственно из charGen, без выделения слота, промаха или генерации. При недостатке кеша этот прямой путь также доступен. Для остальных фаз при промахе создаётся только один запрошенный вариант: 8 байт для фазы 0, 16 байт для фаз 4 и 6.

Lookup занимает **768 байт**, по одной странице на каждую кешируемую фазу (0/4/6). Код символа прямо индексирует нужную страницу; байт 0 означает промах, 1..255 — номер слота. На hit адрес декодируется из номера за фиксированное число инструкций 8080: `pool + token*16`, через перестановку полубайтов и маски. Участок от добавления базовой страницы индекса до готового HL занимает 95 тактов, включая проверку промаха, без выбора фазы и проверки инвалидирования. Три таблицы полных указателей заняли бы 1536 байт и уменьшили бы число доступных слотов. Поиска по диапазонам, обхода тегов и LRU на hit нет.

Слот занимает **16 байт** и содержит только один сдвиг. Для фазы 0 используются первые восемь байт; оставшиеся восемь не заполняются. Выравнивание сохраняет быстрые развёрнутые пиксельные ядра, общие с таблицей 12 КБ, без переходов через страницу внутри глифа. Общая FIFO-очередь обслуживает пары (код, фаза); две обратные страницы по 256 байт хранят код и фазу владельца каждого номера. При стандартной области DB90h–EB90h: 112 байт выравнивания, 768 байт lookup DC00h–DEFFh, 512 байт владельцев DF00h–E0FFh, запрещённый нулевой блок E100h–E10Fh, **168 слотов** E110h–EB8Fh. Всё это находится внутри выделенных BIOS 4096 байт; служебное состояние находится в программе. При недостатке места для сдвинутой фазы используется BIOS. Счётчики обновляются только на промахе/вытеснении. В прежнем варианте каждый miss строил 48 байт четырёх фаз и занимал слот 64 байта; прежние результаты сохранены в локальных отчётах для сравнения.

Независимая проверка: `python source-apps/fontbench/check-cache.py`. Она использует z88dk-ticks в режиме 8080 и проверяет все 256 кодов во всех четырёх фазах, границы экрана, сохранение регистров/флагов, FIFO, нулевую/малую ёмкость, переменное начало области, сужение и замену шрифта. Реальный Query IO.SYS вызывается через тестовый переходник, транспорт проверяется отдельным запуском из NC в Emu80.

В конце документа приведено сводное сравнение со сдвинутым 5×7 и прямым пакетным выводом.

Отдельный стенд для Intel 8080, 2 МГц: сетка 48×32 в экране 384×256. Координаты X и Y кратны восьми, один глиф полностью заменяет восемь последовательных байт экранной колонки. Чтения прежнего фона, масок, сдвигов битмапа и интерпретации управляющих символов в `draw8` нет.

`FONT8.asm` содержит рендер, вывод из общего буфера и прокрутку на восемь пикселей. Рендер принимает C = код 0..255, HL = экранный адрес ячейки, сохраняет AF/BC/DE/HL/SP. Адрес ячейки и перенос строки вычисляет программа. Все глифы имеют размер 8×8; знакогенератор — 256×8 байт.

Для воспроизводимого изображения стенд заранее расширяет шесть бит штатного `assets/system-rom/FONT.FNT` до восьми по ближайшему пикселю. Это только подготовка тестового шрифта вне измерения, файл FONT.FNT и системный шрифт не изменяются. Рендер работает со всеми восемью битами каждого байта; время не зависит от рисунка. Полярность можно поменять предварительной инверсией знакогенератора.

## Размещение и ABI

| Область | Назначение |
|---|---|
| 0100h | Измеряемая программа, текст, счётчик строк; основное ОЗУ либо страница 0 |
| 6000h–67FFh основного ОЗУ | Подготовленный тестовый знакогенератор |
| EB00h–EB86h основного ОЗУ | Рендер и его вспомогательные функции, 135 байт |
| F880h–F8C6h основного ОЗУ | Диспетчер и контекст, 71 байт |
| FFC0h–FFCBh | Шлюз, 12 байт; тот же BUFFERGATE, что в TEXTBEN |
| FFCCh–FFDFh | Общий буфер текста, 20 байт |

Рендер и шрифт находятся в основном ОЗУ во всех режимах. Меняется размещение вызывающей программы и два операнда CALL, алгоритм рисования остаётся тем же. Из страницы 0 используется общий шлюз с A = страница возврата (0), B = функция (0 — глиф C в HL, 1 — C байт буфера начиная с HL, 2 — прокрутка экрана). Диспетчер возвращает страницу, стек, регистры и флаги. Прерывания запрещены, шлюз нереентерабелен, тест работает только в MX. Строка буфера не пересекает правую границу экрана; неверная длина >20 ничего не выводит. Функции 3 и выше — пустой контрольный вызов.

Нативный вариант вызывает ту же функцию напрямую. Буферный вариант включает копирование текста в общий буфер: на строку из 48 символов три вызова по 20, 20 и 8 символов. Копирование выполняется и в нативном варианте, поэтому таблица отдельно показывает обе нативные базы сравнения.


Три повтора каждой пары; `--repeats` меняет число повторов, `--rows 8 32 100` выбирает наборы строк. Строки различаются номером, чтобы ошибка прокрутки не скрылась повторяющимся рисунком. На 8 и 32 строках прокрутки нет, на 100 строках происходит 68 прокруток по восемь пикселей через штатный быстрый `bios_memcpy_bc_hl`. Последняя строка не вызывает лишней прокрутки. Цветовой атрибут во всём экране одинаков и не меняется.

## Сдвинутый 5×7 и сводное сравнение

`SHIFT.asm` сравнивает четыре рендера с одинаковым интерфейсом: символ C, общая позиция BIOS, сохранение AF/BC/DE/HL. MODE=0 вызывает настоящий `bios_printChar` C809h, MODE=1 использует готовые сдвиги штатного 5×7 с шагом шесть пикселей, MODE=2 непрозрачно рисует выровненный 8×8 с шагом восемь. MODE=3 вызывает настоящий C809h с экспериментальной заменой только пиксельного бэкенда. Варианты проверяются в отдельном стенде.

Предварительно подготовлены только четыре варианта буквы `A`, восемь строк каждый, включая пустую восьмую строку. Порядок фаз задаётся старой координатой X: 0, 2, 4, 6 пикселей относительно экранного байта. В первых двух случаях занята одна колонка, в остальных две. Данные двух колонок чередуются по строкам.

| Фаза | Адрес таблицы | Байтов на глиф | Сохраняемые маски экрана |
|---|---|---:|---|
| 0 | 3000h + код × 8 | 8 | 03h |
| 2 | 3800h + код × 8 | 8 | C0h |
| 4 | 4000h + код × 16 | 16 | F0h, 3Fh |
| 6 | 5000h + код × 16 | 16 | FCh, 0Fh |

Фактические подготовленные данные для `A` занимают **48 байт**. Стенд оставляет полное адресное окно 12 КБ, остальные глифы нулевые: индекс кода вычисляется так же, как для полного сдвинутого знакогенератора из 256 символов. Генерация данных выполняется на хосте до измерения. Область 3000h–5FFFh — временное размещение только этого изолированного стенда; он использует интегрированный DOS.sys с C000h, а не раздельный DOS4000.

`oneByte` и `twoBytes` — два отдельных полностью развёрнутых ядра. На строку выполняется `(экран AND сохраняемая_маска) OR готовый_битмап`. Вращений и сдвигов при рисовании нет. Соседние пиксели сохраняются. Чистая запись глифа, без адресации и перехода к продолжению:

| Ядро | Тактов 8080 | Чтений шрифта / экрана | Записей экрана |
|---|---:|---:|---:|
| 5×7, одна колонка | 270 | 8 / 8 | 8 |
| 5×7, две колонки | 585 | 16 / 16 | 16 |
| 8×8, одна колонка целиком | 182 | 8 / 0 | 8 |

При BATCH=1 вход принимает C=0..20 байт общего буфера FFCCh. Только печатные символы: CR/LF и другие управляющие коды не разбираются. Общие регистры сохраняются один раз на пакет. Внутри ускоренного цикла нет CALL/PUSH/POP, в том числе временных сохранений экранного адреса: DE указывает экран, HL — готовый глиф. Указатель текста хранится в операнде LDA; граница буфера — в операнде CPI. Рендер нереентерабелен, прерывания запрещены. Счётчик и проверка конца пакета остаются. Стандартный пакетный вариант продолжает вызывать C809h для каждого символа: он показывает цену существующего пути, а не переписанного стандартного BIOS.

Сдвинутый 5×7 из страницы через буфер быстрее штатного нативного вывода в **1,77 раза**, 8×8 — в **2,79 раза**. Межстраничная добавка одинакового пакетного цикла — 0,0167025 с: 72 пакета по 348 тактов и 23 переноса по 363 такта. Для одиночного символа диспетчер добавляет 343 такта. Нативная пакетная обработка ускоряет сдвинутый 5×7 ещё на 3,15%, 8×8 — на 4,95%, уже с учётом заполнения общего буфера.

Результаты: `docs/bench/shifted-font-001/results.json`, снимок `results.png`, CPU-проверка — `cpu/results.json`. В отчёте сохранены SHA-256 всех образов. Три повтора каждого режима дали одинаковые такты. Стандартный и сдвинутый 5×7 совпали побайтно, 8×8 проверен по своему пиксельному эталону. Независимая CPU-проверка включает 98 случаев: четыре фазы, крайние ячейки, непустой фон, сохранение соседних пикселей и AF/BC/DE/HL/SP, пустой/полный пакет и отказ для длины 21. Такты трёх ядер измерены отдельно. Дизассемблирование проверяет отсутствие CALL/PUSH/POP во всём внутреннем пакетном цикле ускоренных вариантов. Это измерения моделей; физическое оборудование не проверялось.

### Оптимизация штатного рендера без кэша

`OPT_DRAW.asm` — экспериментальная замена только участка drawChar, вызываемого настоящим `bios_printChar`. Код, который разбирает управляющие символы, KOI-7/8, выбирает шрифт и принтер, рассчитывает позицию и сохраняет публичные регистры, остаётся штатным. Переносы и продвижение курсора обрабатывает прежний код. Чтение `bios_vars.inverse` сохраняет normalVideo и инверсию. Исходник и сборка DOS.sys этим тестом не меняются: стенд ставит временный JMP в память только своего эмулятора.

Циклы четырёх фаз полностью развёрнуты на восемь строк. В двухколоночных фазах строка шрифта читается и вращается один раз, её значение держится в E. Формула `(old XOR glyph) AND keep XOR glyph` объединяет её с экраном без временного стека и повторных вращений для второй колонки. Приращения источника и экранного адреса остаются 16-битными, как у старого бэкенда. Для инверсии байт глифа перед вращением XOR-ится с 3Fh.

Бэкенд занимает **549 байт** против **120 байт** прежней пиксельной части: рост 429 байт, дополнительного знакогенератора или кэша не требуется. Размещение автономного бэкенда — ED00h–EF24h, ниже аппаратной области STD. Результаты при 1152 символах:

| Режим | Прежний BIOS, с | Оптимизированный, с | Снижение времени |
|---|---:|---:|---:|
| Основная память, по символу | 0,875269 | 0,746389 | 14,72% |
| Страница 0, по символу | 1,077012 | 0,948132 | 11,97% |
| Основная память, пакет | 0,923725 | 0,794845 | 13,95% |
| Страница 0, пакет | 0,940428 | 0,811548 | 13,70% |

Пакет этого варианта по-прежнему вызывает полный BIOS для каждого символа; это оптимизированный штатный путь, а не сырой интерфейс с удалением проверок и посимвольного сохранения ABI. Варианты с готовыми сдвигами и 8×8 выше имеют отдельный сырой пакетный интерфейс, поэтому сохраняют больший выигрыш.

Запуск только этой проверки:

```powershell
python scripts/emu80/benchmark-shifted-font.py --runtime .local/monitor2-001 --modes 3 --report docs/bench/optimized-standard-001/results.json
python source-apps/fontbench/check-shifted.py --out docs/bench/optimized-standard-001/cpu
```

Три повтора всех четырёх размещений/вызовов совпали по тактам и битмапу. CPU-проверка расширена до **614 случаев**, включая все 224 печатных кода KOI-8 в обычном и инверсном режиме, четыре фазы и крайние позиции, KOI-7, альтернативный FONT_IT.FNT, непустой фон и сохранение регистров. Проверка инверсии и альтернативного шрифта выполнена также через шлюз на плоской CPU-модели; реальное переключение страниц и обычный вывод проверены отдельно в Emu80.
