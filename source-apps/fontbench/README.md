# Бенчмарки рендера шрифтов

## Общий с FONT код

Актуальные `6RotateQuads`, `6PackedQuads`, `6FullQuads`, `COMPACT6`, `FAST8`, `CPM4` и `FAST4` собираются из тех же `source/font/ENGINE.asm`, `COMPACT.asm`, `ALIGNED.asm`, что и устанавливаемые движки. `FONT_BENCH_MAIN` задаёт размещение и установочную обёртку. Код, встроенный шрифт и подготовленные плоскости лежат в собственном блоке DLL в MAIN. Изменения ядра и фронтенда делаются в `source/font`.

Эти DLL предоставляют все пять публичных фронтендов напрямую. FontBen подменяет публичные BIOS-входы, все соответствующие MXCALL-адреса, внутренний скалярный переход D815h, вход переключения KOI и ширину в дескрипторе. Перед выводом отчёта и выгрузкой всё восстанавливается. BIOS-прогон не подменяет ничего. Поведение пяти API, KOI7/8 и инверсии одинаково в MAIN и в резиденте. В обычных пиксельных ядрах нет XOR 0/NOP для инверсии: выбирается отдельный набор до цикла.

Команды `-E=STANDALONE` и `-E=ALL` выбирают актуальную коллекцию; `-E=LEGACY` — прежние контрольные реализации. Контрольные варианты ROW6, 4DUP, ROW8, COL6PRE и остальные доступны явно. Отдельные старые FontLab.com/FontMap.com/FontBlk.com больше не занимают системный образ: их варианты доступны в едином FontBen через Engine DLL.

В актуальных ядрах 6×8 четверки чередуют вертикальное направление. Fast8 и выровненный пакет графических 8×8 чередуют его между глифами. Невыровненные пакеты 8×8 идут вдоль пиксельной строки и читают экран на краях. [Матрица с чередованием направления](../../docs/bench/fontben-alternating-2026-11-21/README.md)

Пары для текущего сравнения включают 6x8/Rotate → 6RotateCol4, 6x8/Packed → 6PackedQuads, 6x8/Fast → 6FullQuads, 8x8/Rotate при выравнивании → FAST8, 4x8/Packed → CPM4 и 4x8/Fast → FAST4. Для BIOS сначала устанавливается нужный FONT. Для `FontBen.com -E=FAST4 -Q -N` выберите шрифт без резервации MAIN, например `FONT 6x8/Rotate`. На H: автономный FAST4 загружается из `BENCH/FontBen/Font4Fst.dll` и берёт обе таблицы из DLL. WIN8 использует исходный знакогенератор оконного монитора, а ROW8 и FAST8 — исправленный KOI8-R. Проверка `python source-apps/fontbench/check-resident.py` принимает флаг `--inverse` для BIOS и актуальных standalone. [Матрица BIOS и standalone](../../docs/bench/resident-vs-standalone/README.md)


## FontBen.com: общая сетка ABI/API

FontBen.com, FontBank.dll, FontBank.com, TextBen.com, TextBank.com, справка Readme.txt в KOI8-R и DLL движков находятся в `A:\Bench\FontBen\`. Весь каталог BENCH можно перенести в корень H:; FontBen и TextBen ищут участников на диске своего запуска. Для современной матрицы FontBen передаёт FontBank.dll указатели на корпус и буфер MAIN через MODULE_CALL. DOS загружает DLL в отдельный EXEC с выравниванием 256 байт и поправками HIGH8. Исполнитель копирует текст в собственную BSS, затем измеряет операции по ВИ53. После каждого вызова FontBen освобождает handle. FontLab использует FontBank.com с текстовым аргументом. Движки Engine6.dll, EngineP.dll, EngineM.dll, EngineB.dll, Engine4.dll и EngineS.dll и EngineW.dll загружаются штатным MODULE_LOAD в MAIN; самостоятельно они не запускаются.

Каждый выбранный standalone-движок испытывается через одну и ту же сетку из пяти функций: `printChar`, `printCharRaw`, `printStringZ`, `printStringRawZ`, `printStringRawLim`. Перед этапом FontBen подменяет пять публичных JMP BIOS и шесть адресов строковых обработчиков в таблице MXOS_CALL, включая MAIN-варианты строковых функций. Актуальные standalone-модули предоставляют собственные публичные функции из source/font. Историческая коллекция LEGACY и отдельно выбираемый ORIONM1 используют общие строковые обёртки над локальными пиксельными ядрами; StringZ у MXOS1, MON2, RAMFOS и WIN8 использует отдельные исторические циклы, описанные ниже. Поэтому измеряется весь публичный вызов, а не один пиксельный цикл. После этапа, перед отчётом, при ошибке и перед выгрузкой DLL исходные адреса восстанавливаются. Вариант BIOS использует установленный системный движок без подмены.

MAIN вызывает публичный BIOS ABI напрямую. Из BANK посимвольный вывод вызывает F81Bh или F824h, строковый проходит через MXOS_CALL. Перед одинаковым посимвольным циклом CMD читает курсор, а CMDZ вызывает пустой StringZ. Для строк NEAR вызывает штатные `PRINT_STRING_*` с указателем в банке клиента: MEM передаёт до 20 байт внутри COMMAND. Far256 использует общий 256-байтный буфер BIOS, USER — собственный MAIN-буфер, выделенный через ARENA/ALLOC. Во всех маршрутах работает выбранный движок. Накладные расходы MXOS_CALL входят в измерение. На один движок приходится 18 измерений для одного состояния пререндера или 36 для обоих; неприменимые клетки обозначаются прочерком.

Для прямого сравнения `printStringRawLim` и `printStringRawPseudo` установите нужный движок командой FONT и запустите `FontBen -R`. Обе стадии используют один корпус из 22 строк по 42 знакоместа с двумя вертикальными разделителями и одной горизонтальной линией. Время измеряется в MAIN, без установки движка и очистки экрана.

Текст зафиксирован в `corpus.koi8` и встраивается при сборке. Обычная сетка выводит 924 байта: 21 строку по 42 кода и CRLF. Raw рисует и эти два кода как глифы. В режиме фаз `-X0…3` это 22 явно позиционированные строки по 42 печатных кода. При X=6 пикселей даже 44 глифа занимают только 358 из 384 пикселей. [Актуальные результаты FontBen](RESULTS.MD)

Исторические отчёты использовали 1152 байта, 24 блока по 46 печатных байтов из `A:\README.TXT` и CRLF. В текущей сетке RawChar выводит и код 00h, RawZ останавливается на NUL, RawLim печатает ровно BC байт. Полные 6×8 используют 256 глифов FONT.PF, 8×8 — 256 глифов оконного монитора, 4×8 — знакогенератор порта CP/M. COMPACT6 содержит 162 глифа FONTKOI.PF, отсутствующие коды отображаются глифом DEL (7Fh), пустым прямоугольником. В PACKED и BLOCK32 отсутствующие глифы обслуживает полный посимвольный путь. По умолчанию используется KOI8 без инверсии. Опция `-I` включает инверсию для BIOS и актуальных standalone во всех MAIN/BANK вызовах. Заголовок отчёта содержит I для инверсии и N для обычного режима. После каждого измерения инверсия сбрасывается. LEGACY проверяется в обычном цвете. Переключение KOI и ESC проверяются отдельно от матрицы.

| Параметр | Назначение |
|---|---|
| `-E=BIOS` или `-K` | Установленный BIOS без подмены; выбор по умолчанию |
| `-E=STANDALONE` | Шесть актуальных standalone-сборок из source/font |
| `-E=LEGACY` | 24 прежних экспериментальных и исторических варианта, только обычный вывод |
| `-E=ALL` | BIOS и шесть актуальных standalone-сборок |
| `-E=имя[,имя]` | Один движок или список; повторные `-E` добавляют выбор |
| `-P=OFF`, `-P=ON`, `-P=BOTH` | Для LEGACY: выключен, включён или оба состояния. BIOS и актуальных standalone всегда тестируют единственное состояние установленного/выбранного модуля |
| `-S` | Только printChar/printCharRaw: MAIN, BANK CMD и BANK CMDZ; 6 этапов на состояние пререндера |
| `-I` | Инверсный вывод BIOS и актуальных standalone: пример FontBen.com -E=CPM4 -I |
| `-N` | Не сохранять файл |
| `-Q` | Пропустить показ итоговой таблицы и ожидание Enter |
| `-?` | Справка |

Вместо `=` допустим пробел; регистр имён не важен. Первый `-E` заменяет выбор BIOS по умолчанию. Для каждого движка выводится своя таблица; результаты всех выбранных движков последовательно записываются в один `B:\FONTBEN.TXT` через DOS OPEN/WRITE/CLOSE. При обычном запуске после каждой таблицы ожидается Enter; `-Q` выполняет всю выбранную серию подряд.

OFF отключает ускоряющие таблицы SCALAR12/CACHE/QUAD/COLD/WARM/HALF/PACKED и ROW6/REMAP32/BLOCK32: остаётся локальный посимвольный или вращающий четвёрки путь. MXOS1, MON2, RAMFOS, ROTLINE, OPT, ROTATE, ROW8 и три формата 4×8 не меняют алгоритм от этого флага. При WARM полный проход по тому же корпусу выполняется вне таймера перед каждым этапом; COLD очищает кэш перед этапом.

`TRIPACK` загружается из EngineQ.dll и участвует в той же сетке пяти MAIN API и всех применимых BANK-вызовов. Запуск: `FontBen.com -E=TRIPACK -P=ON`; сравнение: `FontBen.com -E=ROW6,COL6PRE,TRIPACK -P=BOTH`. OFF использует прежние локальные вращающие ядра ROW6. ON хранит все 256 глифов в трёх построчных массивах по 2048 байт: `(b<<2)|(b>>4)`, `(b<<4)|(b>>2)`, `(b<<6)|b`, с отсечением до байта. Последний массив содержит исходный глиф в младших шести битах, поэтому отдельная копия шрифта не нужна. Адрес строки меняется через INC старшего байта указателя, как у ROW6/COL6PRE. Четвёрки объединяют поля через XOR/AND/XOR без чтения экрана; скалярный COL6PRE тем же приёмом сохраняет соседние пиксели экрана. Режим выбирается при инициализации, в пиксельном цикле выбора между вращениями и пререндером нет. Инверсия, как и для остальных standalone-вариантов этой сетки, не поддерживается.

CPU-проверка и сравнение MAIN: `python source-apps/fontbench/check-triple.py`. Проверяются все 256 кодов в четырёх фазах, сохранение соседних пикселей, неизменность таблицы, публичные регистры и строковые головы/хвосты. Результаты модели 8080 при 2 МГц сохраняются в docs/bench/triple-packed; это отдельные данные, не замеры ВИ53 в Emu80. Полный прогон MAIN/BANK после сборки согласованной ОС: `python source-apps/fontbench/check-grid.py --engine TRIPACK --pre BOTH`.

```text
FontBen.com
FontBen.com -E=ROW6 -P=ON
FontBen.com -E=SCALAR12,QUAD,BIOS -P=BOTH
FontBen.com -E 4DUP -P ON -Q
FontBen.com -E=ALL -N -Q
```

Внутренние одиночные callbacks ROW6/REMAP32/BLOCK32 и 4×8 могут разрушать регистры: их сохраняет общий публичный Char/Raw-вход, а строковые головы/хвосты сохраняют только ещё нужный указатель текста. Пакетные callbacks сохраняют BC/DE/HL; обёртка не дублирует это сохранение. Отдельные входы raw6/pre6/raw8 пиксельного ядра сохраняют прежний контракт, а вложенный DLL-адаптер использует их внутренние helpers без второго набора PUSH/POP. Для 8×8 указатель текста хранится в BC; восьмая строка глифа обходится без ненужного продвижения указателей. Для 6×8 вращения и пререндер имеют самостоятельные циклы чтения и рисования четвёрок; нужный scalar/batch-вход устанавливается при инициализации DLL. В измеряемом пути нет проверки variant/preEnabled и перенастраиваемого перехода между ядрами. В 4DUP продолжение цикла расположено сразу после пары, исключая безусловный переход на каждой итерации.

Контроллер находится ниже 2000h. DLL и их таблицы занимают собственный блок MAIN от 2000h до конца образа, выделенный менеджером памяти; области разных движков перекрываются только после выгрузки предыдущего модуля. Нативный BIOS использует уже установленный FONT-модуль и его постоянную резервацию. FontBen не строит, не отключает и не освобождает её. Временный корпус и отчёт для BIOS используют 3000h; собственный банковый буфер выделяется в свободной арене 3000h–38FFh. Standalone требует memTop >= 84FFh и использует прежнюю арену 2000h–7BFFh; перед ним следует установить модуль без нижних таблиц. Загрузка, подготовка шрифта/пререндера, очистка экрана, выделение буферов и отчёт исключены из времени. ВИ53 читается локально в MAIN и BANK.

Сборка: `powershell.exe -NoProfile -File scripts/build/build-project.ps1 OS`, затем `powershell.exe -NoProfile -File scripts/images/build-image.ps1 SystemEmuWritable`. CPU-проверка всех DLL: `python source-apps/fontbench/check-engines.py`. Проверка полной сетки в собственном видимом Emu80: `python source-apps/fontbench/check-grid.py`; для DLL — например `--engine ROW6` или `--engine 4DUP --pre ON`. Отчёты находятся в docs/bench/native-grid и docs/bench/engine-grid.

## FontLab.com: коллекция standalone-движков

Прежняя коллекция сохранена в `H:\Bench\FontBen\FontLab.com` (bin/FONTLAB.i80); исходник LEGACY.asm/legacy-main.inc. Параметры и исторические результаты ниже относятся к FontLab. FontBank.com обслуживает прежний FontLab.

### Параметры FontLab

Без ключей выбираются standalone и системные движки, main и BANK: 86 строк, 172 измерения. `-E=STANDALONE` сохраняет прежнюю коллекцию экспериментальных ядер; `-E=KERNEL` или `-K` проверяет только публичные системные API. Системные строки включают `mx_printChar`, `mx_printCharRaw`, обычный и прямой строковые API с Win32, Far48 и Far1152. Регистр ключей не важен; повторный ключ заменяет предыдущее значение. Неверный ключ или пустой отбор показывает справку.

| Ключ | Значения | Назначение |
|---|---|---|
| `-E=` | `STANDALONE`, `KERNEL`, `ROW6`, `ALL` | Коллекция движков; по умолчанию ALL |
| `-K` | — | Краткая форма `-E=KERNEL` |
| `-F=` | `4`, `6`, `8`, `ALL` | Геометрия; текущий системный API относится к 6×8 |
| `-P=` | `RAW`, `PACK`, `DUP`, `ALL` | Формат 4×8 |
| `-B=` | `MAIN`, `BANK`, `BOTH` | Где исполняется цикл; DOS сохранён как псевдоним BANK |
| `-C=` | `CHAR`, `SERIAL`, `GROUP`, `WIN32`, `FAR48`, `FAR1152`, `ALL` | Способ вызова; WIN20 и WIN256 сохранены как псевдонимы WIN32 |
| `-S` | Только printChar/printCharRaw: MAIN, BANK CMD и BANK TEXT; 6 этапов на состояние пререндера |
| `-I` | Инверсный вывод BIOS и актуальных standalone: пример FontBen.com -E=CPM4 -I |

| `-Q` | — | Пропустить таблицу и ожидание Enter |
| `-?` | — | Справка |

Примеры: `FONTLAB -K` — только системные API из main и BANK; `FONTLAB -K -B=BANK -C=WIN256 -Q` — один штатный банковый строковый путь; `FONTLAB -E=STANDALONE -F=4 -P=DUP -C=SERIAL -Q` — сохранённый движок 4×8. Неизмеренные сочетания помечаются прочерком. Все standalone-движки доступны из банка через штатный строковый API.

Реализации сгруппированы в [engines/](engines/README.md). Monitor — локальная копия исторического пиксельного ядра; Opt меняет её локальный вход. На время standalone-этапа тест заменяет посимвольные JMP-входы BIOS и строковые JMP-входы BIOS с соответствующими слотами MXOS_CALL. После этапа, перед инфострокой и при ошибке они восстанавливаются. Системные строки с префиксом API используют установленный BIOS. `mx_printCharRaw` и прямой строковый вход получают только печатные байты. CRLF обслуживает обычный BIOS.

FontLab.com имеет IMAGE_FLAG_MAIN. На каждое банковое измерение он штатно запускает FontBank.com с IMAGE_FLAG_BANK через FILE_EXEC_NATIVE. Банковое приложение получает согласованный адрес блока параметров в аргументах, готовит собственный текстовый буфер и ведёт таймер внутри себя. Вход/возврат, чтение файлов, подготовка текста и выгрузка исключены из времени. RET освобождает EXEC-банк и его дочерние ресурсы средствами DOS. Без служебного аргумента FONTBANK показывает подсказку запуска FONTBEN.

FontBank.com печатает поток из собственного банка через MXOS_CALL. SERIAL/GROUP и Win32 используют один PRINT_STRING_BANK на весь поток; штатный адаптер переносит порции до 32 байт в аппаратное окно. Отдельный TEXT_PRINT в новой сетке использует 256-байтный main-буфер BIOS. Far48 переносит 48 печатных байт + CRLF (50 байт), добавляет локальный NUL и вызывает PRINT_STRING_MAIN для каждой строки. Far1152 переносит весь поток с NUL (1201 байт) одним memcpy_far и вызывает PRINT_STRING_MAIN один раз. FbMain.dll и вложенные MODULE_CALL больше не нужны.

В MAIN цикл и текст находятся в основной памяти; в BANK цикл выполняется в отдельном EXEC-банке. CHAR вызывает `mx_printChar` для каждого байта. Остальные MAIN-прогоны вызывают PRINT_STRING_MAIN один раз на весь поток; выбранный standalone-фронтенд обрабатывает его пакетами. Передача текста и вызовы API входят в замер BANK. MAIN у транспортных вариантов — контрольный повтор без копирования. ВИ53 читается локально после полного вывода; интервал должен быть короче периода счётчика (8,388608 с). Подготовка, очистка, проверка изображения, инфострока и запуск/выгрузка BANK COM исключены из времени.

Автономный тест сравнивает штатный BIOS 5×7, полный набор готовых сдвигов 12 КБ и настоящий ограниченный кеш с генерацией сдвигов при промахе. Рендеры 6×8 и 8×8 используют один встроенный линейный FONT.PF; 4×8 — отдельный знакогенератор CP/M Syabr. Все варианты получают одинаковые 1152 байта из встроенного `corpus.koi8`. Корпус содержит печатные коды KOI-8 и пробелы. Копирование текста в рабочую область выполняется до запуска таймера. Текст размещается в сетке **48×24** без прокрутки, пригодной для последующего сравнения с 8×8. Прежняя строка 20h–4Fh больше не используется: её 48 кодов целиком помещались в 53 слота и давали идеальный hit-only второй проход.

Внутри COM результат сравнивается с исходными глифами и корпусом: 36 экранных столбцов для 6×8, 48 для 8×8 и 24 для 4×8, по 24 знакоместа с шагом 10 пикселей; общий результат — `Bitmap: PASS/FAIL`. Полная таблица 12 КБ формируется при сборке. Для кеша отдельно измеряются первый экран (cold) и повторный (warm), из main и отдельного EXEC-банка. В cold входят Query BIOS, инициализация индекса и генерация глифов; предзаполнения нет. В warm не выполняется даже очистка индекса, но промахи и вытеснения по-прежнему возможны: повторный проход не означает попадания всех символов. Выровненный 8×8 включён в COM: он копирует исходные восемь байт глифа в ячейку шириной восемь пикселей без растягивания, пререндера, масок и чтения экрана. Восемь строк развёрнуты, пакет не вызывает подпрограмму на каждый глиф. Пиксельное ядро выводит коды напрямую; общий фронтенд обслуживает CRLF через BIOS. Его экран занимает 48 столбцов вместо 36 и проверяется отдельно по исходным глифам.

### Общая таблица и сериализованные варианты

`matrix-main.inc` задаёт 86 строк MAIN/BANK (172 этапа при полном отборе). Мониторный движок сохранён локально; развёрнутые циклы, повторное использование поворотов и пакетные пути самостоятельных ядер сохранены.

После каждого измерения снизу показаны номер этапа, MAIN/BANK, геометрия, режим и время. Паузы нет; очистка области текста и инфострока находятся вне замеров. Отчёт сохраняется в B:\FONTBEN.TXT через FILE_HANDLE OPEN/WRITE/CLOSE с усечением прежнего файла. Итоговая таблица выводится постранично; переход и возврат — Enter. Перед выходом модули выгружаются, режим текста восстанавливается. Интеграционная проверка: `python source-apps/fontbench/check-emulator.py --report docs/bench/engines/full`.

Входы `serialBIOS`, `serialFull`, `serialCache` принимают HL=текст, C=0..48 и сохраняют A/BC/DE/HL один раз на пакет; CF=1 при длине больше 48. Строка должна помещаться на экране. Monitor serial вызывает локальную копию обработчика печатных символов без внешнего сохранения регистров каждого символа. Full/cache переходят непосредственно в тело рендера и общее продолжение, без посимвольного CALL/сохранения общего набора регистров. На пакет три первых POP общего эпилога временно заменяются JP продолжения, затем исходные POP восстанавливаются; посимвольный путь не платит за дополнительный JMP. Стенд работает с DI, входы нерекурсивны. При недостатке кеша пакетный fallback использует внутренний обработчик BIOS, не пытаясь снять отсутствующий посимвольный стек. Сырые full/cache, как прежние варианты, не интерпретируют управляющие коды. Их cold/warm следуют друг за другом отдельно для main и BANK.

Текст для всех режимов одинаков: 1152 печатных байта README, CRLF после каждой из 24 строк и завершающий NUL, итого 1201 байт. Курсор задаётся один раз до замера; межстрочных SET_CURSOR_POS нет. Шаг строк — штатные 10 пикселей, текст занимает строки экрана 0–237, инфострока — 248–255. Общий ASCIIZ-фронтенд отдаёт полные четвёрки выбранному ядру 6×8, а невыровненные головы и хвосты — штатному посимвольному рендеру. Этот расход входит в BANK Win32, где границы порций могут разрезать четвёрку.

Полный набор готовых фаз остаётся самостоятельным вариантом для банковых программ. Канонический `FONTBEN.shifts.bin` по-прежнему содержит все четыре фазы в 12-КБ формате и пригоден старым стендам. В текущем standalone исходные 2048 байт уже находятся по 2800h, поэтому их дубликат 3800h–3FFFh переиспользован под дополнительные тестовые процедуры: 10 КБ готовых сдвигов + 2 КБ исходной фазы дают тот же полный набор 12 КБ без генерации в рендере. Старый внешний SHIFT без STANDALONE_SERIAL сохраняет прежнее размещение всех четырёх фаз. Полный набор не ограничен алфавитом README, содержит все 256 кодов и не зависит от кеш-арены. Если верхняя арена текущей BIOS меньше 4072 байт, упакованный COMPACT6 временно занимает 4000h–4FE7h в main; фаза 4 полного пререндера восстанавливается из FONT.PF перед следующим этапом, вне замера. Это нативный резерв стенда, без API менеджера памяти.

Прогон с новым потоковым протоколом — `docs/bench/remap32/stream-full/`. `report-matrix.py` строит таблицу из его results.json. Старые прогоны с построчной установкой курсора и MODULE_CALL имеют другую методику; их числа не являются замером нового пути.

### Три формата 4×8

Шрифт извлечён из CP/M Syabr 0.1 без изменения битмап: источник и раскладка описаны в [FONT4CPM.md](FONT4CPM.md). Внутренние форматы: `4raw` — 2048 байт, полезен младший полубайт строки; `4pack` — 1024 байта, два последовательных кода в одной восьмибайтной записи; `4dup` — 2048 байт, один и тот же полубайт повторён в обеих половинах. У RAW и DUP строки глифов разложены по восьми 256-байтным страницам, как в BIOS CP/M; код символа сразу задаёт младший байт адреса. Плотный формат сохраняет восьмибайтные записи и размер 1024 байта. Подготовка форматов выполняется вне измерения в 3000h–37FFh; перед новым направлением main/BANK восстанавливается прежняя фаза 0 полного пререндера. Подготовка таблиц остаётся локальной, без динамического выделения памяти под шрифт.

Для каждого формата измеряются CHAR, SERIAL, FAR48 и FAR1152 из main и BANK. Serial читает строку публичным GET8 и вызывает пакетный рендер; Char вызывает main-модуль на каждый символ. Строки Win32 остаются только как контрольный main-повтор, банковое значение отсутствует: публичный PRINT_STRING_BANK не принимает экспериментальное ядро 4×8.

Формат и продолжение цикла выбираются при подготовке таблицы, вне замеров. Полные пары читаются POP из текста, SP сохраняется и восстанавливается один раз на пакет; до его восстановления нет CALL/PUSH/RET. Экранный указатель вычисляется один раз на пакет, далее используется INC D; курсор публикуется после пакета. Входы нерекурсивны и требуют DI, как остальной standalone. Голова и хвост работают с нормальным стеком.

Полные выровненные пары записываются без чтения экрана; начало с правого полубайта и нечётный хвост используют развёрнутый маскированный путь. У плотного формата выбор ядра учитывает чётность обоих кодов, а не позицию символа в строке. Все три формата дают одинаковый экран. Количество символов сохраняется: 48×24, то есть занятая ширина составляет 192 пикселя. Сырые рендеры не разбирают управляющие коды, инверсию и прокрутку.

`python source-apps/fontbench/check-font4.py` проверяет 256 кодов во всех форматах, пары, непустой фон, начало/хвосты, границы, сохранение регистров, подготовку и восстановление таблиц. Независимые компараторы 4×8 и 6×8 проверяются также намеренной порчей последнего байта. Память экранного эталона больше не требуется: 6×8 сравнивается непосредственно с исходным шрифтом и корпусом, освободившееся место занято кодом и таблицей режимов.

### Четверки без чтения экрана

`quad.inc` добавляет отдельные входы `quadRender` (ограниченный кеш) и `quadFullRender` (полная таблица 12 КБ). HL указывает текст в основной памяти, C задаёт 0..48 кодов, длина кратна четырём. Начальный X должен быть кратен восьми пикселям, вся строка должна помещаться на экране; неполная четверка и неверные параметры возвращают CF=1 до записи экрана. A/BC/DE/HL сохраняются, остальные флаги разрушены. Это сырой normal KOI-8 интерфейс без управляющих команд, инверсии и прокрутки. Хвосты с чтением экрана пока отсутствуют; прежний посимвольный путь сохранён отдельно.

Каждая четверка шириной 24 пикселя собирается прямо при записи трёх экранных байтов: фазы 0 и 6 образуют первый байт, остаток 6 и фаза 4 — второй, остаток 4 и исходный глиф — третий. На восемь строк приходится 24 записи, ни одного чтения видеопамяти и ни одной сохраняющей маски. Пиксельный цикл кеша/полной таблицы развёрнут и пишет восемь строк каждого столбца подряд. BC указывает экран, DE/HL удерживают два источника; между столбцами меняются только источники, восстанавливается Y и выполняется `INC B`, то есть +100h. Все три столбца записываются целиком, поэтому порядок столбцов не требует чтения фона. В рабочей памяти хранятся четыре указателя, промежуточной битмапы и копии четырех входных кодов нет. Общий блок четверок занимает 526 байт, из них 196 байт — пиксельное ядро кеша/полной таблицы; новые бескешевые ядра и подготовка таблицы вынесены в `quad-direct.inc`.

При выборе каждого кешированного сдвига он защищается от вытеснения на два следующих получения указателя. Для фиксированной тройки кешируемых фаз это реализовано двумя байтами последних номеров слотов: FIFO пропускает оба защищённых номера. После выбора третьего указателя выделений до завершения рисования больше нет, четвёртый глиф берётся непосредственно из шрифта. Это эквивалент прибавки времени жизни на два шага без таблицы времён для всех слотов. Защита сбрасывается между четверками, перед возвратом восстанавливается обычный FIFO. Требуется минимум три слота; при меньшей ёмкости вход возвращает CF=1. Самостоятельный вход нерекурсивен.

FONTBEN дополнительно показывает шесть замеров: полная таблица и cold/warm кеш для четверок из main и DOS. В обоих случаях один вызов получает ровно четыре кода. Из страницы DOS они передаются через BC/DE и помещаются в четырёхбайтный буфер кодов в main, а рендер сразу пишет экран. Копирование кодов и один межстраничный вызов на четверку входят во время; посимвольные замеры сохранены. Независимая проверка `python source-apps/fontbench/check-quad.py` проверяет 556 случаев, включая все коды, непустой фон, отказ для хвостов/выравнивания и вытеснение при трёх слотах; дополнительно проверяется отсутствие экранных чтений и стековых команд в пиксельном ядре. Результаты эмуляторных замеров и ограничения находятся в `docs/bench/quad-001/`.

В оптимизированном варианте hit четверки не сохраняет AF на стек и не вызывает отдельный декодер номера слота; защита указателей обновляется в регистрах. Генерация восьми строк каждой фазы развёрнута. Исходная фаза посимвольного пути проходит до проверки инвалидирования: она не запрашивает и не инициализирует кеш вообще. Управляющие коды фильтруются один раз при загрузке README; сырой цикл рендера не повторяет разбор. Актуальные замеры — `docs/bench/quad-opt-001/`.

### Четверки со сдвигами на лету

`quadDynamicRender` и `quadHalfRender` используют тот же интерфейс/проверки и выводят те же четверки без поиска, промахов, вытеснения и защиты кеша. Первый вход читает исходный шрифт и не использует кеш-арену. Второму нужна одна постоянная таблица циклического поворота на четыре бита, восемь байт на глиф: 2048 байт для всех 256 кодов. `quadPrepareHalf` получает арену BIOS и заполняет её вне измерения, помечая прежний кеш недействительным; на каждый символ служба BIOS не вызывается. При отсутствии подготовленной таблицы `quadHalfRender` возвращает CF=1 без вывода. Требуются 2048 доступных байт и начало арены, выровненное на восемь; при отказе подготовки таблица недоступна. Это нормализованный линейный шрифт standalone, не прямой разбор MXFN.

Для шестибитных строк `a,b,c,d` результат — `(a<<2)|(b>>4)`, `((b<<4)&0F0h)|(c>>2)`, `((c<<6)&0C0h)|d`. На 8080 вычисляются `r4=ROR8(b,4)` и `r2=ROR8(c,2)`: первый результат используется дважды через `r4 AND 03h` / `r4 AND 0F0h`, второй — через `r2 AND 0Fh` / `r2 AND 0C0h`. Поэтому вытолкнутые части переходят в следующий байт, повторных поворотов для левой части нет. В бескешевом варианте на строку приходятся два ADD A для `a`, четыре RRCA для `b` и два RRCA для `c`; в варианте с таблицей RRCA для `b` исключены. Маски выделяют части глифов, экран не читается.

Новые ядра идут по строкам четверки: DE указывает экран, B/C удерживают части текущей строки. Четыре исходных указателя читаются POP HL из рабочей памяти и обновляются для следующей строки. SP сохраняется один раз на четверку, до восстановления SP нет CALL/PUSH/RET. Временного пиксельного буфера нет, используется только восемь байт указателей. По четыре строки развёрнуты, две итерации завершают глиф. Публичные регистры сохранены. Прежний результат микротеста против посимвольного чтения битмапы стеком к этому алгоритму не относится.

FONTBEN показывает `Main/DOS quad raw` и `Main/DOS quad rot4`, сохраняя прежние режимы. Методика та же: четыре кода на вызов, подготовка таблицы вне замера, 1200 байт README, проверка всех 9216 байт изображения. Полный новый прогон и снимки — `docs/bench/quad-direct-001/`. На этом корпусе бескешевый вариант немного медленнее прогретого кеша, но не занимает 4-КБ арену; вариант rot4 использует 2 КБ без lookup/FIFO.

### Готовые сдвиги компактного COMPACT6

`python source-apps/fontbench/analyze-fontkoi.py` читает MXFN и создаёт проверочный образ и расчёт в `docs/bench/quad-opt-001/fontkoi/`; системный шрифт и рендер не меняются. Текущий COMPACT6 содержит 162 кода: 20h–7Fh, C0h–FFh и A3h/B3h, всего 147 различных восьмибайтных битмап. Полностью разложенные три сдвига занимают 40 байт на уникальный глиф, то есть 5880 байт без поиска. Исходная фаза остаётся в уже загруженном шрифте. Такой формат в 4 КБ не помещается даже после объединения одинаковых глифов.

В 4 КБ помещается другой формат: три готовых поворота по восемь байт на глиф, 147×24 = 3528 байт; две части фаз 4/6 сохраняются в одном байте и выделяются масками при выводе, без вращений. Прямой поиск по всем 256 кодам через 16-битный относительный указатель занимает 512 байт, всего 4040; с 32-байтным заголовком — **4072 байта**, остаётся 24. Непредставленные коды ссылаются на DEL (7Fh), пустой прямоугольник, одинаковые битмапы разделяют запись. Заголовок/таблица/данные располагаются плотно, без округления начала к странице; выравнивание может съесть оставшийся запас. Таблица указателей внутри образа содержит смещения, при загрузке их можно заменить абсолютными адресами без роста размера. Альтернатива с байтовым номером глифа занимает 3784 байта без заголовка, но требует умножения номера на 24 при поиске. Формат подключён к standalone через `quadPackedRender` и измеряется вместе с остальными вариантами. Указатели превращаются в абсолютные вне замера, поиск остаётся прямым по всем 256 кодам. Четыре строки развёрнуты; вывод идёт сразу в экран без чтения VRAM. Исходная фаза четвёртого символа получается двумя RRCA из готовой фазы 0, поэтому при самом рендере отдельный исходный COMPACT6 не нужен. Конструктор стенда использует 403 байта служебных индексов и встроенный FONT.PF; сборка проверяет совпадение всех представленных глифов с COMPACT6. Эти данные конструктора не входят в 4072 байта резидентной таблицы, подготовка исключена из времени. Схема зависит от фактических битмап текущего файла, а не подходит автоматически любому MXFN. Штатный системный рендер не меняется.

Полная матрица 69 пар, снимки трёх страниц, проверка битмап, чтения и усечения файла отчёта сохраняются в `docs/bench/font4-opt/full/`. Общая таблица строится командой `python source-apps/fontbench/report-matrix.py --results docs/bench/font4-opt/full/results.json --out docs/bench/font4-opt/full/table.md`.

### Устройство ограниченного кеша

`cache.inc` получает границы, размер и эпоху через `MXOS_CALL MXOS_BIOS_GLYPH_CACHE` с A=0. Перед каждым глифом проверяется опубликованный `GLYPH_CACHE_INVALID`. При инвалидировании границы запрашиваются снова, индекс очищается, указатели и число слотов пересчитываются; старый хвост после сужения не затрагивается. После подготовки движок сбрасывает флаг, при добавлении записей обновляет `GLYPH_CACHE_ENTRIES`. Расширение без инвалидирования сохраняет старую ёмкость до следующей подготовки — уже существующие записи продолжают работать. Это временный единственный владелец формата кеша, не интеграция кешированного вывода в BIOS. Источник глифов в этом стенде — линейный шрифт charGen, режим normal KOI-8; при его замене вызывающая сторона должна инвалидировать кеш. Разбор MXFN, KOI-7 и инверсии остаётся задачей будущего фронтенда BIOS.

Ключ кеша — **код символа и конкретная фаза сдвига**, а не весь глиф с четырьмя вариантами. Шесть бит исходного FONT.PF выровнены вправо, поэтому физическая фаза `X mod 8 = 2` уже готова: она рисуется непосредственно из charGen, без выделения слота, промаха или генерации. При недостатке кеша этот прямой путь также доступен. Для остальных фаз при промахе создаётся только один запрошенный вариант: 8 байт для фазы 0, 16 байт для фаз 4 и 6.

Lookup занимает **768 байт**, по одной странице на каждую кешируемую фазу (0/4/6). Код символа прямо индексирует нужную страницу; байт 0 означает промах, 1..255 — номер слота. На hit адрес декодируется из номера за фиксированное число инструкций 8080: `pool + token*16`, через перестановку полубайтов и маски. Участок от добавления базовой страницы индекса до готового HL занимает 95 тактов, включая проверку промаха, без выбора фазы и проверки инвалидирования. Три таблицы полных указателей заняли бы 1536 байт и уменьшили бы число доступных слотов. Поиска по диапазонам, обхода тегов и LRU на hit нет.

Слот занимает **16 байт** и содержит только один сдвиг. Для фазы 0 используются первые восемь байт; оставшиеся восемь не заполняются. Выравнивание сохраняет быстрые развёрнутые пиксельные ядра, общие с таблицей 12 КБ, без переходов через страницу внутри глифа. Общая FIFO-очередь обслуживает пары (код, фаза); две обратные страницы по 256 байт хранят код и фазу владельца каждого номера. При стандартной области DB90h–EB90h: 112 байт выравнивания, 768 байт lookup DC00h–DEFFh, 512 байт владельцев DF00h–E0FFh, запрещённый нулевой блок E100h–E10Fh, **168 слотов** E110h–EB8Fh. Всё это находится внутри выделенных BIOS 4096 байт; служебное состояние находится в программе. При недостатке места для сдвинутой фазы используется BIOS. Счётчики обновляются только на промахе/вытеснении. В прежнем варианте каждый miss строил 48 байт четырёх фаз и занимал слот 64 байта; прежние результаты сохранены в локальных отчётах для сравнения.

Независимая проверка: `python source-apps/fontbench/check-cache.py`. Она использует z88dk-ticks в режиме 8080 и проверяет все 256 кодов во всех четырёх фазах, границы экрана, сохранение регистров/флагов, FIFO, нулевую/малую ёмкость, переменное начало области, сужение и замену шрифта. Реальный Query IO.SYS вызывается через тестовый переходник, транспорт проверяется отдельным запуском из NC в Emu80.

## Перенос в BIOS

Штатный BIOS теперь использует четверки 6×8 с вращением на месте и, при явном включении FONT_RENDER, три предварительно построенные фазы в main. Системные строки API измеряют установленный BIOS; Monitor и остальные standalone-движки сохраняют свои реализации. Старая коллекция FontLab автоматически не выделяет 10-КБ буфер для системного рендера; новая штатная сетка FontBen включает и выключает его явно. Контракт включения приведён в [BIOS](../../source/bios/README.md#fontrender-0130h).

Адресация по 256-байтным страницам уже используется и проверяется в RAW/DUP 4×8. Текущие standalone 6×8 и 8×8 хранят глифы подряд по восемь байт; прямого сравнения построчной раскладки 6×8 с ними пока нет. Выравнивание начала таблицы на 256 байт само по себе не отменяет умножение кода на восемь.

Движки FONTBEN находятся только в `engines/`. Старые отдельные стенды с частными GATE/BUFFERGATE и их сборщики удалены; исторические результаты остаются в локальных отчётах `docs/bench/`.

Сборка обоих тестов: `powershell.exe -NoProfile -File scripts/build/build-project.ps1 OS`. Образ: `powershell.exe -NoProfile -File scripts/images/build-image.ps1 SystemEmuWritable`.

Запуск через NC, банковые вызовы, сохранение отчёта и возврат проверяют `source-apps/fontbench/check-emulator.py` и `scripts/emu80/check-textbench.py`. Они запускают собственный видимый эмулятор без звука и закрывают его после проверки.


## Эксперимент с построчным шрифтом

`engines/paged.inc` содержит отдельные ядра 6×8 с вращениями, 6×8 с пререндером и 8×8. Шрифт полный: восемь страниц по 256 байт, младший байт адреса — код символа, старший — строка глифа. Пререндер 6×8 занимает 10 КБ: три дополнительные фазы, исходная берётся из шрифта. Каждый экранный байт собирается из двух глифов и записывается целиком; чтения VRAM нет. Форматы готовятся вне измерения.

Ядра включены в COM-матрицу с фильтром `-E=ROW6`; для каждого есть Serial, Far48 и Far1152 из MAIN/BANK. Отдельный CPU-стенд — `python source-apps/fontbench/check-paged.py`. Он сравнивает ядра с прежними standalone-реализациями на одном корпусе README из 1152 символов; дополнительно проверяет все 256 кодов, всю VRAM, сохранение регистров и неизменность таблиц. В модели 8080 при 2 МГц: 6×8 с вращениями 493,526 → 350,246 мс, с пререндером 300,998 → 187,838 мс, 8×8 244,262 → 175,094 мс. Это времена автономных ядер; полный фронтенд BIOS измеряется отдельно. Отчёт: `docs/bench/paged-font/results.json`.

Таймер настраивается и читается локально через общую библиотеку [timing-pit.inc](../../source/include/timing-pit.inc), без вызовов BIOS/DOS и переключений банка. Чтение занимает 10 байт и 54 такта 8080 с RET, без входного CALL; аппаратные требования и интерфейс описаны в [документации таймера](../../source/include/timing.md).

## Сравнение компактного шрифта: FontBlk.com

`H:\Bench\FontBen\FontBlk.com` — альтернативная сборка того же FONTBEN, заменяющая только движки PageRaw/PagePre экспериментальными `block32.inc` и `block32-support.inc`. Прежний `FontLab.com` сохранён. Отдельный исполняемый файл позволяет сравнивать оба ядра при фиксированной раскладке стенда, не добавляя второй комплект ядер в его ограниченную main-память. Для FontBlk по умолчанию выбраны `-E=ROW6 -F=6`; доступны MAIN/BANK и Win32, Far48, Far1152. Вариант Page8 исключён.

Шрифт содержит 160 глифов: 20h–7Fh и C0h–FFh. Восьмибайтная таблица задаёт старший байт адреса каждого блока из 32 символов. Восемь строк глифа идут подряд, ядро увеличивает младший байт указателя. Шрифт занимает 1280 байт, пять плоскостей пререндера — 6400 байт; в стенде они используют прежние раздельные арены, поэтому размер COM и резерв стенда не равны полезному размеру этих данных. Четыре указателя готовятся один раз на четвёрку, до развёрнутой пиксельной части.

Ёё и остальные коды 80h–BFh заменяются в корпусе пробелами до начала измерений. Внутреннее ядро принимает только сохранённые диапазоны. Для KOI-7 достаточно заменить `blockPages+3` на страницу блока E0h; этот вариант проверяется CPU-тестом, переключение битмапы не меняет. Пользовательское переключение KOI внутри FONTBEN пока не добавлено; ядро BIOS остаётся прежним.

Примеры: `FontLab.com -E=ROW6 -F=6 -N -Q` и `FontBlk.com -N -Q`. Для полностью одинакового корпуса автоматический сравнительный прогон прежней сборки использует `check-emulator.py --block32-corpus`; новая сборка выбирается `--block32`. `check-block32.py` проверяет пиксели и сравнивает ядра в модели 8080.

## Построчная раскладка с перекодировкой: FontMap.com

`H:\Bench\FontBen\FontMap.com` сохраняет полный построчный шрифт и прежние пиксельные ядра, но при чтении каждой четвёрки перекодирует символы восьмибайтной таблицей блоков. Три RLC и маска 07h выбирают блок; младшие пять бит исходного кода сохраняются. Таблица применяется и к вращению на лету, и к пререндеру. Данные шрифта и фаз при смене таблицы не переставляются. В отличие от FontBlk, все 256 глифов, включая Ёё, остаются доступны; размер данных не сокращается.

По умолчанию выбраны `-E=ROW6 -F=6`, MAIN/BANK, Win32/Far48/Far1152. Прежний вариант запускается как `FontLab.com -E=ROW6 -F=6`. Внутренние имена строк PageRaw/PagePre сохранены, конкретную реализацию выбирает исполняемый файл. Для эмуляторной проверки служит `check-emulator.py --remap32`. CPU-тест `check-block32.py` сравнивает все три раскладки и проверяет KOI-7 заменой одной записи таблицы. Он проверяет отображение кодов, а не полный BIOS-фронтенд с управляющими кодами и запретом старших диапазонов в KOI-7.

Штатный BIOS с P=ON использует пререндер и для скалярных символов, голов и хвостов строк. OFF отключает его для всех путей. Скалярный пререндер BIOS использует COL6PRE; сравнительные числа и параметры повторного прогона приведены в docs/bench/colpre-bios/README.md.

## Сравнение скалярных ядер 6×8

FontBen.com -S -E=BIOS,MXOS1,MON2,RAMFOS,OPT,ROTLINE,ROW6,SCALAR12,FULLFAST,COL6PRE запускает два символных API через одинаковые публичные обёртки и MAIN/BANK-переходники. Для воспроизводимого отдельного варианта: FontBen.com -S -E=COL6PRE -P=ON. Для BIOS имеет смысл BOTH; SCALAR12/FULLFAST/COL6PRE с OFF используют путь без готовых сдвигов. Прочие скалярные варианты не зависят от P. EngineS.dll содержит исторические пиксельные механизмы, линейный развёрнутый скаляр и новые варианты пререндера.

MON2 и RAMFOS адаптированы к полному установленному 256-символьному FONT.PF и общим координатам 6×8. Управляющие коды исполняет общая обёртка FontBen. Это сравнение механизмов рисования, а не запуск неизменённой прошивки монитора. Очистка и наложение сохранены, специальный исторический код очистки 7Fh заменён внутренним флагом, чтобы Raw мог печатать все 256 глифов. Пробел завершает вывод после очистки, как в исторических обработчиках. Монитор SP580 использует такой же стековый механизм, отдельное дублирование одинакового пиксельного цикла не добавлено. Оконный монитор имеет выровненное 8×8-ядро и рассматривается отдельно от 6×8.

Новые ядра проверяются check-engines.py ENGINES. Штатный Emu80-прогон: python source-apps/fontbench/check-grid.py --engine COL6PRE --pre ON --scalar. Счётчики и снимки сохраняются в docs/bench/scalar-grid/<engine>/. Все вызовы идут из MAIN-ядра, банковый клиент исполняет штатный MXOS_CALL, а не код рисования внутри банка.

Результаты сопоставимых скалярных прогонов и ограничения исторических сравнений: docs/bench/scalar-grid/README.md. После удаления проверок KOI BIOS измерен повторно; прежняя серия сохранена отдельно.

Стенд check-grid.py принимает --out <каталог> для сохранения отдельной серии без перезаписи прежних отчётов.

## Исторические строковые циклы

У MXOS1, MON2 и RAMFOS нормальный printStringZ использует посимвольный ASCIZ-цикл соответствующего исторического движка, а не общий пакетный фронтенд. MXOS1 сохраняет BC/AF на строку и вызывает полный символьный адаптер для каждого байта; Monitor-2 читает байт через A/C и вызывает его до NUL; RAMFOS вызывает printCharA с дополнительным сохранением BC. Символьный адаптер сохраняет AF/BC/DE/HL на каждый символ. Для MXOS1 он входит в тело пиксельного ядра без повторного комплекта сохранений. У Monitor-2/RAMFOS однократный внешний адаптер обеспечивает нынешний контракт сохранения AF/BC/DE; его время включено.

Пиксельные механизмы MON2/RAMFOS остаются адаптированными: полный FONT.PF, единые координаты и штатный BIOS для управляющих кодов. Исторические опрос клавиатуры и эхо на принтер не воспроизводятся. RawZ/RawLim не имели исторических аналогов и продолжают использовать общий фронтенд FontBen. Режим пререндера не меняет эти три исторических алгоритма. Сравнение через `FontBen.com -E=MXOS1,MON2,RAMFOS -P=ON` сохраняет одинаковую сетку MAIN/BANK; `-S` исключает строки и для этого сравнения не подходит.

Автоматический повтор: `python source-apps/fontbench/check-grid.py --engine MXOS1 --pre ON --out docs/bench/engine-grid/historical-string/mxos1` (аналогично MON2 и RAMFOS).

Старые отчёты сохраняют исходные названия. Новые команды используют только новые имена.

WIN8 находится в enginew.asm (EngineW.dll). Пиксельный цикл соответствует D172h–D1A3h оригинального ROM; проверка check-window-font.py сравнивает машинные инструкции с учётом перемещённых адресов и проверяет все 256 глифов. Сохранены поиск 32-символьного блока, вычисление code*8, цикл восьми строк и CALL → JMP → RET для каждой строки. Таблица блоков настроена на прямые коды вместо исходной раскладки KOI7; исторические глифы 80h–BFh не соответствуют KOI8-R. Координаты и переходы строк адаптированы к FontBen. printStringZ использует исторический цикл CA4Dh–CA5Eh; обработка управляющих кодов — общий адаптер BIOS, не полный обработчик ESC оконного монитора. RawZ/RawLim — современные обёртки для сравнения в общей сетке, таких API у оригинала не было. Инверсия WIN8 пока не измеряется.

[Сравнение WIN8, ROW8 и FAST8](../../docs/bench/window8-grid/README.md): один корпус, локальный ВИ53, все 18 сочетаний MAIN/BANK. Воспроизведение: `python source-apps/fontbench/check-resident.py Window8 Fast8 Standalone8 Shared8`.

После исправления Fast8 под KOI8-R исторический WIN8 сохраняет шрифт из оригинального ROM; ROW8/FAST8 используют исправленный Win8.pf. Предыдущая матрица с одинаковым шрифтом сохранена как исторический прогон.


Для сравнения фаз 8×8 сначала установите `FONT 8x8/Rotate`, затем запустите `FontBen -X0`, `-X1`, `-X2` или `-X3`. Фазы соответствуют 0, 2, 4 и 6 пикселям от начала байта. Каждая серия сравнивает все пять текстовых API в MAIN на 22 строках по 42 глифа. Строки позиционируются явно внутри измеряемого участка, автоматических переносов нет. `-I` включает инверсию. Для сравнения выровненного пути установите `FONT 8x8/Rotate` и повторите `FontBen -X0`.

Чтобы сравнить вывод по одному и четыре байта, используйте `-E=8RotateStream,8RotateQuads`. Парный Graph8x2 доступен как отдельная экспериментальная сборка. Для сравнения строковых ядер используйте столбцы StringZ, RawZ и RawLim. Посимвольные входы служат контролем.

### Горизонтальные циклы Rotate

| Параметр `-E` | Порядок записи |
|---|---|
| `6RotateQuads` | Четыре глифа за раз. Три байтовые колонки блока записываются сверху вниз. |
| `6RotateCol4` | Штатный 6×8 Rotate. Слияние в аккумуляторе, проход по трём столбцам, развёртка на четыре пиксельные строки. |
| `6RotateRows` | Та же четвёрка. Три байта каждой из восьми пиксельных строк записываются слева направо, повёрнутые байты двух средних глифов используются повторно. |
| `6PackedQuads` / `6FullQuads` | Четвёрки с упакованными / раздельными плоскостями пререндера. |
| `8RotateQuads` | В невыровненной позиции один горизонтальный проход на пиксельную строку, по четыре байта за итерацию. |
| `8RotateStream` | Такой же проход по одному байту, с переносом битов до конца участка. |
| `6RotateStream`, `6PackedStream`, `6FastStream` | Восемь горизонтальных проходов по выровненному участку текстовой строки. Два `POP BC` читают коды очередной четвёрки в каждом проходе. |
| `4PackedStream`, `4FastStream`, `4CompactStream` | Восемь проходов по строке. Один `POP HL` читает два кода на байт экрана. Compact использует одну таблицу на 1024 байта. |

Для сравнения 4×8 используйте пары `CPM4,4PackedStream`, `FAST4,4FastStream` и `4Compact,4CompactStream`. Обычный фронтенд обрабатывает управляющие коды, невыровненное начало и хвост строки.

Имена `ROTATE6`, `PACK6K`, `FAST12K` оставлены как алиасы для воспроизведения прежних прогонов. Новые варианты доступны в FontBen. Для 8×8 используйте, например, `FontBen -E=8RotateQuads,8RotateStream -X2 -Q -N`. При `-X0` оба используют один выровненный цикл Fast8. Для 6×8 запустите `FontBen -E=6RotateQuads,6RotateRows -Q -N` с обычной сеткой MAIN/BANK.
