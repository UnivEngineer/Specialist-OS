# SDK MXOS2 для SjASMPlus и C

## Приложение на ассемблере

Добавьте `--i8080 --inc=<путь-к-sdk>/asm` в команду SjASMPlus. [Мастер-заголовок](asm/mxos.inc) можно подключать до ORG и повторно. Он объявляет вызовы BIOS/DOS, пакеты, файловые объекты и сервисы MEM и IO.

```asm
    INCLUDE "mxos.inc"
    ORG 0100h
    ld hl,message
    MXOS_CALL_REGS MXOS_BIOS_PRINT_STRING_BANK
    ret
message: db "MXOS2",0
```

Форматы FAT и релокаций, контракты драйверов и макросы размещения подключаются отдельно из `formats/`, `drivers/` и `assembly.inc`. Реализации библиотек из `lib/` размещайте в теле программы. [UI](asm/lib/UI.md) описывает двухпроходное включение, [библиотека измерений](asm/lib/timing.md) — настройку и чтение счётчика.

## Приложение на C

Путь включения для z88dk — `sdk/include`, основной заголовок — `mxos.h`. Общие типы и соглашение вызова определены в `mxos_types.h`. Файловый интерфейс, таймер и локальная куча имеют самостоятельные заголовки.

`mxos_call_packet(MXOS_CALL_PACKET*)` обращается к пакетному входу `mx_callPacket` (F800h). Структура содержит пять слов в порядке operation, HL, DE, BC, AF. Номер операции задаётся как `operation=(группа<<8)|номер`. Вызов возвращает AF как 16-битное слово, включая CF и код A при отказе диспетчера. При таком отказе пакет сохраняется. Имена `MXOS_BIOS_*` и `MXOS_DOS_*` генерируются из `source/bios/syscalls.json` в `include/mxos_syscall_ids.h`. Группа BDOS зарезервирована и возвращает UNSUPPORTED. Для CP/M используется отдельное сменное ядро.

Общим окном FFC0h управляет MEM. Для обмена между страницами используйте FAR API, для доступа к диску — секторные службы DOS.

`include/mxos.h` и `src/mxos.c` открывают службы BIOS/DOS. Переходники sccz80 в `src/mxos_z88dk.asm` направляют посимвольную печать, курсор и MEMTOP на выделенные регистровые входы MEM 1.4. Именованные обёртки C могут вызывать `mx_callRegs` (F806h) или локальную службу IO.SYS согласно контракту функции. Например, `mxos_file_call` вызывает F806h с номером `MXOS_DOS_FILEHANDLE`. В ASM регистровый макрос `MXOS_CALL_REGS` вызывает `mx_callRegs` с номером службы после `CALL`. Низкоуровневый `mxos_bios_call(MXOS_REGS*)` в MAIN принимает пять 16-битных слов entry/AF/BC/DE/HL, sizeof=10. После вызова пакет содержит выходные регистры и флаги. Ассемблерные имена `mx_*` генерируются из `sdk/asm/abi/memory.inc` и проверяются `scripts/tests/check-sdk-abi.py`.

| Группа | Обёртки |
|---|---|
| Память | memcpy/memmove с перекрытием, контрольная сумма Monitor-2, get/set memtop, освобождение модуля |
| Консоль | getch/getkey/keyscan, putch, puts, printStringLim с точной длиной, readline с нулевым терминатором, очистка, координаты курсора, DEC/HEX |
| Строки | upper для KOI, сравнение N байт с учётом регистра или без него |
| Таймер | Захват таймера, получение базы регистров и прямое чтение счётчика |
| Диски | Выбор диска, DISK_INFO и физическая ёмкость, логический сектор, flush и числовая ошибка |
| Файлы | Список FILE_INFO, stat, загрузка/сохранение целиком, удаление, переименование и копирование с явным запросом/буфером |
| Графика | Список объектов, инверсия и перенос прямоугольника через BIOS |

Префикс всех функций таблицы — `mxos_`; точные прототипы находятся в заголовке. FILE_DESCRIPTOR/FILE_INFO/DISK_INFO/FILE_COPY_REQUEST представлены массивами 32/16/48/86 байта с фиксированными смещениями из mxos.inc. Буфер списка должен иметь capacity×16+1 байт для завершающего FFh. Полная загрузка файла требует заранее проверенного размера и достаточного буфера; для потокового доступа используется интерфейс ниже.

Консольные getch/putch/puts/readline обращаются непосредственно к BIOS. Стандартные stdin/stdout/stderr будут реализованы выше SDK, вместе с CLI, наследованием потоков и перенаправлением. Файловый backend ниже предоставляет операции над конкретным открытым файлом; глобальных стандартных потоков в нём нет. Будущий CLI сможет назначать stdout файлу для команды `DISKBEN.EXE -H > B:RESULT-H.TXT`; сейчас такого синтаксиса и режима DISKBEN ещё нет.

`mxos_printStringLim(text, bytes)` выводит ровно `bytes` байт из текущей страницы и возвращает `text + bytes`. Каждый байт, включая нуль, обрабатывается как при вызове `printChar`. При нулевой длине указатель возвращается без чтения буфера. Переходник sccz80 вызывает F806h с операцией 012Eh. Для ассемблерного кода в MAIN доступен прямой `CALL bios_printStringLim` по C884h с указателем в HL и длиной в BC.

## Файловый backend

Первое API каталогов: `MXOS_MAX_PATH=128`, `MXOS_PATH` содержит массив `bytes[128]`. `mxos_chdir(path.bytes)` принимает весь буфер с завершающим 0, с необязательным префиксом диска; длина строки до 127 байт. Диск выбирается через `mxos_drive_select`. Поддерживаются абсолютные/относительные пути, `/`, `\`, . и ..; ошибка не меняет текущий каталог. `mxos_directory_get` возвращает компактный контекст — кластер, `mxos_directory_set` восстанавливает ранее полученный контекст на том же томе. Для строкового пути используется mxos_getcwd. `mxos_directory_list` имеет контракт file_list, но включает каталоги и записи . / ... Полный ABI — [DOS](../source/dos/README.md#каталоги).

Буфер пути принадлежит программе; удобно объявить `static MXOS_PATH path = { "/Almaz/MXOS" };`. После успешного `mxos_chdir(path.bytes)` можно открывать файлы этого каталога через `mxos_fopen(&file, "ALMAZ2MX.EXE", "rb")`. Сам fopen пока не разбирает вложенный путь. mkdir/rmdir и расширение заполненного каталога относятся к следующему этапу.

`include/mxos_file.h` и `src/mxos_file.c` — основа файлового backend для собственной stdlib. `MXOS_FILE` содержит только 64 байта двоичного ABI; выравнивание структур компилятора не влияет на раскладку. Требуются 8-битный char, 16-битные unsigned short/указатели и 32-битный long. Объект выделяет вызывающий; адаптер не использует malloc и скрытую таблицу открытых файлов DOS.

В начале программы вызвать `mxos_dos_init()` и проверить нулевой код DOS. Программа/heap должны оставаться ниже memtop, в штатной системе — не выше 8BFFh; стек предоставляет MEM. Служебный стек MAIN занимает 256 байт, из них 64 байта оставлены под запас транспорта; крупные объекты и буферы удобно размещать в статической памяти или heap. Затем доступны open/read/write/seek/flush/close, fread/fwrite, fgetc/fputc, ftell, feof/ferror/clearerr. Полный контракт ядра и раскладка FILE_HANDLE приведены в [описании DOS](../source/dos/README.md#открытые-файлы).

```c
#include "mxos_file.h"

MXOS_FILE file;
char buffer[128];

/* После успешного mxos_dos_init(): */
if (mxos_fopen(&file, "B:EDITOR.CFG", "w+b") == 0) {
    mxos_fwrite("OPTION=1\r\n", 1, 10, &file);
    mxos_fseek(&file, 0, MXOS_SEEK_SET);
    mxos_fread(buffer, 1, sizeof(buffer), &file);
    if (mxos_fclose(&file) != 0) {
        /* Проверить mxos_ferror(&file), повторить flush/close после устранения ошибки. */
    }
}
```

Режимы: r, w, a, r+, w+, a+, необязательный b в любом порядке с +. Имена — точные 8.3 в KOI-8, необязательный префикс A:–H:, без префикса используется текущий диск DOS. Каталог выбирается через mxos_chdir; вложенный путь в самом fopen пока не разбирается. Преобразования CR/LF нет. CREATE/TRUNCATE выполняются при открытии; READ/WRITE передают байты, fread/fwrite возвращают количество целых элементов. Произведение size×count должно помещаться в 16 бит; непрерывный буфер должен помещаться в доступной памяти.

Ошибки числовые: `mxos_ferror` возвращает код DOS, EOF хранится отдельно. Указатель после частичного чтения/записи продвигается на фактически переданные байты. `mxos_ftell` возвращает unsigned 32-битную позицию; при подключении к stdlib с signed long её нужно проверять на представимость. FOPEN здесь принимает адрес готового объекта и возвращает 0/−1; собственная stdlib может выдавать FILE* из своего пула и устанавливать errno. Текстов ошибок в ядре нет.

Для другого компилятора требуются `mxos_bios_call` и два файловых переходника. `mxos_file_call(MXOS_FILE*)` передаёт указатель в HL, байт bytes[63] в A и выполняет CALL mx_callRegs / DW MXOS_DOS_FILEHANDLE. `mxos_current_drive()` использует тот же вход с MXOS_DOS_FILE_GET_SET_DRIVE и DE=0. Возвращаемое A преобразуется в unsigned char согласно соглашению компилятора. В `src/mxos_file_z88dk.asm` есть готовый мост sccz80 `__z88dk_fastcall` из команд 8080.

Проверка `python scripts/tests/check-file-stdlib.py --z88dk <каталог z88dk>` компилирует backend и `tests/file-stdio.c` с `-clib=8080`, затем вызывает `scripts/emu80/check-unified-sdk.py` для проверки с банковым DOS. Режим `--build-only` ограничивается сборкой. Профиль +cpm выбирает 8080-компилятор и арифметическую библиотеку, а собственный CRT работает без BDOS CP/M. Heap и runtime проверяются в `scripts/tests/check-near-heap.py` и `scripts/emu80/check-memory-lifecycle.py`.

`mxos_getcwd` заполняет MAX_PATH-буфер абсолютным путём с `\`; `mxos_chdir` допускает префикс диска и оба разделителя. MXOS_COPY_REQUEST теперь занимает 86 байт: слова по смещениям 80 и 82 — каталоги источника и назначения (0 — корень).

`mxos_file_getattr`/`mxos_file_setattr` используют существующий ABI C857h для файлов и каталогов: изменяются R/H/S/A, DIR сохраняется. `mxos_file_move` принимает тот же запрос, что COPY; внутри одного тома переносит запись без копирования данных. Обёртки входят в вызывающую C-программу, а не в DOS.

FILE_COPY_REQUEST.onExists (слово по смещению 84) — необязательный адрес обработчика в соглашении 8080: A=FAR-банк DOS, HL=FILE_DESCRIPTOR назначения; перед BIOS-вызовами дескриптор копируется на локальный стек через memcpy_far (готовый переходник source/common/copyConfirmLocal.inc). Ответ A=0 пропуск / A=1 замена / A=2 Yes to all / A=3 No to all, CF=0; CF=1 отказ. Значение 0 сохраняет неинтерактивный отказ EXISTS. Это адрес машинной процедуры, а не обычный указатель на C-функцию; C-клиент обнуляет поле либо предоставляет ASM-переходник.

## FAR-копирование MEM

`mxos_memcpy_far(MXOS_FAR_COPY*)` вызывает F80Fh из MAIN или исполняемого банка. Пакет из 8 байт содержит FAR-источник, FAR-приёмник и длину. Код 0 означает MAIN, 1…16 — банки ДОЗУ. Функция возвращает слово AF с CF в младшем байте и кодом ошибки в старшем. Нулевой размер возвращает успех. Исключающая граница диапазона — FE00h. `mxos_memcpy_far` и `mxos_memmove_far` принимают один и тот же пакет и поддерживают перекрытие в одной странице, включая DATA. Вызывающий обеспечивает владение диапазонами и сохранность кода, стека и системных данных.

## Печать из банка и main

`mxos_printString_bank(const char *text)` печатает локальную ASCIIZ. Из банка порции до 32 байт печатаются прямо из окна MEM, а длина вычисляется при наполнении до первого NUL. Из MAIN печать локальная. `mxos_printString_main(mxos_u16 address)` явно задаёт адрес ASCIIZ в MAIN и передаёт в BIOS только регистры. Строка должна оставаться действительной до возврата. ASM-эквиваленты — `MXOS_CALL_REGS MXOS_BIOS_PRINT_STRING_BANK` и `MXOS_CALL_REGS MXOS_BIOS_PRINT_STRING_MAIN`, адрес передаётся в HL. Прежние PRINT_STRING и mxos_puts_local сохраняются.

Счётные `MXOS_BIOS_PRINT_STRING_LIM` и `MXOS_BIOS_PRINT_STRING_LIM_MAIN` принимают адрес в HL и число байтов в BC, включая коды 00h. Первый вход читает из страницы вызывающей программы, второй — из MAIN. Чтобы передать строку в собственный буфер MAIN перед печатью, используйте `mxos_memcpy_far`.

## Аллокатор и операции памяти

Закреплённый регистровый контракт, ошибки, границы и правила владения: [публичный ABI MEM](../source/mem/api.md). Подключение mxos_far.c добавляет malloc/free/realloc FAR, регистрацию main-арены и GET/PUT; эти обёртки входят в программу, не в ядро. Все номера MEM_OP и ошибки продублированы в mxos.h и сверяются с ASM. Размер MXOS_FAR_ADDRESS — 3 байта, MXOS_FAR_COPY — 8 байт. Вызовы возвращают AF; проверять MXOS_CF до использования результата.

Перед FAR-выделением в main нужно передать собственный диапазон mxos_main_arena; локальная C-куча не должна использовать эти байты. Уже размещённый MAIN-буфер вне статического диапазона образа регистрируется через `mxos_main_register(start, bytes)`: точные границы без обнуления, перемещения или выгрузки других модулей. Пересечение возвращает ACTIVE. Освобождение — `mxos_free_far` с `{bank=0, offset=start}` либо штатное завершение владельца. Загрузчик учитывает такие буферы вместе с остальными блоками; MAIN-DLL не может затереть живой буфер приложения. Лимит FAR-реестра — 32 блока, один блок не пересекает банк. FILE_EXEC очищает временные выделения MAIN/BANK при RET, а зарегистрированные резиденты сохраняются при Reset. Прямые вызовы вне загрузчика требуют явного управления сроком жизни. mxos_fill_far, mxos_calloc_far и mxos_memory_query дают заполнение, выделение с обнулением и статистику. RAMDISK.COM -P 4 резервирует и подготавливает фиксированные банки, затем передаёт их DOS через MEMORY/RAMDISK COMMIT; после закрепления размер не меняется.

## Загружаемые модули

mxos_module_load(path, MXOS_MODULE_MAIN/MXOS_MODULE_BANK/MXOS_MODULE_DOS, &handle), mxos_module_call(handle, &regs) и mxos_module_unload(handle) находятся в дополнительном src/mxos_module.c. Это обёртки трёх штатных DOS-операций 0226h…0228h; код входит в вызывающую программу. MXOS_MODULE_REGS содержит ровно 8 байт HL/DE/BC/AF. Не подменять его прежним 10-байтным MXOS_REGS с полем entry.

module_call возвращает AF статуса API; AF самого модуля, в том числе CF, находится в regs.af. NEAR-параметры регистров не преобразуются; FAR-адреса общих объектов передаются по соглашению модуля. Статический диапазон MAIN-DLL резервирует загрузчик по заголовку; ARENA используется для динамической памяти. Ошибки HANDLE/ACTIVE обозначают устаревший handle и активный модуль. Выгрузка освобождает образ, дочерние модули и FAR-блоки текущего модуля; MAIN-приложения FILE_EXEC имеют отдельные временные теги; прямые вызовы вне загрузчика сохраняют контекст банка. Полный контракт и ASM-пример: [api.md](../source/mem/api.md). FILE_EXEC запускает банковое приложение через тот же механизм; RUN делегирует нативные контейнеры DOS.


MXOS_DOS_FILE_EXEC_NATIVE (0229h) — явный путь с аргументами в локальном HL, без PATH/CLI/ассоциаций. Доступен через обычный MXOS_CALL_REGS/mxos_call_packet; AF возвращает статус загрузки/вызова. MXOS_IMAGE_FLAG_MAIN=04h, DRIVER=01h, BANK=02h описывают заголовок контейнера; это взаимоисключающие признаки. Flags=0 оставляет совместимость неподтверждённой. Для ASM задать IMAGE_FLAGS, для своего C-упаковщика передать flags при формировании контейнера. RUN запускает подтверждённый контейнер без меню через FILE_EXEC_NATIVE; неизвестный COM/EXE предлагает выбор режима.


Обычный MXOS_DOS_FILE_EXEC сначала применяет нативные MAIN/DRIVER/BANK найденного COM/EXE и только для flags=0 обращается к CLI.EXT. FILE_EXEC_NATIVE остаётся явным путём без поиска и ассоциаций.

## NEAR stdlib и старт C-программы

Добавьте src/mxos_heap.c и src/mxos_stdlib.c. Явный mxos_heap_init(&mxos_default_heap, begin, bytes) задаёт принадлежащий программе диапазон. Локальная куча работает в любой исполняемой странице, не переключает банки и не использует FAR-реестр. Отдельные MXOS_HEAP подходят для внутренних куч ядра. sizeof(void*) остаётся 2, FAR-адрес передаётся явно. Не превращайте NEAR NULL в {home_page,0}: нулевой FAR всегда {0,0}.

Для самостоятельного приложения sccz80 используйте -crt0=sdk/runtime/crt0, -clib=8080, -compiler=sccz80, -zorg=256. CRT обнуляет BSS и автоматически выделяет остаток своей страницы под NEAR-кучу; символы mxos_args и mxos_home_page объявлены в mxos_runtime.h. Он рассчитан на main(void), обычный RET и не инициализирует stdio/C++/atexit. Для DLL и резидентного повторного входа используйте собственный CRT и явную арену. Пример воспроизводимой сборки MAIN/BANK — scripts/tests/build-memory-runtime.py, пример stdlib — sdk/tests/heap.c.

### Консольный printf

При сборке sccz80 с этим CRT добавьте `sdk/src/mxos_printf.asm` к исходникам приложения. В C используется обычный заголовок z88dk. Штатная таблица classic 8080 поддерживает, в частности, `%d`, `%u`, `%x`, `%s`, `%c` и `%%`, в том числе в формате, полученном во время исполнения. Для вещественных чисел и `%i` в этой таблице нет обработчиков. Форматтер проходит по аргументам один раз, а перед возвратом выводит остаток. Результат — число выданных байтов или −1 при ошибке вывода. Байты управляющих кодов и результат `%c` со значением 0 входят в длину. Вывод идёт на экран, перенаправление через CLI и файловый `fprintf` в этот модуль не входят.

```c
#include <stdio.h>

int main(void)
{
    return printf("%s %u\r\n", "MXOS", 2u) < 0;
}
```

По умолчанию форматтер заполняет 256-байтный буфер в BSS текущей страницы. В MAIN каждая готовая порция идёт прямо в `bios_printStringLim`. В EXEC `PRINT_STRING_LIM` передаёт её через окно MEM порциями до 32 байт.

Банковая программа может привязать к `printf` собственный локальный буфер и принадлежащий ей буфер в MAIN той же ёмкости. Каждая готовая порция, включая короткий остаток, копируется через `mxos_memcpy_far` и выводится одним `PRINT_STRING_LIM_MAIN`. Аргументы `mxos_printf_buffer` — локальный указатель, 16-битный адрес в MAIN и ёмкость обоих буферов в байтах. Оба диапазона должны оставаться доступными до снятия привязки. Перед копированием `printf` проверяет весь диапазон MAIN. Начало должно быть не ниже 0100h, а исключающий конец — не выше 8C00h. Вызов `mxos_printf_buffer(0, 0, 0)` возвращает штатный режим. Если программа уже зарегистрировала свободную область MAIN через `mxos_main_arena`, выделение и освобождение выглядят так.

```c
#include <stdio.h>
#include "mxos.h"
#include "mxos_runtime.h"

static char local[1024];

int print_report(const char *text)
{
    MXOS_FAR_ADDRESS main_buffer;
    int result;

    if (mxos_malloc_far(MXOS_ALLOC_MAIN, sizeof local, &main_buffer) & MXOS_CF)
        return printf("%s", text);
    mxos_printf_buffer(local, main_buffer.offset, sizeof local);
    result = printf("%s", text);
    mxos_printf_buffer(0, 0, 0);
    mxos_free_far(&main_buffer);
    return result;
}
```

Консольные обёртки putch/puts/getch/getkey/keyscan, курсор и uppercase работают в MAIN и BANK. Низкоуровневый mxos_bios_call и исторические Cxxx-обёртки предназначены для MAIN. Для файлов в BANK используйте mxos_file.h и mxos_call_packet. Служба mx_memInfo возвращает версию 0104h и бит MXOS_MEM_CAP_BIOS_REGISTERS (64) для выделенных регистровых входов.

## Сохраняемые сервисы

mxos_resident_retain(key) отделяет текущий BANK-модуль или DOS-модуль резидентного слота от вызвавшей программы. Ключ ненулевой и уникальный. mxos_resident_find/next позволяют найти и перечислить сохранённые handle. mxos_resident_restore вызывает вход с A=1; mxos_resident_close вызывает A=2 и выгружает только после успешного callback; mxos_resident_kill удаляет без callback. Код/данные и дочерние ресурсы резидента сохраняются при тёплом сбросе, CPU-контекст не сохраняется. После RETAIN разрешены отслеживаемые MAIN-ресурсы: неактивная дочерняя MAIN-DLL может быть выгружена при запуске пересекающейся программы, поэтому её handle проверяют при RESTORE. MAIN-буфер самого EXEC-резидента остаётся занятым до FREE или выгрузки владельца и может препятствовать запуску; восстанавливаемые буферы лучше закреплять за MAIN-DLL. RETAIN нужно вызвать до загрузки дочерних модулей. Фиксированный пул B: принадлежит самой DOS, а не резиденту; модульного handle у RAM-диска нет.

Запрос FAR-памяти при нехватке банков может вытеснить свободный от исполнения резидентный модуль. По умолчанию приоритет 100, у банковых EDIT и NC — 150 и 200, у пула RAM-диска — 254. Приоритет 255 защищает резидента. `mxos_resident_policy` задаёт приоритет и флаг автовосстановления. В ядре есть два слота для абсолютных путей автовосстановления, по 32 байта с терминатором в каждом. `mxos_resident_veto` регистрирует код, две последовательные строки ASCIIZ с именем 8.3 и объяснением и необязательный адрес байта, при ненулевом значении которого отказ действует. При E8h `mxos_malloc_far_ex` возвращает код и FAR-адреса обеих строк. Их нужно прочитать до следующего запроса с вытеснением.

## DLL в банке DOS

`mxos_module_load(path, MXOS_MODULE_DOS, &handle)` загружает DRIVER-DLL в арену 9D00h–C9D7h. Для v2 адрес задан в заголовке, для v3 DOS выбирает выровненный интервал при загрузке. Активный BAT при пересечении освобождает свой кэш и сохраняет файловую позицию. Реестр хранит точный интервал каждого образа: непересекающиеся DLL и установщики могут сосуществовать; пересечение с активным кодом даёт ACTIVE до записи. Неактивный кэш ENUM/FILEOPS при реальном пересечении можно вытеснить. Вызов и выгрузка — через mxos_module_call/unload; пакет MXOS_MODULE_REGS находится у контроллера, NEAR-указатели автоматически не переводятся. Стек общий с DOS. RETAIN допускается во всей арене. Обычные модули освобождаются с владельцем. Полный контракт — [source/mem/api.md](../source/mem/api.md).

```c
mxos_u16 handle, af, unload_af;
MXOS_MODULE_REGS regs = {0, 0, 0, 0}; /* HL, DE, BC, AF модуля */
af = mxos_module_load("B:\\DOSMOD.DLL", MXOS_MODULE_DOS, &handle);
if (!(af & MXOS_CF)) {
    af = mxos_module_call(handle, &regs);
    /* af — статус API, regs.af — результат самого модуля. */
    unload_af = mxos_module_unload(handle); /* Также после ошибки вызова. */
}
```

Значение `MXOS_MODULE_DOS=2` выбирает размещение и не является FAR-кодом банка: DOS имеет FAR-код 1. Код DLL должен обращаться к BIOS/DOS через MXOS_CALL_REGS; адреса BIOS C000h/C800h в банке DOS обозначают память арены. Отдельной NEAR-кучи загрузчик DOS-DLL не создаёт. Диск для измерений следует выбирать после загрузки DLL, поскольку файловый загрузчик может изменить выбранный диск.

## Владение RAM-диском

`mxos_ramdisk_status(&pages, &state, &fresh)` вызывает MEMORY/RAMDISK (A=14, C=0): pages — число банков пула, state — 0 не закреплён, 1 владелец DOS, 2 исторический модульный владелец. fresh получает D: 1 — bootstrap обнаружил потерю хвоста MEM первого банка B:, 0 — хвост был сохранён либо подготовка уже завершена. `mxos_ramdisk_commit()` (C=1) передаёт подготовленный пул DOS; разрешён только из DRIVER-инициализатора, повторно проверяет геометрию B: и не форматирует том. При ошибке владелец не меняется. Штатный RAMDISK.COM выполняет передачу после подготовки тома и завершается без резидентного кода. Изменение размера закреплённого пула пока запрещено. Обёртки находятся в src/mxos_far.c.

Четырёхбайтные объекты передаются через обычный FAR COPY. Курсор FAT находится внутри FILE_HANDLE и ведётся ядром. Отдельных системных входов и C-обёрток GET/PUT32 нет.

Владение ВИ53 оформляется через MXOS_DOS_TIMER в MAIN, DOS и EXEC. В C вызовите `mxos_timer_request(MXOS_TIMER_RAW)` и проверьте CF перед настройкой измерителя. `mxos_pit_get_port(&base)` возвращает тип доступа к каналам (0 — MMIO, 1 — IN/OUT). После настройки `mxos_pit_read()` вызывает локальный вход IO.SYS и возвращает убывающий U16. Завершайте сеанс через `MXOS_TIMER_RELEASE`. Банковый ввод использует TIMER_CLOCK через mxos_bank_key_begin/end. [Операции и интервалы](../source/mem/api.md#владение-ви53)

Умножение, деление и деление на два больше не предоставляются BIOS/MXOS_CALL_REGS; C использует локальную арифметику компилятора, ASM — sdk/asm/lib/math.inc с выбором MATH_SUB/MATH_DIV2/MATH_MUL/MATH_DIV. Для выбора раскладки шрифта доступна регистровая служба MXOS_BIOS_SET_FONT_ENCODING (A=0 KOI8, иначе KOI7); рендер не следит за прямыми записями режима.

## Перечисление с масками

`mxos_enumerate(op, &request)` вызывает MXOS_DOS_ENUMERATE. Пакет MXOS_ENUM_REQUEST содержит handle, NEAR-адрес пути (буфер 128 байт), NEAR-адрес массива MXOS_ENUM_ENTRY, capacity/count, flags/state. OPEN=0, NEXT=1, CLOSE=2; флаги RECURSIVE=1 и CHECK_CANCEL=2. Запись состоит из 32 байт FAT-дескриптора и полного пути на 128 байт. Всегда закрывайте курсор, включая конец и ошибку. count=0/state=0 означает продолжение поиска, state=1 — конец. Один активный курсор, вместимость пачки 1..255, глубина до 32 каталогов. Полный контракт — [ENUM.DLL](../source/enumerate/README.md). Указатели принадлежат банку вызывающего; перечислитель можно использовать вместе с пошаговым FILEOPS без командного парсера.


`mxos_fileops(op, &job)` поддерживает COPY/MOVE/DELETE и управление BEGIN/STEP/ANSWER/CANCEL/CLOSE/SKIP_PREPARE. MXOS_FILEOPS_JOB занимает 112 байт; `phase`, `known`, `total`, `required` описывают подготовку. Необязательный `path` — отдельный 128-байтный NEAR-буфер клиента, указанный до BEGIN. Он не должен пересекать объект задания. Для работы при уже открытом курсоре ENUM задайте NO_PREPARE. Подробности отмены, подсчёта места и частичного результата — [FILEOPS](../source/fileops/README.md).

## Единый файловый ввод-вывод

Все операции данных проходят через MXOS_DOS_FILEHANDLE. mxos_fopen принимает полный путь и использует OPEN_PATH; fread/fwrite/fseek/fflush/fclose используют тот же объект. mxos_file_read_all и mxos_file_write_all — библиотечные обёртки над ними с локальным MXOS_PATH_IO; отдельных LOAD_PATH/SAVE_PATH системных вызовов нет. Метаданные и каталоги вызываются через MXCALL, старые BIOS_ABI_FILE_* удалены. Для ASM доступны sdk/asm/lib/file-io.inc и необязательный file-image.inc для инструментальной загрузки родного контейнера.

Нативный контейнер v2 имеет 32-байтный MXOS_IMAGE_HEADER, общий для COM/EXE/DLL/FNT. BSS только резервируется загрузчиком; C CRT обнуляет его сам. Политики и точная раскладка описаны в [MEM API](../source/mem/api.md#контейнер-v2-и-политики-памяти). Утилита [EXE.COM](../source/exe/README.md) позволяет менять формат и метаданные на самом компьютере.

Релоцируемая DLL использует 40-байтный MXOS_RELOC_IMAGE_HEADER версии 3. Обычные mxos_module_load/call/unload работают с обоими форматами. В v3 load и entry отсчитываются от базы полного интервала. DOS применяет внутренние поправки WORD16 либо HIGH8 при холодной загрузке и удерживает базу до выгрузки. Указатель на данные модуля действует в его странице и только при живом handle. Перемещаемая MAIN DLL работает на исходном MX. [Формат таблицы и пример ASM](../source/mem/api.md#релоцируемый-образ-v3)

C CRT в MAIN резервирует у DOS один блок под NEAR-кучу; отдельные malloc/free/realloc остаются локальными и не вызывают DOS. Это предотвращает размещение DLL поверх живой C-кучи. В EXEC вся память банка уже принадлежит приложению; верх кучи EF80h оставляет отдельный служебный стек. Для конкурентных MAIN-DLL приложение задаёт собственный startup/размер кучи.


Для прямой генерации команд подключите mxos_queue.h и sdk/src/mxos_queue.c. mxos_command_open(&q, buffer, 256, 32) задаёт ёмкость и резерв; программа пишет запись прямо в q.next и вызывает mxos_command_commit(&q, end). Для известной крупной команды сначала вызывается mxos_command_reserve. mxos_queue_flush — явный барьер, mxos_command_close завершает сеанс. Пример — sdk/tests/command-queue.c. Автосброс выполняется при недостатке резерва и перед обычным API/COPY. Детальный формат и ограничения — [очередь MEM 1.3](../source/mem/api.md#очередь-команд-mem-13). Очередь и её буфер принадлежат программе. Для смены адресата вызовите mxos_command_select(&q, target, handle). Для серии вызовов DLL передайте контроллер в mxos_module_scope(handle, controller). Внутри контроллера mxos_route_call(handle, &input, &result) возвращает регистры одиночного вызова. Выбор другой цели отправляет прежнюю пачку. После барьера проверьте q.error.
