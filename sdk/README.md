# SDK MXOS для C

Новый `mxos_call(MXOS_CALL*)` обращается к общему входу F800h. Структура содержит пять слов: operation, HL, DE, BC, AF; operation=(группа<<8)|номер. Она предназначена для родных групп BIOS/DOS, использующих регистровый пакет. Имена `MX_BIOS_*`/`MX_DOS_*` генерируются из `source/bios/syscalls.json` в `include/mxos_syscall_ids.h`. Файловый мост `mxos_file_call` уже использует регистровый адаптер F806h с номером `MX_DOS_FILEHANDLE`. Остальные старые именованные входы пока доступны параллельно для поэтапной миграции. C-обёртка возвращает AF как 16-битное слово, включая CF/код A при отказе диспетчера, когда сам пакет не изменяется. Группа BDOS пока зарезервирована и возвращает UNSUPPORTED; работа CP/M предполагает отдельное сменное ядро.

Общее окно RAM-диска выбирается через `mxos_bios_call` с `entry=MXOS_BIOS_RAMD_DRIVER` (C86Fh), старшим байтом BC=`MXOS_RAMD_DRIVER_*`. RESTORE=0 возвращает обычный шаблон, BYTE=1 выбирает сервисный побайтовый, REGISTER=2 регистрирует резидентные 32 байта по HL без смены окна, BLOCK=3 временно выбирает встроенный R3, USER=4 применяет зарегистрированный шаблон. До регистрации обычным служит R3. Перед файловыми/секторными операциями после BYTE/BLOCK требуется RESTORE. Регистры и флаги селектор сохраняет; это выбор окна FFC0h, а не регистрация физического драйвера диска. В USER/RESTORE раскладка окна принадлежит зарегистрированному драйверу; входы чтения/записи по FFC0h/FFD0h не гарантируются. Для секторного I/O используйте C863h, для прямого сервисного доступа явно выбирайте BYTE или BLOCK.

`include/mxos.h` и `src/mxos.c` открывают уже реализованные службы BIOS/DOS. Горячие функции sccz80 имеют короткие переходники в `src/mxos_z88dk.asm`: например, putch занимает четыре байта и передаёт управление BIOS без упаковки регистров. Для остальных вызовов есть общий мост `mxos_bios_call(MXOS_REGS*)`: пять 16-битных слов entry/AF/BC/DE/HL, sizeof=10; после вызова в них находятся выходные регистры и флаги. Адреса проверяются `scripts/tests/check-sdk-abi.py` по собранному mxos.inc.

| Группа | Обёртки |
|---|---|
| Память | memcpy/memmove с перекрытием, контрольная сумма Monitor-2, get/set memtop, освобождение модуля |
| Консоль | getch/getkey/keyscan, putch, puts без добавления перевода строки, readline с нулевым терминатором, очистка, координаты курсора, DEC/HEX |
| Строки | upper для KOI, сравнение N байт с учётом регистра или без него |
| Таймер | Инициализация и чтение штатного измерителя ВИ53 |
| Диски | Выбор диска, DISK_INFO и физическая ёмкость, логический сектор, flush и числовая ошибка |
| Файлы | Список FILE_INFO, stat, загрузка/сохранение целиком, удаление, переименование и копирование с явным запросом/буфером |
| Графика | Список объектов, инверсия и перенос прямоугольника через BIOS |

Префикс всех функций таблицы — `mxos_`; точные прототипы находятся в заголовке. FILE_DESCRIPTOR/FILE_INFO/DISK_INFO/FILE_COPY_REQUEST представлены массивами 32/16/48/86 байта с фиксированными смещениями из mxos.inc. Буфер списка должен иметь capacity×16+1 байт для завершающего FFh. Полная загрузка файла требует заранее проверенного размера и достаточного буфера; для потокового доступа используется интерфейс ниже.

Консольные getch/putch/puts/readline обращаются непосредственно к BIOS. Стандартные stdin/stdout/stderr будут реализованы выше SDK, вместе с CLI, наследованием потоков и перенаправлением. Файловый backend ниже предоставляет операции над конкретным открытым файлом; глобальных стандартных потоков в нём нет. Будущий CLI сможет назначать stdout файлу для команды `DISKBEN.EXE -H > B:RESULT-H.TXT`; сейчас такого синтаксиса и режима DISKBEN ещё нет.

## Файловый backend

Первое API каталогов: `MXOS_MAX_PATH=128`, `MXOS_PATH` содержит массив `bytes[128]`. `mxos_chdir(path.bytes)` принимает весь буфер с завершающим 0, с необязательным префиксом диска; длина строки до 127 байт. Диск выбирается через `mxos_drive_select`. Поддерживаются абсолютные/относительные пути, `/`, `\`, . и ..; ошибка не меняет текущий каталог. `mxos_directory_get` возвращает компактный контекст — кластер, `mxos_directory_set` восстанавливает ранее полученный контекст на том же томе. Для строкового пути используется mxos_getcwd. `mxos_directory_list` имеет контракт file_list, но включает каталоги и записи . / ... Полный ABI — [DOS](../source/dos/README.md#каталоги-первый-этап).

Буфер пути принадлежит программе; удобно объявить `static MXOS_PATH path = { "/Almaz/MXOS" };`. После успешного `mxos_chdir(path.bytes)` можно открывать файлы этого каталога через `mxos_fopen(&file, "ALMAZ2MX.EXE", "rb")`. Сам fopen пока не разбирает вложенный путь. mkdir/rmdir и расширение заполненного каталога относятся к следующему этапу.

`include/mxos_file.h` и `src/mxos_file.c` — основа файлового backend для собственной stdlib. `MXOS_FILE` содержит только 64 байта двоичного ABI; выравнивание структур компилятора не влияет на раскладку. Требуются 8-битный char, 16-битные unsigned short/указатели и 32-битный long. Объект выделяет вызывающий; адаптер не использует malloc и скрытую таблицу открытых файлов DOS.

В начале программы вызвать `mxos_dos_init()` и проверить нулевой код DOS. Программа/heap должны оставаться ниже memtop, в штатной системе — не выше 8BFFh; стек наследуется от DOS. Системный стек занимает 479 байт; крупные объекты и буферы удобно размещать в статической памяти или heap. Затем доступны open/read/write/seek/flush/close, fread/fwrite, fgetc/fputc, ftell, feof/ferror/clearerr. Полный контракт ядра и раскладка FILE_HANDLE приведены в [описании DOS](../source/dos/README.md#открытые-файлы).

```c
#include "mxos_file.h"

MXOS_FILE file;
char buffer[128];

/* После успешного mxos_dos_init(): */
if (mxos_fopen(&file, "B:EDITOR.CFG", "w+b") == 0) {
    mxos_fwrite("OPTION=1\r\n", 1, 10, &file);
    mxos_fseek(&file, 0, MXOS_SEEK_SET);
    mxos_fread(buffer, 1, sizeof(buffer), &file);
    if (mxos_fclose(&file) != 0) {
        /* Проверить mxos_ferror(&file), повторить flush/close после устранения ошибки. */
    }
}
```

Режимы: r, w, a, r+, w+, a+, необязательный b в любом порядке с +. Имена — точные 8.3 в KOI-8, необязательный префикс A:–H:, без префикса используется текущий диск DOS. Каталог выбирается через mxos_chdir; вложенный путь в самом fopen пока не разбирается. Преобразования CR/LF нет. CREATE/TRUNCATE выполняются при открытии; READ/WRITE передают байты, fread/fwrite возвращают количество целых элементов. Произведение size×count должно помещаться в 16 бит; непрерывный буфер должен помещаться в доступной памяти.

Ошибки числовые: `mxos_ferror` возвращает код DOS, EOF хранится отдельно. Указатель после частичного чтения/записи продвигается на фактически переданные байты. `mxos_ftell` возвращает unsigned 32-битную позицию; при подключении к stdlib с signed long её нужно проверять на представимость. FOPEN здесь принимает адрес готового объекта и возвращает 0/−1; собственная stdlib может выдавать FILE* из своего пула и устанавливать errno. Текстов ошибок в ядре нет.

Для другого компилятора реализовать `mxos_bios_call` и три файловых переходника: `mxos_file_call(MXOS_FILE*)` передаёт указатель в HL, байт bytes[63] в A и выполняет CALL F806h / DW MX_DOS_FILEHANDLE; `mxos_dos_init()` вызывает C8D8h; `mxos_current_drive()` вызывает C842h с E=0. Возвращаемое A преобразуется в unsigned char согласно соглашению компилятора. В `src/mxos_file_z88dk.asm` есть готовый мост sccz80 `__z88dk_fastcall`, состоящий только из команд 8080.

Проверка `python scripts/tests/check-file-stdlib.py --z88dk <каталог z88dk>` компилирует backend и `tests/file-stdio.c` с `-clib=8080`, затем запускает машинный код с настоящим BIOS/DOS и моделью блочного драйвера. Проверяются память, флаги регистрового моста, клавиатурные обёртки, вывод, курсор, строки, memtop, файловые службы и файловый backend. Профиль +cpm используется только для выбора 8080-компилятора и арифметической библиотеки; собственный CRT не вызывает BDOS CP/M. Это проверка CPU, не реального оборудования.

`mxos_getcwd` заполняет MAX_PATH-буфер абсолютным путём с `\`; `mxos_chdir` допускает префикс диска и оба разделителя. MXOS_COPY_REQUEST теперь занимает 86 байт: слова по смещениям 80 и 82 — каталоги источника и назначения (0 — корень).

`mxos_file_getattr`/`mxos_file_setattr` используют существующий ABI C857h для файлов и каталогов: изменяются R/H/S/A, DIR сохраняется. `mxos_file_move` принимает тот же запрос, что COPY; внутри одного тома переносит запись без копирования данных. Обёртки входят в вызывающую C-программу, а не в DOS.

FILE_COPY_REQUEST.onExists (слово по смещению 84) — необязательный адрес обработчика в соглашении 8080: HL=запрос, A=0 пропуск / A=1 замена / A=2 Yes to all / A=3 No to all, CF=0; CF=1 отказ. Значение 0 сохраняет неинтерактивный отказ EXISTS. Это адрес машинной процедуры, а не обычный указатель на C-функцию; C-клиент обнуляет поле либо предоставляет ASM-переходник.
