# MXCALL и пакетная передача, 17.11.2026

Измерения в тактах CPU видимого Emu80, звук отключён. При частоте 2 МГц 2000 тактов соответствуют 1 мс. Для скалярного теста использована операция BIOS UPPERCASE с проверкой результата и восстановленного контекста. В измерение входят вход в API, маршрут до BIOS, возврат и завершающий JMP стенда. Исходный профиль окна COMMAND уже установлен, кроме последней строки.

| Версия скалярного MXOS_CALL | MAIN | Банк DOS | Банк EXEC |
|---|---:|---:|---:|
| До оптимизаций | 1129 | 4976 | 4976 |
| После снятия проверок горячего маршрута | 1064 | 4634 | 4634 |
| Прямой регистровый возврат и сокращённый диспетчер | 637 | 2959 | 2959 |
| Итоговая MEM 1.3 с поддержкой очереди, очередь отключена | 664 | 3092 | 3092 |
| Та же версия, первый вызов после COPY | 664 | 4309 | 4309 |

Целевой скалярный вызов из EXEC занимает 1,546 мс вместо 2,488 мс. Если перед ним межбанковый обмен занял аппаратное окно, восстановление COMMAND добавляет 1217 тактов. Измерения по этапам хранятся в [исходном](current.json) и [итоговом](routes.json) протоколах, а также в [прогоне после COPY](routes-copy.json).

## BIOS из EXEC

Один и тот же набор установок курсора выполняется отдельными синхронными вызовами и через локальную очередь. Время очереди включает генерацию записей, commit и завершающую отправку. Инициализация очереди выполняется до замера.

## MAIN-DLL из EXEC

Уже загруженная тестовая DLL выполняет INC HL. Серия из 16 обычных MODULE_CALL занимает 320629 тактов. Одна MODULE_SCOPE и 16 прямых вызовов mx_routeCall занимают 56339 тактов с учётом входа и выхода из области. Это 160,315 и 28,170 мс, ускорение 5,69×. Дисковая загрузка DLL и отрисовка приложения в эти числа не входят. [Результат серии](queue/route.json)

## Воспроизведение

Использованы scripts/emu80/benchmark-mxcall.py и scripts/emu80/benchmark-command-queue.py. В пакетном стенде проверяются граница 256 байт системного приёмника, точная длина 320 байт при доставке собственной DLL, порядок DOS/DLL/BIOS, барьеры COPY и регистрового запроса, недоступность прямого маршрута после возврата и отказ выгрузить активную DLL. Обратный маршрут MAIN → EXEC → DOS проверяет владение FAR-выделениями и очистку при выгрузке. C-менеджер и вызов привязанной DLL из C проверены в MAIN и EXEC. Файловая проверка на B: выполняет смену диска, остановку на неизвестной команде, удаление тестового файла по встроенному имени 8.3 и повторный отказ для отсутствующего файла. При создании EXEC и при тёплом Reset проверено, что регистрация очереди DOS не попадает в новый контекст и отброшенный обработчик не вызывается. [Результаты пакетного теста](queue/result.json)
