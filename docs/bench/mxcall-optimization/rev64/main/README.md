# Привязка регистрового вызова F806h в MAIN

В изолированной сборке MEM rev63 sysInstall записывает адрес sysRegsEntry в операнд уже существующего CALL bankMxRegsRoute. Оба исходных регистровых маршрута MEM остаются в установочном образе и банковых страницах. В MAIN этот CALL минует повторное чтение bankPage, загрузку MEM_NATIVE_CALL и смещение к регистровому входу. Та же точка BIOS передаёт DOS, включая RAW, к прежнему диспетчеру. Очередь сбрасывает прежний вход F806h.

Добавлено 6 байт BIOS, конец D7FBh, зазор до FONT_ENGINE_BASE равен 5 байтам. Метка CALL не меняет код CLIENT. DOS.sys занимает 29975 байт. Вариант с отдельным быстрым распаковщиком BIOS превысил границу FONT_ENGINE_BASE. Промежуточный вариант с записью целого JP побайтно уменьшал выигрыш на 10 тактов и расходовал на 5 байт больше. Emu80 запущен в видимом окне на отдельном слоте 19781. Измерения проведены на 8080 при 2 МГц, с фиксированным ускорением 32× и выключенным звуком. Зачёт изменения относится только к CALL в MAIN, 73 такта на каждый измеренный F806. F800 и добавочная стоимость одного callback очереди не изменились. [До](before/profile.json) [После](operand/profile.json)

Холодный старт, тёплый аппаратный Reset и программный C800h восстанавливают привязку MAIN после записи исходного операнда. DOS сохраняет исходный CALL. После каждого входа проверены успешные BIOS UPPERCASE и DOS_GET_ERROR, неизвестная группа 0904h с A=DOS_ERR_UNSUPPORTED и CF=1, а также исходный SP после возврата. Стенды холодной загрузки и STD-возврата учитывают только два изменяемых байта CALL в ожидаемом MAIN. Дополнительно прошли CPU MEM 13, CHAR/RAW 16, штатная компоновка BIOS/DOS с 21 фиксированной точкой, автономный BIOS и таблица JMP DOS. [Установка](binding-operand/result.json)

В контрольном A/B один и тот же кандидат загружен дважды. Контроль восстанавливает только исходный операнд CALL в MAIN RAM перед измерением. Во всех 16 строках подтверждена разница 73 такта для F806 и 0 для F800. Хеш системного образа совпадает между контрольным и связанным прогонами. [Контроль](control/profile.json) [Результат A/B](ab.json)

На объединённом образе rev64 SHA-256 9D1B8508D793319EDEB74A8C0CF7B7B80374AD20CC5B4AE398A3C004C979758B прошли очередь команд, реальный вложенный DLL и тёплый Reset. Банковый транспорт прошёл 54 сценария, из них 50 проверок FAR/sector. CPU проверил 13 случаев MEM, 98 CPM32, 16 CHAR/RAW, компоновку и автономный BIOS. Эти прогоны подтверждают интеграцию с изменениями rev64, а не отдельный вклад привязки CALL. [Очередь](final/queue/result.json) [Транспорт](final/transport/result.json) [CPM32](final/cpm32/result.json)

На rev64 холодная загрузка, тёплый Reset и C800h снова восстановили привязку MAIN. Отдельно прошли 23 вызова с номером операции по 80FFh и группой по 8100h. В MAIN, DOS и EXEC SUB с займом и без него, SET/GET курсора с заданным входным AF и UPPERCASE совпали с историческими входами BIOS по регистрам и флагам. DOS_GET_ERROR проверен при нуле и ненулевой ошибке на всех трёх страницах, при занятом DOS из DOS и EXEC. Возврат из DW достигает 8101h с исходным SP и в исходной странице. Сохранены owner/home/depth/serviceSP и защитные байты. [Край DW и восстановление](final/binding/result.json)
