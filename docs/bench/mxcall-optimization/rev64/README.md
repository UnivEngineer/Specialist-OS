# MXOS2 MEM rev64. Регистровый вызов BIOS и DOS

Прямой CALL C875h из MAIN для UPPERCASE на строчной латинской q занимает 73 такта. Полный F806h из EXEC занимает 525 тактов, или 262,5 мкс при 2 МГц. Доплата за вход через MEM из EXEC составляет 452 такта, или 226 мкс. Время измерено от CALL приложения до следующей инструкции, для F806h сразу за DW. Для DOS_GET_ERROR с нулевым кодом прямой CALL dosGetError внутри DOS занимает 45 тактов. F806h в том же банке занимает 333 такта (rev63 508), из EXEC — 501 такт (rev63 583). Вложенный рейс EXEC → DOS → BIOS → DOS → EXEC сократился с 2200 до 2073 тактов. Среди 244 сопоставимых измерений 84 стали быстрее, в 160 время совпало. Регистры и число вызовов очереди совпали во всех 244. Ещё 24 измерения охватывают SET_CURSOR_POS в MAIN, DOS и EXEC. [Сопоставление](comparison.json) · [Изолированный тест входа MAIN](main/README.md)

Инициатор узнаёт один из четырёх номеров BIOS и выставляет SP на пару слов по F00Ch–F01Bh. В MAIN первое слово ведёт к историческому JMP C8xxh. На входе в обработчик SP указывает на второе слово, адрес возврата в MEM. Все четыре допущенные реализации завершаются RET и только читают стек. На обратном пути MEM выбирает исходную страницу, восстанавливает SP и BC и возвращается за DW. Для GET_ERROR переход из DOS идёт сразу в обработчик на стеке инициатора. Из EXEC служба использует отдельное слово возврата в банке DOS.

От первой инструкции в MAIN до тела UPPERCASE теперь проходят ровно 20 тактов на RET и JMP исторической таблицы. В rev63 на том же отрезке проходило 136 тактов, из них 10 на JMP к диспетчеру BIOS. Время самого UPPERCASE на измеренной букве составляет 46 тактов. Поэтапный стенд заканчивает замер после дополнительного JMP на точку останова, поэтому его полный результат на 10 тактов больше непосредственного измерения. [Разбивка rev63](../emu-final/final-command.json) · [Разбивка rev64](stages/rev64-command.json)

## Откуда берутся 593 такта в MAIN

Для UPPERCASE с A=71h публичный макрос выпускает пять байт `CD 06 F8 17 01`. После CALL F806h в потоке лежит DW 0117h. При отключённом обработчике очереди путь MAIN → MAIN делает ноль записей в маппер и передаёт ноль байт через общее окно. Клиент сохраняет AF, BC, DE и HL в восьми байтах стека приложения. Он помещает адрес продолжения за DW на место адреса возврата, передаёт BC=0117h и DE=адрес сохранённых регистров. sysInstall заранее привязал внутренний CALL к sysRegsEntry. У банкового быстрого пути вход в upperCase приходится на такт 421, весь вызов из EXEC занимает 525 тактов. [Трассы](profile/profile.json) · [Прямой CALL](direct-canonical/direct-bios.json)

## Окно и клавиатура

Для остатка 1–31 байт MEM собирает байтовый цикл шестнадцатью PUSH прямо в FFC0h–FFDFh. BC и DE остаются указателями источника и назначения. В 77-байтной передаче EXEC → MAIN два полных 32-байтных блока и 13-байтный остаток в сумме занимают 8060 тактов против 8808. В 94 аппаратно-банковых сценариях Emu80 получен выигрыш 748 тактов у 81 некратной передачи. Нулевые и кратные 32 размеры дали прежнее время. Проверены все длины остатка, невыравненные адреса, конец разрешённого диапазона и ROM → DATA. [Раздельное измерение](window/README.md) · [Объединённый образ](poll/copy-77-final/measured.json)

В выпускаемом NC EXEC для стрелок панели задано 8/1 тиков. В тесте стандартного автоповтора меняются только непосредственные операнды двух MVI A в RAM загруженного NC. Оба плеча выполняют те же инструкции. Записанные настройки и фактические приращения счётчика KEYBANK на каждом шаге равны 12, затем 2 тика по 32,768 мс. NC EXEC с этой настройкой дал медиану между готовыми кадрами 65,620 мс в rev63 и 65,724 мс в rev64. На каждый обработанный шаг уходит на 748 тактов меньше. [Штатный автоповтор](standard-repeat/report.md) · [Замер с настройками выпуска](apps/report.md)

В этой же серии EDIT EXEC дал 65,478 → 65,759 мс между кадрами при тех же фактических 12/2 тиках. В MAIN время между кадрами совпало на обеих ревизиях, 37,042 мс в NC и 31,959 мс в EDIT. Проверены десять шагов NC и восемь шагов EDIT без прокрутки, выход из EDIT в NC и отсутствие F806h в ожидании. [Данные по каждому событию](standard-repeat/summary.json)

Прямой BIOS KEY_SCAN из MAIN занимает 122 такта в простое и 4188 при удержании ↓. Тот же опрос через F806h из EXEC занимает соответственно 2582 и 6648 тактов. Путь через MEM добавляет 2460 тактов в обоих случаях. [Опрос BIOS](poll/README.md)

Собраны OS и SystemEmuWritable. Emu80 работал в видимом окне с фиксированным ускорением 32× без full throttle. MEM.SYS занимает 3069 байт, DOS.SYS — 29975, BIOS.SYS вырос с 6133 до 6139 байт, IO.SYS уменьшился с 827 до 823. ## Постоянный код в банках и 32 байта общих данных

После записи в маппер значение PC указывает на продолжение уже в новой странице. Для обычных вызовов достаточно согласовать адреса продолжений в MAIN, DOS и EXEC. В ревизии 64 регистровые входы четырёх коротких функций BIOS уже используют этот приём. Выделенный вход GET_CURSOR_POS позволяет также убрать разбор номера функции. [Транспорт](../../../../source/mem/TRANSPORT.asm) · [Стенд GET_CURSOR_POS, листинг и результаты](replica/README.md)

Штатный F806h из EXEC попадает в bankFastPrepare на 300-м такте, доходит до первой инструкции в MAIN на 435-м и до тела getCursorPos на 455-м. Полный вызов занимает 539 тактов при начальном COMMAND и COPY, с двумя записями в маппер и нулём байтов снимка. Измерение выделенного входа выполнено при пустой очереди. Если перед запросом курсора отложен вывод, который его перемещает, результат зависит от порядка исполнения этих операций. [Трасса rev64](profile/profile.json)

У COMMAND сегодня в окне находятся восемь байт переходников, временный кадр, тип сообщения и метка профиля. В схеме без снимков SP и банк возврата каждого активного вызова должны переживать вложенный вызов в регистрах либо на частном стеке. Получатель строки или пачки должен успеть прочитать данные до следующей операции, использующей окно, либо сохранить ещё нужную часть у себя. Тогда любая операция может занять все 32 байта, а обращение только к регистрам оставляет окно свободным. [Поля кадра](../../../../source/mem/abi.inc) · [Смена профиля](../../../../source/mem/memory.inc)

CPM32 использует все 32 байта для данных на полном блоке. Подготовка запроса от 32 байт временно исполняет в окне 28-байтную программу настройки обеих страниц. При остатке 1–31 байт в окне исполняется отдельный байтовый цикл. Для постоянно свободного буфера потребуется вынести оба участка в банковый хвост. В DATA уже установлены 239 байт для GET/PUT и CPM32. Между частями хвоста свободно 7 байт и ещё 1 байт непосредственно перед окном, поэтому новые участки придётся разместить вместе с существующим кодом. Восстановление MEM после классической программы использует окно для работы с потенциально повреждённым хвостом и имеет собственный протокол. [Подготовка копирования](../../../../source/mem/copy-prepare.inc) · [Полный блок](../../../../source/mem/copytail.inc) · [Карта DATA](../../../../source/include/mxos.inc) · [Восстановление BIOS](../../../../source/bios/recover-copy.inc)

Профиль LOCAL обслуживает F815h с A=0 (MEM_OP_MOVE), когда оба адреса находятся в одной чужой странице либо в текущей странице отсутствует MEM_NEAR_COPY и оба адреса лежат в ней. Цикл исполняется с отображённой страницей данных и выбирает направление по порядку адресов. Разные страницы идут в CPM32. Пример из тестов сдвигает 257 байт с 4000h на 4001h внутри FAR-страницы 3 при вызове из MAIN. SDK экспортирует mxos_memmove_far. В исходниках поставляемых NC и EDIT удалённого MOVE не найдено. При переразметке цикл можно установить в банковых хвостах постоянно, сохранив публичный memmove. [Выбор маршрута](../../../../source/mem/memory.inc) · [Тест перекрытия](../../../../scripts/emu80/check-memory-operations.py) · [Вход SDK](../../../../sdk/src/mxos_z88dk.asm)

## Подстановка арифметики и локальные драйверы

В CPU-стенде 8080 подстановка UPPERCASE для `q` сократила стоимость с 73 до 41 такта, CMP_HL_DE — с 47/60 до 19/28, SUB_HL_DE — с 65 до 28. Сравнение сделано с прямыми историческими CALL из MAIN, включая возврат. Размер подстановок — 37, 7 и 6 байт соответственно. [Входы, регистры и такты](inline/README.md)

Для клавиатуры, звука и часов разобрана загрузка нужных служб в страницу вызывающего с прямыми локальными CALL. Зафиксированы условия возврата приложению до 384 байт в EXEC без устройств и места, где гостевым измерителям нужны переносимые чтение, диапазон и шкала времени. [Проект размещения и перечень бенчмарков](io-dll.md)

Штатный SjASMPlus 1.24.0 с `--i8080` собирает макросы CMP_HL_DE, SUB_HL_DE и DELAY_B с отдельными локальными метками каждого раскрытия. Для задержки при N итерациях прямой CALL из MAIN по C190h занимает 27 + 15N тактов, подстановка — 15N. Для входа C18Fh из L добавляются 5 тактов к каждому пути. Значение 0 задаёт 256 итераций. В автономном CPU-стенде сопоставлены 20 пар с разными счётчиками и начальным CF. Пример также показывает прямой CALL из MAIN, одиночные F800h/F806h и синхронную передачу двух PRINT_CHAR одной десятибайтной пачкой через 012Ch. [Собираемые примеры](call-examples.asm)
