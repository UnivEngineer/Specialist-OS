# Банковая печать MXOS2, MEM rev71

Итоговый образ MMX Flash имеет SHA-256 `b87ba3033b0dbc6cdd4fce4d0ecb9317c0e1d12f986190ec64f70c550c25dcee`. Измерения выполнялись на 8080, 2 МГц, в скрытом Emu80 с фиксированными 32×. Продолжительность указана в тактах эмулируемого процессора.

## Выбор вызова

`printStringZ` и `printStringRawZ` проверяют каждый байт у отправителя в развёрнутом цикле ×4. Завершающий NUL остаётся под HL. Пустая порция заканчивается в банке. При полной порции получатель сразу печатает 32 байта из окна FFC0h–FFDFh.

`printStringLim` принимает точную длину BC и обрабатывает каждый байт по правилам `printChar`, включая 00h. В MAIN прямой вход C8F9h, в DOS и EXEC операция 012Eh через F806h или F800h. HL возвращается за массивом, AF/BC/DE сохраняются. В SDK доступна `mxos_printStringLim(text, bytes)`. Для глифов без обработки управляющих кодов предусмотрен `printStringRawLim`.

Для известной длины каждое полное окно заполняется через 16 пар POP HL / SHLD общей развёртки CPM32 по FF0Eh. Последние 29–31 байт переносятся локальным стековым копировщиком, 1–28 байт — прямым циклом ×4 с точным остатком. При 28 байтах прямой цикл ещё выигрывает. С 29 байт общий стековый путь стабильно быстрее при обоих выравниваниях источника. [Замеры выбора порога](../text-lim-crossover/README.md)

При BC=30 локальный копировщик устанавливает SP на источник и входит со второй пары своей развёртки из 16 пар. Он выполняет 15 команд POP DE и после каждой записывает E и D в окно. При BC=29 или 31 первый байт копируется отдельно, затем следуют 14 или 15 пар. При BC=62 получаются две порции — 32 байта через FF0Eh и 30 локальным путём.

## Полный вызов с обработкой управляющих кодов

Отсчёт включает внешний CALL, обработку текста, отрисовку и RET. Во всех маршрутах используются одни и те же байты, начальный курсор и содержимое видеопамяти. Адреса источника относятся к странице вызывающего. Столбцы F806h и F800h одинаковы для DOS и EXEC. Каждая строка сравнивает вызовы на одной длине. Стоимость отрисовки зависит от текста и выравнивания глифов, поэтому порог копировщика определён отдельным измерением без вывода.

В обеих таблицах банковая ячейка содержит такты и два процента. Первый показывает прирост времени относительно MAIN, второй — долю добавочных тактов в банковом вызове. Для Z длиной 128 байт разница равна 19 080 тактам. Деление на 74 785 тактов MAIN даёт +25,5%, деление на 93 865 тактов F806h даёт 20,3%. Оба показателя охватывают весь путь печати, включая разбиение на порции.

## Почему растёт разница на 128 и 256 байтах

В контрольной серии сравнили одну и ту же строку `Abc123! ` с повторениями. Первый маршрут печатает её целиком через C818h в MAIN. Второй вызывает в MAIN тот же вход шрифта D830h, который принимает банковые порции, и передаёт ему по 32 байта с сохранением позиции курсора. Третий печатает через F806h из EXEC. Для каждой длины совпали все 12 КиБ видеопамяти и координаты курсора. Исходный X равен 16 в единицах BIOS, то есть 32 пикселям от левого края.

| ----: | -------------: | ---------------: | -----------: | --------------------------------: | ----------------------: | --------------------------: |
|    32 |          16962 |            17114 |        19790 |                               152 |                    2676 |                       0 / 0 |
|    64 |          40941 |            42286 |        47011 |                              1345 |                    4725 |                       8 / 8 |
|   128 |          74785 |            85042 |        93865 |                             10257 |                    8823 |                      8 / 16 |
|   256 |         140811 |           170554 |       187573 |                             29743 |                   17019 |                      8 / 32 |

¹ Разница между серией вызовов D830h и одним вызовом C818h включает смену строкового входа. Если использовать D830h в обоих вариантах, один вызов на 256 байт занимает 141 449 тактов, восемь вызовов по 32 — 170 554. Само разбиение добавляет 29 105 тактов в MAIN.

² Разница между F806h и такими же порциями D830h в MAIN включает заполнение окна, переходы, возвраты и обработку TEXT. В этой серии Z она точно равна `627 + 2049 × число полных окон`.

Rotate 6×8 быстро рисует четвёрку глифов, если начальный пиксель выровнен на байт экрана и в порции осталось хотя бы четыре символа. После первого переноса строки очередное окно начинается при X=18, следующее при X=114. Обе позиции смещены на четыре пикселя от границы экранного байта. При таком начале два символа нужны для выравнивания, а в конце порции может остаться ещё неполная четвёрка. В отдельном прогоне счётчик на вызовах одиночной отрисовки из Z и LIM показал 8 глифов для непрерывной строки в 256 байт и 32 для восьми окон. Такты в таблице сняты без счётчика.

Контроль с X=0 дал на 256 байтах ноль одиночных глифов в обоих маршрутах, 132 173 такта в MAIN и 154 451 через F806h. Доля добавочных тактов в банковом времени снизилась с 24,9% до 14,4% при тех же восьми окнах. Для воспроизведения в штатном измерителе предусмотрен режим `--suite text-windows`. [48 измерений в скрытом Emu80 при 32×](window-cost/result.json)

Для выбора маршрута длинных строк отдельно измерены штатный Far256, переход на него после двух окон и подбор длины порции по фактическому X курсора в MAIN. [Сравнение с Win32 при разных X и с управляющими кодами](buffers/README.md)

## CPM32 и размеры

От входа читателя TEXT до RET полный блок занимает 519 тактов против 693 у предыдущего стекового варианта. С внешним CALL это 536 и 710 тактов. Горячий шаг физического межбанкового переноса занимает 1020 тактов против 1022. [Отдельная методика, матрица и результаты CPM32](physical/README.md)

| Компонент, байт | rev70 | rev71 | Изменение |
| --------------: | ----: | ----: | --------: |
|        BIOS.sys |  6107 |  6142 |       +35 |
|         DOS.sys | 31471 | 31471 |         0 |
|          IO.sys |   796 |   818 |       +22 |
|         MEM.sys |  3070 |  3070 |         0 |
|  LOCALBLOCK.bin |  1600 |  1600 |         0 |
|      CLIENT.bin |   448 |   448 |         0 |
|   TRANSPORT.bin |   960 |   960 |         0 |
|      Хвост DATA |   448 |   448 |         0 |
|      Общее окно |    32 |    32 |         0 |

BIOS получил публичный JMP, запись реестра и выбор между счётным входом шрифта и совместимым посимвольным путём. До шрифтового слота D800h остаются два байта. Прибавка IO приходится на MAIN с совместимым обработчиком и таблицей режимов. Физическая развёртка CPM32 расположена в MEM. Хвост DATA входит в TRANSPORT, окно учитывается отдельным сегментом MEM.

## Проверки

- Штатные сборки прошли через `build-all.ps1` и `build-image.ps1 SystemEmuWritable`. Проверены раскладка BIOS/DOS, раздельные таблицы, операции памяти, DOS batch и ABI SDK. Обёртку C с аргументами на стеке собрал sccz80 и выполнил на 8080 через настоящий F806h. [Журнал сборки](build-all.log)
- CPU-тест проверил начало и конец исходного диапазона, отсутствие чтения за NUL и FFE0h, точный порог, очередь, вложенные пачки, вывод с прежним FNT и перехваченные C809h/C8F9h. Для обычного LIM проверены F800h и F806h в MAIN и банке, прямой C8F9h, сохранение AF с обоими значениями CY и запись результата в MX_REGS.
- В Emu80 в отдельном 33-байтовом буфере встречаются NUL, CR, LF и ESC на позиции 31 с аргументом в следующем окне. Для всех пяти маршрутов видеопамять, курсор, инверсия и состояние ESC совпали с серией отдельных вызовов C809h из MAIN. [Результаты проверки печати](text/result.json)
- В Emu80 прошли 776 сценариев копирования и MOVE с физическим маппером MX2, включая RAM, ROM, хвосты, перекрытие и возврат в банк инициатора. [Результаты переноса](copy/result.json)
- Через гостевую клавиатуру запущены NC EXEC, CLI, NC MAIN, EDIT MAIN и EDIT EXEC. Оба редактора открыли C:/AUTOEXEC.BAT и вернулись в основной NC. Пройдены холодный и тёплый сброс, а также перезагрузка DOS при несовместимой ревизии MEM с сохранением B:. [Приложения](apps/result.json) · [Сбросы](physical/bootstrap-hidden.json)
