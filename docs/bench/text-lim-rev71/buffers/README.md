# Far256 и выбор размера окна, MEM rev71

Архивные замеры MEM rev71 показывают, как работал прежний общий буфер Far256. В действующей сборке FontBen использует собственный Far1024, а 012Ah вызывает PRINT_STRING_LIM_MAIN. [Актуальный ABI](../../../../source/mem/api.md#печать-из-буфера-в-main) · [Сравнение Far1024 и Win32](../../fontben-far1024/README.md)

`Far256` — название маршрута FontBen. Приложение вызывает `MXOS_BIOS_TEXT_PRINT` (012Ah) с методом `TEXT_PRINT_SHARED`. MAIN забирает десятибайтовый запрос, затем CPM32 копирует исходные данные в общий буфер BIOS по ED80h порциями до 256 байт. Шрифт получает всю порцию одним вызовом. Для Z в запросе задаётся доступная длина с учётом NUL. При 255 печатных байтах терминатор входит в первую порцию, при 256 нужен ещё один перенос. Штатные виды запроса — Z, RawZ и RawLim.

## Две опытные реализации

**Переключение после 64.** Банк печатает два полных окна обычным путём. У ASCIIZ длина хвоста неизвестна. Если следующий байт ненулевой, 8080 ищет NUL в оставшейся строке и передаёт точную безопасную длину штатному запросу Far256. У RawLim и обычного Lim оставшаяся длина уже есть в BC. Стоимость исполнения счётчика окон, подготовки изменяемых полей запроса и сканирования ASCIIZ включена. Заранее выделено статическое место под запрос с постоянным методом, отдельного выделения памяти в каждом вызове нет.

**Выравнивание порции.** Банк сначала штатно заполняет до 32 байт с соблюдением контракта Z или LIM. Уже в MAIN прототип читает фактический X из BIOS перед рендером. Для полного окна таблица выбирает самый длинный префикс в пределах 29–32 байт, который для печатных символов Rotate 6×8 закончится на границе байта экрана с учётом переноса строки. В банк возвращаются число напечатанных байтов и признак первоначально полного окна. До трёх оставшихся байтов снова читаются при следующем заполнении. Последняя короткая порция исполняется как есть. Отдельного системного вызова для курсора нет. При ровно 32 оставшихся байтах прототип тоже может разбить последнюю порцию. Таблица на 256 байт и вспомогательный код размещались только в тестовой памяти. Выбор настроен на текущий Rotate, стоимость обнаружения и выбора алгоритма для произвольного сменного FNT не измерялась.

**Управляющие коды.** Прогноз ширины учитывает только печатные символы. Следующая порция начинает с фактического курсора, включая все эффекты предыдущей. В серии с CR и ESC на границе 32 байт при длине 256 получены MAIN 151 569, Win32 195 074, Far256 171 728, после 64 — 183 650, по X — 194 603 такта для обычного Z. При X=16 на печатном тексте выравнивание экономило 20 816 тактов, а с этими управляющими последовательностями — 471 такт. Для опытного счётного Lim дополнительно проверен 00h внутри диапазона. Видеопамять, курсор, ESC и инверсия совпали с прямым BIOS во всех проверенных случаях.

## Воспроизведение

Три серии выполнены на одном образе rev71 `b87ba3033b0dbc6cdd4fce4d0ecb9317c0e1d12f986190ec64f70c550c25dcee`. Скрытый Emu80 с физическим маппером MX2 работал на фиксированных 32×, модель 8080 на 2 МГц. Начальный Y=10. Печатный текст состоит из повторов `Abc123! `. Все общие контрольные точки MAIN и Win32 при X=16 совпали до такта с предыдущим опытом. Проведено 494 измерения, включая повторные контрольные маршруты. Подмены кода применялись только в оперативной памяти тестового экземпляра и снимались после вызова.

```powershell
$rt = "$env:LOCALAPPDATA\Specialist-OS\emu80\19782\text32"
python docs/bench/text-lim-rev71/buffers/run.py --runtime $rt
python docs/bench/text-lim-rev71/buffers/run.py --runtime $rt --raw-z
python docs/bench/text-lim-rev71/buffers/run.py --runtime $rt --counted-extension
```
