# Разделение файловой подсистемы и состояние FAT16

Аудит исходников на 24.10.2026. Область задачи — файлы в корне тома,
без подкаталогов и без реализации FAT12. Существующий формат образов в этой
работе не меняется.

## Слои

```text
Программа / NC
    → файловые точки входа DOS
    → драйвер выбранного тома
        → текущая FAT-подобная реализация MXOS
        → будущая реализация стандартного FAT16
        → будущий модуль файловой системы RAMFOS
    → интерфейс физических блоков
        → RAM / системное ПЗУ / AT29C040A / будущий дисковод
```

Физический драйвер читает и пишет блоки, но не разбирает имена, записи
каталога, FAT или заголовки RAMFOS. Драйвер тома отвечает за эти структуры.
Одна буква диска связывает физический драйвер, файловый драйвер и его контекст.
Загружаемый модуль и контекст должны оставаться в памяти до отключения тома.
После подмены ядра их нужно загрузить и зарегистрировать заново.

Первый шаг разделения сохраняет старые регистровые контракты DOS, структуру
`FILE_DESCRIPTOR`/`FILE_INFO` и существующий дисковый формат. Это подготовка
диспетчеризации, а не готовый файловый драйвер RAMFOS.

## Текущий формат и кэш FAT

Сейчас реализован собственный FAT16-подобный формат MXOS: каждая запись FAT
занимает два байта. Упаковки 12-битных записей FAT12 нет. При этом малые тома
не соответствуют стандартной FAT16 по геометрии и ряду других признаков;
называть их стандартными FAT12 тоже нельзя.

Кэш расположен в FB00h–FEFFh и занимает 1024 байта: четыре физических сектора
по 256 байт. Он хранит востребованные сектора FAT и корневого каталога,
вытесняя старые с записью изменённых секторов. Вся FAT одновременно в памяти
не требуется. Надёжность записи и вытеснения нужно исправить до нового формата.

Сборщик сейчас выделяет FAT по числу всех физических секторов: у тома 64 КБ
таблица занимает 512 байт, у тома 2 МиБ — 16 КБ. Второй вариант уже работает
через частичный кэш. При переходе к логическим секторам 512 байт нужно выбрать
единицу кэширования: два логических сектора в том же 1-КБ буфере либо четыре
физических блока с обработкой составного сектора. Увеличение кэша не обязательно.
Требование держать FAT целиком стало бы отдельным ограничением размера тома.

29.10.2026 исправлен один случай вытеснения при создании файла:
`fatFindClusterFirst` мог загрузить достаточно секторов FAT, чтобы вытеснить
сектор каталога. После его повторной загрузки старый `v_cachedDescrPtr`
указывал в прежний слот кэша. Теперь адрес записи восстанавливается из
актуального буфера каталога и сохранённого смещения внутри 256-байтного сектора.
Это не исправляет остальные перечисленные ниже ошибки кэша и не меняет формат.

## Что уже работает в текущем формате

29.10.2026 добавлена обработка отказа записи при создании, удалении и
переименовании файла. Ошибка физического драйвера из сохранения кэша
фиксируется в `diskWriteErr`; итоговая файловая операция возвращает CF=1
и сбрасывает неподтверждённый кэш. Следующее чтение отражает носитель,
поэтому попытка удалить файл из ROM больше не скрывает его только в ОЗУ.
NC показывает отказ удаления и обновляет число файлов по каталогу.
Это не транзакционный откат: уже записанные секторы при частичной ошибке
не восстанавливаются. Преждевременное снятие dirty и общая обработка ошибок
чтения, изменения адреса/атрибутов и переключения тома остаются отдельными задачами.

- Отдельный аппаратный ABI: B=1/2/3, DE=номер блока/размер, HL=буфер/информация.
- Поля 32-байтной записи в основном расположены по адресам FAT.
- Слова и двойные слова создаются в little-endian (`DW`, `Set-Word`, младший
  байт первым). Проблемы общей перестановки байтов не обнаружено.
- Нумерация данных начинается с кластера 2; `fatClusterToSector` использует
  смещение области данных и число секторов в кластере.
- Значение свободной FAT-ячейки — ноль. Константа плохого кластера `FFF7h`
  корректна; FORMAT помечает недоступные хвосты страниц RAM-диска.
- В новой сборке аппаратные драйверы возвращают CF при ошибке обмена.
- F5 уже переносит файл порциями через пользовательское ОЗУ.

Этого недостаточно для чтения и записи стандартного FAT16.

## Выявленные отклонения и незавершённые места

| Область | Фактическая реализация и оставшаяся работа |
|---|---|
| Определение типа тома | `fatReadBootSector.inc` принимает первые три символа `BS_FilSysType` как признак FAT. Геометрия и число кластеров не проверяются. Нужны отдельное распознавание старого MXOS-формата и строгий разбор стандартного тома. |
| Размер логического сектора | FORMAT, сборщик образов, кэш, файловые циклы и драйверы используют 256 байт. Нужен слой логического сектора FAT поверх физических блоков: например, один логический сектор 512 байт из двух блоков по 256. Это сохраняет существующее оборудование. |
| Малые носители | Системный ROM 64 КБ, малые RAM-тома и flash 2 МиБ не укладываются в стандартную геометрию FAT16. Их нельзя молча объявить стандартными FAT16. Старый формат должен остаться отдельным режимом совместимости. FAT12 в эту задачу не входит. |
| BPB | Читается только `TotSec16`; `TotSec32` и `HiddSec` не применяются. Нет проверок степеней двойки, нулевых полей, переполнения, достаточности FAT и выхода областей за носитель. Данные помечаются валидными ещё до расчётов. |
| Загрузочный сектор | FORMAT создаёт 256 байт без сигнатуры по смещению `1FEh`. Системный загрузчик содержит команды 8080 и привязан к старой разметке. Для нового формата нужно отдельно решить загрузку «Специалиста», не превращая старый образ в новый на месте. |
| Зарезервированная область | Значение 1 уже записывается и читается. Однако FORMAT и сборщик размещают FAT по собственным константам; общая геометрия пока не стала единственным источником расчётов. |
| Число FAT | FORMAT/сборщик создают одну FAT. Одна копия сама по себе допустима, но DOS игнорирует `NumFATs`: начало корня считается сразу после первой FAT; обновление нескольких копий не реализовано. |
| Размер FAT | FORMAT вычисляет ёмкость из числа всех физических секторов, а не уточняет её по числу кластеров данных. Нужен проверенный расчёт геометрии нового тома и ограничение доступных кластеров областью данных. |
| FAT[0]/FAT[1] | FORMAT и сборщик записывают `FFFFh` в обе ячейки при `Media=F8h`. Первая ячейка не согласована с media descriptor. Изменяемые флаги состояния тома пока не поддерживаются. |
| Завершение цепочки | Последний кластер указывает на себя. Это не EOC FAT16. Загрузка/удаление не распознают диапазоны EOC, reserved и bad как отдельные состояния цепочки. |
| Выделение кластеров | `fatFindClusterCommon` начинает с нужного номера, но счётчик равен всей ёмкости FAT, а не оставшемуся диапазону. Возможен просмотр за допустимой границей. Нужна единая проверка `2..последний кластер данных`. |
| Свободное место | `fatGetFreeSpace` считает все нулевые ячейки всех FAT-секторов, включая запас таблицы; количество FAT-секторов берётся младшим байтом. Геометрия данных не ограничивает подсчёт. |
| Корень | Корень уже выделен отдельно и начинается с `dirStartSector`, без обхода FAT. Размер корня округляется вниз; циклы используют 8-битное число секторов. Нужно округление вверх и проверка предела числа записей, включая последний неполный сектор. |
| Свободные и удалённые записи | Пустые записи заполняются `FFh`; удаление ставит `FFh`. Поиск/создание/список понимают только этот маркер. Нужны стандартные состояния записи, специальное представление первого символа E5h через 05h и сохранение поддержки старых образов. |
| Типы записей | Поиск и список не фильтруют LFN, метку тома и каталог по атрибутам. Без поддержки подкаталогов их всё равно нужно пропускать, не выдавая за обычные файлы. |
| Метка тома | Читается только EBPB, запись метки в корне не создаётся. В конце копирования метки обнуляется адрес из HL, а не гарантированно `volumeLabel+11`: это затрагивает буфер boot-сектора вместо назначения. |
| Размер файла | Сборщик хранит `N-1`; DOS/NC/редактор опираются на эту семантику. У RKS в размер попадает размер исходного контейнера минус один, хотя записывается извлечённая нагрузка. Переход к точному N требует синхронной смены писателей и читателей. |
| Пустой файл | Создание всегда ищет первый свободный кластер; штатного случая «ноль байтов, нет цепочки» нет. Нужны отдельные пути создания, загрузки, копирования и удаления пустого файла. |
| Частичный сектор | `fileLoad`/`fileCreate` передают полные 256-байтные блоки. Последний блок может писать за конец целевого буфера или читать лишнюю память источника. Нужен байтовый остаток и служебный секторный буфер. |
| Многосекторный кластер | Пересчёт адреса учитывает `sectorsPerCluster`, но передача читает только один блок и затем переходит по FAT. Нужен общий цикл по секторам внутри кластера. |
| Большие файлы | `fileLoad`/`fileCreate` используют усечённый размер и 8-битный счётчик блоков; F5 расширяет счётчик, но всё ещё зависит от кластеров FAT. Для файлов больше доступного ОЗУ нужен общий потоковый интерфейс с 32-битной длиной. |
| Повреждённая цепочка | Нет общего лимита обхода, проверки цикла, свободного/плохого/зарезервированного следующего кластера, несоответствия длины файла цепочке. Удаление ждёт самоссылку и может зациклиться. |
| Перезапись и усечение | Старый файл удаляется до успешного выделения нового. При нехватке места остаётся частичная цепочка/запись; обработчик F5 частично компенсирует это удалением. Общего commit/abort и корректного truncate нет. |
| Ошибки кэша | Чтение/сброс кэша не проводят CF до всех вызывающих файловых функций. Флаг изменения снимается до записи и теряется при её ошибке; переключение диска очищает кэш без гарантированного flush. Успешный CF аппаратного драйвера ещё не гарантирует достоверный результат файловой операции. |
| Атрибуты | Удаление записей с флагами Read-only или System и замена файлов Read-only отклоняются FAT-драйвером на любом диске. System без Read-only можно заменить с сохранением атрибутов. Общей проверки всех остальных операций и допустимых изменений нет. В `fileGetSetAttr` входной B затирается значением A, хотя контракт обещает новые атрибуты в B; перед добавлением меню атрибутов это нужно исправить и проверить сохранение ошибок записи. |
| Времена и резерв | Заголовки в значительной степени копируются от вызывающего кода. Нужны определённая инициализация времён/резерва, нулевой `FstClusHI` для FAT16 и проверка сохраняемых полей. Комментарии «только FAT32» у времён неверны. |
| Имена | Короткие имена уже имеют ширину 8+3. Валидация символов, регистр и кодировка «Специалиста» требуют явной политики обмена. Сборщик уже отклоняет длинные/конфликтующие имена, но DOS-парсер обрезает длинное имя. |
| Границы носителя | Встроенный RAM-драйвер использует номер страницы из запроса без общей проверки диапазона. Flash маскирует адресные биты. Для разделения RAMFOS/MXOS обязательны проверки границ и отдельное резервирование страниц. |

## Расширение MXOS с адресом загрузки

`FILE_DESCRIPTOR.loadAddress` занимает **два байта `12h–13h`, little-endian**.
Это используется DOS, загрузчиками, редактором, NC и сборщиком образов.
Расширение сохраняется явно в старом формате. Эти байты одновременно являются
стандартным полем даты последнего доступа. Поэтому текущий вариант нельзя
называть полностью совместимым FAT16 с сохранением всех стандартных полей.

Для нового совместимого формата требуется отдельное решение хранения адреса
и точки входа: заголовок исполняемого файла либо отдельный индекс. Нельзя
самовольно перенести адрес в другие зарезервированные поля каталога. Пока
такое решение не принято, преобразование носителей не выполняется.

## Нормативные ориентиры

Использована спецификация Microsoft **FAT: General Overview of On-Disk Format,
v1.03, 06.12.2000**: [оригинал DOC](https://download.microsoft.com/download/1/6/1/161ba512-40e2-4cc9-843a-923143f3456c/fatgen103.doc),
[копия документа Microsoft в PDF](https://www.isdaman.com/alsos/protocols/fats/fatgen103.pdf).
Проверенные разделы: Boot Sector and BPB, FAT Type Determination,
FAT Data Structure, FAT Directory Structure.

Краткие критерии: логический сектор 512/1024/2048/4096 байт; FAT16 при
4085–65524 кластерах; EOC `FFF8h–FFFFh`; bad `FFF7h`; свободная FAT-ячейка 0;
удалённая запись `E5h`, конец списка `00h`; пустой файл имеет размер 0 и
первый кластер 0. Тип определяет геометрия, а не строка `FAT16`.
Размер корня округляется вверх, корень не является кластерной цепочкой.
Нумерация начинается с 2; наибольший кластер данных равен их количеству плюс 1.

Число 512 записей корня и две FAT — рекомендации совместимости, а не причина
отклонять любой том с другим ненулевым размером корня или одной FAT.

## Очерёдность реализации без подкаталогов

1. Завершить общий байтовый поток: открытие/чтение/запись/закрытие и отказ
   незавершённого создания. Убрать зависимость F5 от номера кластера.
2. Отделить логические сектора тома от физических блоков; проверять границы
   носителя и ошибки. Устранить потерю ошибок и грязных данных в кэше.
3. Ввести отдельные режимы старого MXOS и стандартного FAT16, распознавание
   BPB, геометрии и ёмкости FAT. Не применять эвристику строки `FAT` как
   доказательство FAT16 и не менять старые образы автоматически.
4. Исправить цепочки, выделение/освобождение, корень, состояния записей,
   размеры и пустые файлы. Согласованно обновить FORMAT и сборщик образов.
5. Определить метаданные исполняемых файлов, затем миграцию данных и совместимость
   старых программ, использующих `N-1` и адрес в `12h–13h`.
6. Проверить независимым FAT-инструментом на тестовых образах: пустой файл,
   границы сектора/кластера, многосекторные кластеры, фрагментация, полный
   корень/том, последний свободный кластер, обрыв/цикл/bad в цепочке,
   ошибки чтения/записи, граница 64-КБ страницы и копии FAT.

Для маленьких реальных RAM/ROM-носителей и flash 2 МиБ сохраняется старый режим.
Даже 4085 кластеров по 512 байт вместе с FAT, BPB и корнем требуют больше 2 МиБ.
Обычная дискета также потребует отдельного решения формата: физический драйвер
дисковода сам по себе не сделает её стандартным FAT16-томом.
Стандартные тестовые FAT16-тома должны иметь достаточную ёмкость; подмена
геометрии ради надписи FAT16 и реализация FAT12 здесь не планируются.
