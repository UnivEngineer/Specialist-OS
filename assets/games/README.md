# Библиотека игр «Специалиста»

Здесь хранятся игровые бинарники, исходные контейнеры и сопроводительные тексты. Состав образов `Games2M` и `Games64k` задаётся манифестами в `assets/`.

## Общий реестр

[catalog.csv](catalog.csv) охватывает рабочие и архивные игровые образы, включая демо из коллекции. Парный I80 относится к строке своего CPU. Вспомогательные BAT и тексты описаны в README семейств. Реестр отсортирован по колонке `Platform`.

- [std/](std/) — несгруппированные игры для аппаратного режима STD. В реестре отдельно указана рекомендованная среда MON или STD с BIOS MXOS.
- [mx/](mx/) — несгруппированные исторические MX-версии в исходных контейнерах. У [StarWars 2](families/starwars/originals/StarWars2-mx.cpu), Cannon Ball и Driller Tanks описатели указывают `m2_d400.mon` из `Soft/games_mx_i80`. После 26-байтного пролога образ совпадает с проектным Monitor-2 в 4040 из 4096 байт и содержит MX-адрес ВВ55 FFE3h. Для Cannon Ball и Driller Tanks в реестре стоит AUTO до проверки со стандартными средами RUN. У одноимённых STD RKS другие нагрузки и адрес загрузки.
- Adventur и Fish Cat хранятся в более ранних парах CPU/I80 из `Soft/games_mx_i80`. В описателях указан `m2_d400.mon`, а нагрузка, адрес загрузки и адрес входа совпадают с известными STD-файлами `ADVENTUR.RKS` и `CAT.RKS`. Образ H: воспроизводит эти RKS при сборке.
- [unknown/](unknown/) — нагрузки с неустановленной средой запуска. В [lafan/](unknown/lafan/) сохранены файлы исторических подборок Lafan. Суффиксы `.com.bin` и `.exe.bin` сохраняют архивное имя формата и отличают эти образы от исполняемых файлов MXOS. Файлы EXI, EX2, MG2 и MGK хранятся с архивными расширениями. Пустой `LoadAddress` означает, что адрес ещё предстоит установить.
- [families/](families/) — разобранные семейства. В `originals/` лежат исторические файлы, в `repaired/` — исправленные повреждения, в `patched/` — двоичные доработки, в `repacked/` — переупакованные образы, в `builds/` — сборки из восстановленных исходников.

В `README.md` семейства описаны происхождение, управление и проверенные способы запуска. Авторские тексты сохраняются побайтно в `originals/` или рядом с соответствующим архивом. Например, у [Elite](families/elite/README.md) отдельно хранятся авторское описание порта и старый текст в KOI8-R, который используется на H:. С исходной кодировкой сохранены четыре [описания из `games_mx_new`](mx/manuals/games_mx_new/README.md), [описание чёрно-белой Driller Tanks](std/manuals/games_new/driller_bw.txt) и [руководство к Saboteur из Lafan](unknown/lafan/Saboteur.TXT).

| Платформа | Что входит | Рекомендация для RUN |
|---|---|---|
| `STD+MON` | Классическая карта памяти и вызовы Monitor-2, включая варианты с цветовыми приставками. Статические признаки дают предполагаемую платформу. Игровые и аппаратные прогоны отмечаются в `Status` и описаниях семейств. | `MON` |
| `STD` | Аппаратный STD с BIOS MXOS. Так проверена Skachki. | `STD` |
| `RAMFOS` | Исторические нагрузки с установленным ABI RAMFOS и сборки из проекта для RAMFOS. | `RF` |
| `MXOS` | Сборки и адаптеры проекта для MXOS. | `NATIVE` для источника с флагом MAIN, `MX` для совместимого запуска |
| `MX` | Исторические адаптации для MX, включая StarWars 2, Cannon Ball, Color Ball, Driller Tanks, Fire Rescue и 16-цветный Exolon для MX2. | `MX` для StarWars 2 и Exolon, `AUTO` для остальных |
| `Unknown` | Архивные варианты с неустановленной средой запуска в MXOS. | Выбор в меню RUN |

`Origin` указывает совпавшую архивную копию или источник сборки. Пути с `Soft/`, `MySoft/` и `specialist-mx.org/` отсчитываются от `G:/Projects/RetroPC/Specialist/`, пути с `repo:` от корня проекта. `::` обозначает файл внутри архива, `+число` — смещение в байтах. `OriginMatch=file` означает совпадение всего файла, `payload` — совпадение нагрузки после снятия контейнера, `payload+checksum` — нагрузку с хвостом RKS. `derived` указывает исходник правки, `build` и `earlier-build` указывают исходники актуальной и прежней сборок. Самая ранняя доступная архивная копия и авторство отмечаются отдельно там, где их удалось установить.

`MySoft/` содержит ранние версии этого проекта. Происхождение игр устанавливается по независимым архивам. Например, файлы EXI/MG2 из Lafan совпадают по нагрузке с частью STD RKS. Для этих игр в библиотеке используются побайтно совпавшие экземпляры из `Soft/games1_rks` и `Soft/games_my`, пока порядок появления форматов не установлен.

`TapeCopies` перечисляет побайтно совпавшие копии в `Soft/games_my` и `Soft/games_my_test`. По уточнению владельца, эти папки, вероятно, содержат личный архив кассет, оцифрованных через эмулятор. RKS описывает полученный контейнер. Часть записей не запускалась на аппаратном STD, поэтому при оценке платформы учитываются обращения к ВВ55, вызовы системных входов и фактические прогоны.

`LikCopies` связывает шесть RKS с файлами из `Soft/games_lik_rks`, у которых совпали загрузочный диапазон и нагрузка после снятия префикса LIK. Обычные RKS уже лежат в `std/`. Архивное описание и формат приведены в [справке подборки LIK](std/manuals/games_lik_rks/README.md). В [семействе ZOO](families/zoo/README.md) сохранены три отдельные LIK-записи.

При пополнении из `Soft` сопоставляются нагрузка, адрес загрузки и адрес входа, если они установлены. Поэтому под одним названием могут храниться несколько редакций. Для пар CPU/I80 поле `ArchiveProfile` хранит имя ядра из описателя, например `r6_0000.mon` для RAMFOS и `m2_d400.mon` для MX-адаптации Monitor-2. `RunMode` для новых MX-вариантов остаётся `AUTO` до проверки со штатными средами RUN.

Игры из [games_rks/](unknown/games_rks/README.md) переупакованы в обычные RKS и получили имена по [исходному индексу](unknown/games_rks/games_m_2.txt), сохранённому в CP866. Адреса и контрольные суммы сверены с индексом. В [games_lik_rks/](unknown/games_lik_rks/) лежат дополнительные варианты с префиксом LIK и суффиксом `.rks.bin`.

Колонка `Variant` описывает историю файла независимо от платформы и контейнера.

| Вариант | Содержимое |
|---|---|
| `original` | Исторический файл побайтно, в исходном контейнере. Сюда входят и повреждённые входы патчей. |
| `repaired` | Исправлены ошибки контрольной суммы, карт или другие найденные повреждения. Примеры есть у [Lines](families/lines/README.md) и [«Алмаза-2»](families/almaz-2/README.md). |
| `enhanced` | Доработаны графика, данные или код игры. Пример — четыре публикации [BUDI](families/budi/README.md) с плашкой GAME OVER. |
| `rebuild` | Игра собрана из восстановленных и переработанных исходников. Пример — восемь сборок [«Алмаза-2»](families/almaz-2/README.md) для разных платформ. |
| `repacked` | Историческая нагрузка сохранена побайтно, а контейнер или заголовок запуска изменён. |

Во всех каталогах семейства используем нормализованные имена. Указываем название и номер игры, затем при необходимости среду запуска (`-std`, `-ramfos`, `-mx` или `-mxos`) и отличие варианта. Исходные имена указываем в README семейства. Короткие имена FAT 8.3 задаёт манифест образа. Жанр и родство игр можно указывать в реестре независимо от пути на диске.

В штатных образах H: игры STD имеют расширение `.rks` и по умолчанию запускаются в Monitor-2. Для игр RAMFOS указан `MODE=RF` в EXE, команда запуска — `RUN H:ПУТЬ.EXE -RF`. У проверенных пользователем MX-игр с `RunMode=MX` указан `MODE=MX`, сейчас это `EXOLON.EXE`. Для запуска Exolon в MX используется команда `RUN H:EXOLON.EXE -MX`. Остальные игровые EXE получают `MODE=AUTO`. Команда RUN без ключа для EXE с полем режима открывает меню выбора среды. Нативный «Алмаз-2» передаётся загрузчику DOS по флагу MAIN. [Большой образ](../H-Flash-2M-Games.txt) · [Малый образ](../H-ROM-64k-Games.txt).

Колонка `Ramfos` связывает нагрузки по SHA-256 с [реестром RAMFOS](ramfos-candidates.md). У BUDI и новых сборок «Алмаза-2» ссылки с пометками относятся к исходному или раннему бинарнику. Одноимённые RAMFOS-версии с другой нагрузкой перечислены в `Evidence`. Например, STD-файлы Digger, Dungeon, Chess4 и ZOO отличаются от кандидатов RAMFOS. Один вызов C836h у Paket даёт лишь слабый признак. Игровая проверка отражена отдельно в `Status` и README семейств.

По пользовательской проверке [Paket](std/Paket.rks) работает с `RUN H:PAKET.RKS -MON` (аппаратный STD и KOI-7). Для [Skachki](std/Skachki.rks) подтверждена команда `RUN H:SKACHKI.RKS -STD`. В прежней проверке игры в MON отсутствовали звук и меню. После запуска в MX система перестала нормально работать, и перезагрузка её не восстановила. По последующему сообщению автора проекта Skachki уже исправлена.

В исторической пробе Emu80 сбой прежней версии Skachki в MX при выключенной SDP изменил 11 страниц системной flash C:, включая загрузочную страницу. При включённой SDP после того же сбоя C: и H: остались побайтно целы, а Reset вернул систему в NC. [Подготовка flash-образов Emu80](../../scripts/emu80/README.md)

С обновлённой моделью AT29 `std/Skachki.rks` прошла проверку запуска и контрольного чтения в STD и MON. Одноимённая [архивная версия](unknown/games_rks/Skachki.rks) прошла в MON. Для неё в MX после первого Reset контрольный файл не прочитался, а после второго Reset прочитался в трёх дополнительных стартах. Во всех пробах содержимое A:, C: и H: сохранилось побайтно. [Протоколы повтора](../../docs/compat/game-campaign/at29-sdp-skachki/results.json) · [Проверка двух сбросов](../../docs/compat/game-campaign/at29-sdp-skachki/rechecks/summary.json).

[exolonmx.i80](mx/exolonmx.i80) взят из `16color/MX/` в сборнике Ивана Городецкого. Его 22 303 байта совпадают с нагрузкой авторского `16color/MX2/exolonmx.rks`. В авторском CPU-дескрипторе адрес загрузки и входа равен `0000h`. Это порт версии Максима Китченко для «Вектора-06Ц», восходящей к игре Раффаэле Чекко для ZX Spectrum. При входе Exolon пишет в F01Ch и на MX2 переводит карту STD в MX. По авторскому описанию игра использует собственные процедуры и шрифты. Пользователь проверил запуск и базовое управление во всех средах RUN. [Авторский архив](https://zx-pk.ru/attachment.php?attachmentid=73487).

Скачанный `ExolonsSpecialist09062020.zip` совпадает с вложением автора от 12.09.2020. Ссылка `exolon_src.zip` в первом сообщении ведёт к демонстрации заставок и биперной музыки января 2019 года. По сообщению Ивана Городецкого, перенос основан на бинарнике для «Вектора-06Ц» с заменёнными процедурами. [Подтверждение финального архива](https://zx-pk.ru/showthread.php?p=1218751#post1218751) · [Исходники демонстрации](https://zx-pk.ru/attachment.php?attachmentid=67784) · [Комментарий автора о коде переноса](https://zx-pk.ru/showthread.php?p=1068989#post1068989).

На H: `EXOLON.EXE` содержит ту же нагрузку. Для явного выбора MX используется `RUN H:EXOLON.EXE -MX`. Игра ставит стек на `9000h` и использует временные данные выше `8C00h`; в заголовке стоят флаги `00h`.

В меню Exolon клавиша `1` начинает игру. Стрелки управляют движением, прыжком и приседанием, короткий пробел стреляет. Для гранаты удерживайте пробел примерно секунду. В Emu80 при запуске в MX подтверждены выстрел и уменьшение счётчика GRENADES с 10 до 09 при удержании. [Инструкция Exolon](https://www.gamesdatabase.org/Media/SYSTEM/Amstrad_CPC/Manual/formated/Exolon_-_1987_-_Hewson_Consultants.pdf).

### Мониторы в архивных описателях CPU

В `Soft/games_mx_i80` и `Soft/games_mx_new` найдены 76 пар CPU/I80. Третья строка описателя задаёт образ среды для архивного загрузчика. Для представленных в коллекции пар она записана в `ArchiveProfile` отдельно от `Platform` и `RunMode`. `games_mx_i80` можно считать каталогом конфигураций архивного эмулятора для MX и RAMFOS. Какой режим подходит самому бинарнику, проверяется отдельно. Например, для Adventur и Fish Cat архив указывает MX-монитор, а их нагрузки совпадают с STD-вариантами.

| Имя в CPU | Пар | Что удалось установить |
|---|---:|---|
| `m2_d400.mon` | 45 | Вход D400h, пролог переносит резидентный код в C000h. У Monitor-2 заменены вход и аппаратные адреса для MX, включая ВВ55 FFE3h. Все четыре игры из `games_mx_new` указывают этот образ. |
| `r6_0000.mon` | 24 | RAMFOS с входом 0000h. Все 6144 байта совпадают с началом `OS/spmx.rom`. Пролог переносит код в C000h, C600h и F800h. Начальный вход F97Bh выбирает ОЗУ MX записью в FFFCh. |
| `m1_d800.mon` | 1 | У `BUDI.CPU`. Пролог с D800h копирует код в C000h. За прологом есть код Monitor-2 с MX-адресами ВВ55. |
| `mx_d400.mon` | 2 | У `SEX0.CPU` и `SEX1.CPU`. Пролог совпадает с `m2_d400.mon`, резидентный монитор отличается. |
| `SPMX.ROM` | 2 | У `d_t_e.cpu` и `shahm_mx.cpu`. Это ссылка на образ ПЗУ MX. Обе внешние игровые нагрузки также есть в RAMFOS-реестре. |
| Третьей строки нет | 2 | `BLOB_COP.CPU` и `R_TEST.CPU`. |

У `M2_D400.MON` и `R6_0000.MON` в `OS/soft_mx_i80.rar` стоят даты 1996 и 1997 годов соответственно. На оригинальном «Специалисте-MX» Афанасьева селектор обслуживает основное ОЗУ, RAM-диск и ROM-диск по адресам FFFCh–FFFEh. HardWareMan добавил карту STD как четвёртое состояние селектора в MX2. Её выбирает запись по адресу FFFFh из MX. Номер режима задают младшие биты адреса записи. [Карта памяти «Специалиста-MX»](https://spetsialist-mx.softrest.eu/index18.html), [описание MX2 со слов HardWareMan](https://spetsialist-mx.softrest.eu/index21.html).

В ветке RAMFOS, датированной vinxru 1 ноября 2013 года, запуск RKS использует другой образ `Monitor2.sys`. Архивный `OS/RAMFOS-master/RomDisk/Monitor2.49152.sys` совпадает с проектным Monitor-2. Его вход C001h пишет в FFFFh и включает STD на MX2. Архивный `M2_D400.MON` рассчитан на поведение оригинального MX и инициализирует ВВ55 по адресу FFE3h. [Загрузчик RKS vinxru](../../source/ramfos/rks.inc), [вход Monitor-2](../../source/monitor2/loader.inc).

В STD ВВ55 зеркалируется в окне F800h–FFFFh, поэтому FF00h–FF03h также используются классическими играми. В режиме MX устройство доступно по FFE0h–FFE3h. Подмена монитора сохраняет входы C000h/C800h для программ, работающих через BIOS. Играм с прямым опросом ВВ55 для запуска в MX требуется соответствующая аппаратная адресация. [Карта памяти профиля MX2](../../scripts/emu80/specialist-mx2.conf).

Все четыре сборки из `Soft/games_mx_new` — адаптации игр MSX для «Специалиста-MX». Сопроводительные тексты к Cannon Ball, Color Ball, Driller Tanks и Fire Rescue называют Ивана Городецкого автором MX-версий и Александра Тимошенко автором рекомпиляции с Z80 на КР580. При проверке старта в модели 8080 все четыре MX-нагрузки записали 91h в FFE3h и использовали регистр цвета FFF8h. Классические Cannon Ball и цветной Driller Tanks из `Soft/games_new` записали 91h в FF03h. Проверка охватывает начальные обращения к устройствам по карте памяти. Игровой процесс на MXOS требует отдельного прогона.

Байты `Almazy.rks` и `tetris.rks` совпали с файлами из авторского `almazy.zip`. `AlmazyMX.rks` совпал с более поздней сборкой `almazy_specialist.rks` в `Soft/Almazy`. 3D-демо совпало с обоими локальными архивами CityAceE. [Первая публикация «Алмазов» с бонусным Tetris](https://zx-pk.ru/threads/36767-igra-quot-almazy-quot-dlya-spetsialista.html), [сборка с выбором 16 цветов MX2](https://zx-pk.ru/threads/36804-igra-quot-almazy-quot-dlya-raznykh-8-bitnykh-kompyuterov.html), [3D-движок](https://zx-pk.ru/threads/36776-3d-dvizhok-dlya-spetsialista.html).

Сборщик сохраняет `RunMode` в заголовке игрового EXE как рекомендацию. Обычный COM/EXE загружает DOS. Для установки рекомендуемой среды укажите ключ в команде RUN. Вызов RUN с COM/EXE без нативного флага и ключа режима открывает меню. Для RKS RUN по умолчанию выбирает Monitor-2. [Документация сборщика](../../scripts/images/README.md)

Для исследования удобно фильтровать каталог по `Platform`. Для H: после проверки вариантов удобнее папки по семействам и механике. В `Dash` можно собрать Dash-1, Dash-2, Almaz, Almaz-2, Almazy и DownEarth, указав в описании родство вариантов и сходство механики. Следующие готовые группы — Tetris, Chess, BUDI с ZOO, Buran и StarWars. Вложенные папки STD, RAMFOS и MXOS пригодятся там, где несколько платформенных вариантов одной игры. У ещё не разобранных игр поле `Family` можно оставить пустым.

## Исправления бинарников

Перед патчем сохраните побайтный оригинал в `originals/` соответствующего семейства или в `assets/games/originals/<игра-или-группа>/` для отдельной игры. Сверьте уже существующую архивную копию, сохраните её и исторические варианты. Исключите оригиналы из образов; для исключения из автоматического поиска добавьте `.bin` после исходного расширения. Если есть исходники, исправляйте их. Для внешнего бинарника сценарий патча должен проверять известный хеш и ожидаемые байты и отклонять неизвестный вариант.

В реестре укажите рабочий файл, причину и суть исправления (включая контейнер или сумму), оригинал, сценарий воспроизведения и фактическую проверку. Подробности исследования храните в локальной `docs/`.

## Реестр RAMFOS-кандидатов

02.11.2026: в [реестр игровых RAMFOS-кандидатов](ramfos-candidates.md) внесены все 62 различные игровые нагрузки с отобранными ABI-признаками. [Машинно читаемый реестр](ramfos-candidates.json) хранит SHA-256, происхождение, копии и смещения вызовов. Сильные/неоднозначные кандидаты отделены от уже известных адаптаций и пользовательских сообщений об ошибках. Наличие в реестре не означает подтверждённую совместимость и не включает файл в образы.

Полные локальные отчёты находятся в `docs/games/` и `docs/compat/`. Для ADSKOK: `docs/compat/adskok-001/RESULTS.md` и `patch-check.json`. Эти отчёты могут отсутствовать в Git; данный реестр, оригиналы и сценарии должны оставаться достаточными для определения внесённого изменения.

Новые исправления добавляются в таблицу исправлений вместе с исходным файлом, точным описанием изменения, способом воспроизведения и фактическим статусом проверки. Все варианты учитываются в общем реестре.

[Инструкции для игровых проб по вариантам](playbook.md).

[Воспроизводимая кампания через NC и RUN](../../scripts/games/README.md) сопоставляет исходники каталога с нагрузками по SHA-256, проверяет пути запуска и собирает результаты по вариантам и средам. [Локальная таблица результатов](../../docs/compat/game-campaign/RESULTS.md).
