# Профили NC: MAIN и EXEC

Оба профиля собираются из `NC.asm`. `NC_BANKED=0` оставляет непосредственный MAIN-рендер; `NC_BANKED=1` выбирает EXEC-контроллер и пакетный MAIN-бэкенд. Логика клавиш, каталогов, Radix, конфигурации, файловых операций и геометрии общая.

Сборка: `python scripts/build/build-nc.py`. Общий движок и приложения собирает `scripts/build/build-project.ps1 OS`. CPU-файлы являются метаданными сборщика образа; исполняются COM/DLL-контейнеры с заголовком MXOS2.

| Файл в образе | Результат сборки | Назначение |
|---|---|---|
| `A:\NC_MN.COM` | `NC.cpu` + `NC.i80` | MAIN-профиль для тестов и сравнения |
| `A:\NC.COM` | `NC_DOS.cpu` + `NC_DOS.i80` | Штатный DOS-лаунчер, находит или регистрирует резидент |
| `A:\NC_CORE.DLL` | `NC_CORE.cpu` + `NC_CORE.i80` | EXEC-контроллер, каталоги, индексы, сортировка и состояние |
| `A:\UI_GFX.DLL` | `UI_GFX.cpu` + `UI_GFX.i80` | MAIN-движок, текст, окна, битмапы, цвета и клавиатурный курсор |

Оба профиля и DLL банкового профиля включены в системный образ A:. Бенчмарки и StarTrek находятся на H:. Загрузчик и DLL должны лежать в корне одного диска A:..H:, его буква определяется при запуске. Системный образ A: тоже должен быть обновлён: профилю нужен соответствующий ABI DOS. BIOS, DOS и оба профиля устанавливаются из одного системного образа.

## Жизненный цикл

NC.COM использует RESIDENT_FIND по ключу 434Eh. При отсутствии загружает NC_CORE.DLL в EXEC и вызывает короткую регистрацию с B=1. Этот вызов возвращается до начала интерфейса. Если CORE уже зарегистрирован, загрузчик выбирает его ключ и передаёт управление BIOS, который возобновляет оболочку на свежем стеке. Лаунчер выполняется в арене установщиков DOS и освобождает её до входа в интерфейс. При вызове из BAT сценарий продолжает выполнение.

EXIT из CLI возвращает к последнему профилю NC. Для BANK BIOS вызывает RESIDENT_SHELL_RESUME на свежем стеке, а при отсутствии резидента запускает A:\NC.COM. Для MAIN BIOS повторно загружает A:\NC_MN.COM. При отказе загрузки остаются переход в CLI и запрос пути. Явные команды NC и NC_MN выбирают соответствующий профиль.

Вход CORE: начальная регистрация либо RESTORE; A=2 — общий кооперативный CLOSE SDK. CORE сохраняет состояние панелей, при необходимости загружает MAIN-движок, обновляет геометрию и рисует интерфейс. Существующий handle GFX проверяется через MODULE_CALL; если модуль был освобождён загрузчиком, GFX загружается заново. Сам CORE при обычном возврате не перечитывается с диска.

Штатный **Shift-F10 Exit** возвращает в CLI с сохранением CORE. Физическая F10 без Shift также принимается, но её подпись находится на втором уровне подсказок. **Ctrl-F10** в банковом профиле сохраняет состояние и полностью освобождает NC: CORE снимает ключ через RESIDENT_RELEASE, возвращается в системный диспетчер, после чего DOS освобождает банк. До RET код активного резидента не удаляется. Автоматическое вытеснение произвольных резидентов при неудачном ALLOC не включено.

Перед запуском внешней программы CORE выполняет накопленные команды рисования и сохраняет счётчики изменений дисков. Загрузчик MAIN проверяет пересечение нового образа с кодом и выделениями BSS неактивных MAIN-модулей. Программа или установщик шрифта с пересекающимся диапазоном вытесняет свободный GFX. Активный модуль закреплён и возвращает ACTIVE при коллизии. Неизвестная совместимость и верхние пусковые программы рассматриваются как пользователи всего нижнего MAIN; их запуск также изменяет счётчики изменений всех дисков.

F4 и Shift-F4 передают управление EDITCORE.DLL синхронно. Enter на файле использует тот же путь, если команда в CLI.EXT целиком равна `A:\EDIT.COM` без параметров. Другие обработчики и команды, набранные вручную, выполняются штатно. Редактор получает путь из банка NC, возвращается через RET и освобождает свой EXEC-банк. NC освобождает свой экземпляр UI_GFX перед запуском EDITCORE. Редактор загружает UI_GFX под своим владельцем, а после выхода NC загружает её для своего сеанса. NC сохраняет позицию на панели.

## Память

UI_GFX занимает 1B00h–337Fh. На время области рисования NC_CORE регистрирует в MAIN диапазон 3380h–539Fh для приёмного пакета, снимка окна, серий цветов и двух снимков тулбара. Каталоги, палитры строк, геометрия и признаки пригодности снимков остаются у NC_CORE. NC передаёт UI_GFX путь к общей справке и события клавиатуры, а после её закрытия перерисовывает панели.

UI_GFX исполняет развёрнутые копировщики и общие UI-примитивы с адресами, переданными клиентом. NC_CORE освобождает свою область MAIN перед запуском дочерней программы. Оба диапазона заканчиваются ниже Fast12K, таблицы которого без других верхних резервов начинаются с 6400h.

CORE использует отдельный EXEC, четыре слота по 255 записей с терминаторами, индексные таблицы и scratch Radix. Видимые каталоги защищены, среди остальных преимущество у корней текущих дисков обеих панелей. Корни занимают обычные слоты и не привязаны к H:. Пакет CORE начинается с D000h; зеркало текстового состояния — с DF00h. Всё остаётся ниже служебного стека EXEC. Предварительные серии палитр диалога используют уже свободный scratch Radix, без килобайта нулей в файле CORE.

MAIN-модули и BSS учитываются таблицей модулей и аллокатором. NC_MN.COM объявляет постоянную рабочую область `[vars,FILE_CACHE_A)` как BSS, а минимальную память каталогов — как MIN_HEAP в заголовке. Три каталога переменной вместимости получают один блок `[FILE_CACHE_A,ncMemoryEnd)` через MEMORY/ARENA и ALLOC. Ни BSS, ни каталоги не записываются в COM. NC не использует MAINREGISTER: эта операция нужна для уже размещённых буферов с точным адресом. MODULE_LOAD проверяет образ и выделенный блок каталогов, а FILE_EXEC при замене MAIN-программы освобождает все блоки её владельца, в том числе при пересечении только с хвостом.

Публикуемый memTop учитывает MAIN-DLL, чужие зарегистрированные буферы и резерв FONT; CLI и соблюдающие memTop локальные кучи не могут затереть GFX. При освобождении граница пересчитывается. Системные резервы FONT используют отдельные слоты; прямой legacy SET_MEM_TOP ещё не объединён с реестром. Код, который игнорирует и memTop, и объявленный диапазон/профиль, аппаратно защитить нельзя. Замену ядра, аппаратный Reset и сохранность банков при работе гостевой ОС нужно проверять отдельно.

## Граница графики

`source/ui-gfx/abi.inc` задаёт формат записей графической DLL, а очередь и доставку обслуживает MEM 1.3. CORE привязывает UI_GFX через MODULE_SCOPE на время интерактивной работы и выбирает MX_QUEUE_DLL. Обычная запись занимает до 96 байт, для более длинной CORE сначала вызывает reserve. Буфер очереди NC занимает 3072 байта в его EXEC по D000h. У EDIT собственная очередь на 1024 байта в его EXEC. MEM передаёт код банка, адрес и точную длину потока, а DLL копирует его одним FAR-вызовом и разбирает в MAIN.

Каждая команда содержит операцию, цвет, координаты, инверсию, значения HL/DE/BC/AF и при необходимости данные. Текст, элементы окон и палитры передаются в очереди, перенос битмапы выполняют развёрнутые ядра в MAIN. NC_CORE перед переносом сохраняет исходную палитру в команде и обновляет свою таблицу цветов. MEM отправляет пачку при заполнении буфера и перед синхронными вызовами. CORE явно завершает кадр и проверяет ошибку отправки. Перед ожиданием CORE отправляет готовый кадр. Ожидание и отсчёт автоповтора работают локально в EXEC через io_bankKeyPoll. Нажатие и очередной повтор декодирует BIOS в MAIN по единой таблице. Для сырого кода используется io_bankKeyScan. NC хранит собственный IO_KEY_STATE в KOI8 и сохраняет его при возврате к резиденту. CORE считывает Shift через io_bankKeyShift и выбирает свои подписи с учётом ширины шрифта. При первом выводе каждого состояния подписи входят в графический пакет. При повторе NC_CORE передаёт UI_GFX дескриптор своего сохранённого битмапа и его палитры. Курсор обслуживается отдельным запросом CORE. Пустой опрос и чтение Shift сохраняют банк и очередь. Ctrl приходит в CF события io_bankKeyPoll. Перед запуском программы или выгрузкой DLL CORE закрывает очередь и возвращается из MODULE_SCOPE, чтобы снять закрепление модуля.

Строковые и арифметические операции CORE локальны: используются общие исходники upperCase и развёрнутого memmove 8080. Сортировка не делает банковых BIOS-вызовов для каждого символа. Ветвь MAIN сохраняет прежние прямые вызовы.

DOS хранит 32-битные поколения изменений каждого диска независимо от временного наблюдателя CLI. CORE сравнивает один 32-байтный снимок и отменяет только кэш изменившихся дисков. Запись CLI-истории на B: не заставляет перечитывать A:/H:. Во время активности NC сохраняются более точные уведомления по каталогу. Для неактивного NC поколение диска консервативно отменяет все его каталоги.

## Проверки и сравнение

- `check-nc-bank-graphics.py`: реальное исполнение обоих путей на 8080, сравнение VRAM и курсора для заголовков, выделения, текста, прокрутки, тулбара и открытия/закрытия диалога; 4/6/8px, примитивы Fast12K.
- `check-nc-sort.py` и тот же тест с `--nc bin/NC_CORE.i80 --symbols bin/NC_CORE.sym`: порядок, независимость имени/расширения, кириллица, неизменность каталогов и выделение.
- `check-main-module-claim.py`: код/BSS, CLI без пересечения, запрет удаления активной DLL, fallback legacy, явные запросы рабочих областей FONT/RUN и границы диапазонов.
- `check-nc-bank-regressions.py`: возврат после затирания MAIN, локальный опрос, F1 с кодом 00h и флаг Ctrl, вход в каталог после чужого контекста, учёт пропущенных файлов с 32-битным переносом.
- `check-resident-shell.py`: поиск оболочки, передача A/CF модуля, возврат владельца/стека, освобождение и переполнения поколений; межбанковый транспорт в этом тесте заменён стендом.
- Общие проверки раскладки DOS, резидентной памяти, SDK ABI и геометрии диалогов остаются обязательными.

Для сравнения скорости запускать A:\NC_MN.COM и A:\NC.COM с одинаковым шрифтом, каталогами, сортировкой и состоянием кэша. Холодное чтение файлов/каталогов измерять отдельно. Время реакции включает подготовку пакета, FAR-копирование, вызов MAIN, перенос битмапа, дорисовку и статус. Сравнение только ядра копировщика не подтверждает скорость интерфейса.

DOS-лаунчер выводит копирайт до поиска/чтения CORE. При возврате к уже инициализированному резиденту CORE не печатает заставку заново и очищает исполненную команду. Графический запрос CURSOR передаёт позицию, режим и цвет в MX_REGS и выполняет один XOR. Клавиша и Ctrl возвращаются из локального IO без обращения к DLL. При привязке GFX также передаёт идентификатор движка FNT1 в CORE для блока Font на инфопанели.

FONT перед загрузкой инициализатора и RUN перед проверкой диапазона вызывают MEM_OP_MAINCLAIM для своей рабочей области. Неактивная GFX при пересечении освобождается, memTop пересчитывается; CORE остаётся в EXEC и восстанавливает DLL при следующем входе. Системные резервы шрифта эта операция не отменяет.
