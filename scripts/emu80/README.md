# Emu80: профиль «Специалиста-MX2»

Для тестов агента обязателен собственный **видимый** экземпляр без звука. Можно сразу включить фиксированную скорость **32×**. Full throttle пока не работает из-за ошибки эмуляции таймера. Выбор слота, настройка скорости и проверка владельца описаны в [инструкции для Emu80](../../.agents/skills/mxos-emu80/SKILL.md).

Собственные аппаратные модели хранятся в `source-emulators/emu80/`. Полный upstream и runtime оставляйте вне отслеживаемых каталогов.

Для скрытой проверки используйте `run.ps1 -Hidden`. Скрипт выбирает платформу Qt offscreen. Установщик `deploy-build.ps1` помещает в runtime платформенный плагин `_qtplugins/platforms/qoffscreen.dll` из того же комплекта Qt, что и остальные DLL. Если в старой копии есть только qwindows.dll, скрытый запуск завершается сообщением в консоли до создания процесса.

## Клавиатура MXOS

Тест `benchmark-nc-repeat.py` по умолчанию измеряет стрелки панели со штатным автоповтором драйвера. В MAIN он считывает задержки BIOS, в EXEC устанавливает в загруженной тестовой копии NC значения KEY_REPEAT_FIRST и KEY_REPEAT_NEXT и проверяет счётчик после каждого шага. Системный образ сохраняется. Для замера с настройками выпуска служит `--repeat application`. Интервалы считаются по тактам гостевого 8080.

В окне собственной сборки Emu80 клавиша End передаёт ПС (перевод строки, код 0Ah). В строке ввода MXOS она перемещает курсор в конец. PgDn дублирует End. Alt+End включает максимальную скорость на время удержания. Для сочетаний Ctrl используются левая или правая Ctrl на ПК.

По умолчанию профиль MXOS использует «Умную» раскладку. Если раньше была сохранена QWERTY, нажмите Alt+K в окне эмуляции. В английской раскладке Windows двоеточие вводится через `Shift+;`, знак равенства — клавишей `=`, а подчёркивание в собственной сборке — через `Shift+-`. Alt+Q возвращает позиционную QWERTY. В стандартной сборке Emu80 для ПС используйте PgDn.

В Windows собственная сборка Emu80 использует скан-коды для буквенно-цифровых клавиш в позиционных раскладках `Alt+J` (ЙЦУКЕН) и `Alt+Q` (QWERTY). Положение клавиш в этих режимах не зависит от языка Windows. `Insert` переключает LAT/RUS в MXOS. Позиционная ЙЦУКЕН сохраняет матрицу «Специалиста», поэтому в LAT верхний ряд `QWERTY` даёт `JCUKEN`. В «Умной» раскладке (`Alt+K`) для русского ввода выберите русский язык в Windows и RUS в MXOS, для английского — английский язык в Windows и LAT в MXOS.

## Самостоятельный CP/M для Сябра

Сценарий `scripts/emu80/run-built-profile.ps1 CPM` собирает один загрузочный ROM из внешнего `OS/CP-M/syabr-cpm-0.1.zip` и запускает отдельную платформу `specialist-cpm/`. Для сборки образов отдельно выполните `python -X utf8 scripts/images/build-cpm.py`. На старте появляется приглашение CP/M `A>`; A: — 8-МиБ файл `specialist-cpm/sdcard/CPM/CPM.DSK`, B: — RAM-диск 446 КиБ. Рабочий A: сохраняется между запусками; `run-cpm.ps1 -ResetDisk` заменяет его seed-образом без резервной копии. Инструкция, карта памяти и ограничения: [source/cpm/README.md](../../source/cpm/README.md).

`scripts/emu80/check-dos-module.py --runtime <свой runtime>` проверяет загрузку DOSMOD, запуск E через клавиатуру NC, сохранность модуля и файловый обмен/копирование больше 64 КБ.

## Самостоятельный RAMFOS с играми

Сценарий `scripts/emu80/run-built-profile.ps1 RAMFOS` собирает один системный ROM RAMFOS и запускает его с заранее заполненными RAM-дисками. Для сборки образов отдельно выполните `python -X utf8 scripts/images/build-ramfos.py`. Состав доступен в `images/RAMFOS-games.md` и `images/RAMFOS-games.json`. Все 62 нагрузки из `assets/games/ramfos-candidates.json` распределяются по 16 страницам ДОЗУ; реестр Markdown описывает тот же набор. `images/RAMFOS-system.bin` содержит полноценное ядро, родной ROM-каталог и `Monitor2.sys`; `images/RAMFOS-games.ramdisk` — 16 последовательных страниц по 64 КБ в формате загрузки RAM-диска Emu80. Сейчас игры занимают 12 страниц, оставшиеся четыре пусты. В RAMFOS при старте открывается RAM-страница 0. Короткие имена игр содержат последние три цифры RF-ID; исходные имена, статусы, адреса и хеши сохраняются в отчёте. Это испытательная коллекция: признаки ABI и включение в образ не подтверждают совместимость.

```powershell
python -X utf8 scripts/images/build-ramfos.py
python -X utf8 scripts/images/check-ramfos.py
powershell.exe -NoProfile -File scripts/emu80/run-ramfos.ps1
```

Сборщику нужна внешняя библиотека `D:/Projects/RetroPC/Specialist`; другой корень задаётся через `--library`. Из неё читаются проверенные по хешам игры и `OS/RAMFOS-master/RomDisk/Monitor2.49152.sys`. Исходные файлы не изменяются. Штатные COM/EXE/I80 включаются как исполняемые EXE, RKS — через загрузчик Монитора-2. Для большинства raw-нагрузок адрес 0000h пока предположен реестром.

Профиль использует тот же `SPECIALIST_EMU80_DIR`, но отдельную платформу `specialist-ramfos/`. Профиль, системная flash и RAM-диски MXOS не заменяются. `-PrepareOnly` подготавливает файлы без запуска окна. Параметр `ramDisk.fileName` загружает игры после привязки всех 16 страниц. Каждый запуск через этот сценарий начинает с исходного набора; автосохранение выключено. Для сохранения изменений используйте Save RAM disk As в Emu80 и отдельный файл, затем открывайте его вручную. Хвост каждой страницы с `FFBBh` оставлен свободным: там RAMFOS проверяет память. Старые `RAMFOS-games-NN.bin` больше не используются. Аппаратный вход STD через PUSH/RST обходится тем же начальным режимом MX, что и в профиле MXOS. Переключение на RAM выполняет загрузчик без стека; совместимость игр, сброс после подмены Монитором-2 и реальные аппаратные тайминги требуют отдельной проверки.

Сам Emu80 устанавливается **снаружи проекта**. Репозиторий хранит конфигурацию, скрипты, схемы и собственные расширения, а не Qt DLL, пользовательские настройки и изменяемые диски.

Рекомендуемый вариант — отдельный portable-каталог рядом с прежним Emu80, например `D:\Projects\RetroPC\Specialist\Emulator\Emu80-MXOS`. Не устанавливайте поверх старых профилей MXOS My.

```powershell
powershell.exe -NoProfile -File scripts/emu80/install.ps1 -DestinationDirectory D:\Projects\RetroPC\Specialist\Emulator\Emu80-MXOS
$env:SPECIALIST_EMU80_DIR = 'D:\Projects\RetroPC\Specialist\Emulator\Emu80-MXOS\Emu80qt_40571'
powershell.exe -NoProfile -File scripts/emu80/run.ps1
```

Установка загружает около 28 МБ и проверяет SHA-256 из `upstream.json`. Версия runtime зафиксирована: 4.0.571. Старый установленный 4.0.379 не подходит этому профилю. `referenceCommit` фиксирует исходники, использованные при подготовке интеграции; это не утверждение, что release ZIP собран из этого SHA.

Прямой вызов `scripts/emu80/run.ps1` использует готовые 64-КиБ образы системы и ROM-диска H:. Скрипт принимает также `-EmulatorDirectory`, `-SystemImage` и `-PrepareOnly` (подготовка файлов без запуска). Он копирует только файлы в `specialist-os/` внутри runtime и не редактирует `emu80.conf`, штатные профили или сохранённые настройки. Закройте экземпляр этой установки перед повторным запуском. Переменную можно сохранить на уровне пользователя Windows; скрипт читает её и оттуда. Если окружение VS Code ещё содержит путь к обычной сборке, flash-запуск проверяет также актуальную пользовательскую переменную и выбирает установку с маркером `SpecialistFlashDisk`. Явный `-EmulatorDirectory` не подменяется.

Профиль задаёт CPU 8080 2 МГц, 16 страниц RAM-диска, непереключаемые 32 байта, две страницы ROM по 32 КБ, стандартный режим и переключение 8/16 цветов. Сброс начинается сразу с MX-страницы ROM (режим 2). Аппаратный вход через `LXI SP,F7FFh; RST 0` в STD-странице не используется: Cpu8080 Emu80 реализует PUSH через запись младшего байта перед старшим, тогда как загрузочная последовательность MX2 требует обратного порядка для переключения через F7FEh. Загрузчик MX-страницы копирует DOS без использования стека; вход DOS на C000h сам устанавливает SP. Исходный системный образ не изменяется. Это обход дефекта порядка шинных операций ядра Emu80, а не полная эмуляция аппаратного сброса; после исправления ядра можно вернуть начальный режим 3. Проверка загрузочного пути без стека: `python scripts/emu80/check-boot.py`. Она исполняет ограниченный набор команд загрузчика до установки SP в DOS; это проверка обхода при старте, а не тест загрузки NC или всего Emu80. Обычный профиль H: использует тот же 64-КБ образ и протокол ROM64KX.COM, что и EMU. Отдельный flash-профиль поддерживает запись на четыре AT29C040A (см. ниже). Порты второго ВВ55 не заняты SD-контроллером или мышью. Файлы `.rks` запускаются из NC через RUN/Monitor2; штатный загрузчик Commander не используется как замена загрузчика MXOS.

Источник аппаратных моделей: `source-emulators/emu80/`. Полный upstream хранится в отдельном checkout `emu80-src`.

## Сборка и запуск flash-профиля

Собственная сборка содержит также `SpecialistMx2VideoRam` для независимых MX/STD-цветов. `run.ps1` определяет наличие модели по манифесту сборки и создаёт `specialist-os/launch.conf` с `MX2_MODELS`. Это работает и с обычным ROM-профилем на собственной сборке. Прямое подключение клавиатурного ВВ55 к штатному SpecVideoRam может затирать MX-цвет при сканировании клавиатуры; официальная сборка без модели проекта не получает это исправление. Проверка: `python scripts/emu80/check-interface.py --runtime <Emu80-flash-test>` (для анализа PNG требуется Pillow). Она проверяет независимость MX-защёлки, STD-цвета, возврат MX-цвета после STD и курсор NC после удаления файлов.

Профиль **MMX Flash + floppy** использует сборку Emu80 с моделями `SpecialistFlashDisk` и `SpecialistSystemFlash`. На `C:` подключается системная flash 512 КиБ, на `H:` внешняя flash 2 МиБ, на `A:` дискета программ 720 КиБ. AUTOEXEC устанавливает AT512KS.COM, AT2MXF.COM и FLOPPY.COM соответственно.

```powershell
.\scripts\emu80\run.ps1 -Flash -ResetFlash -SystemImage C-Flash-128k-MMX-System.bin
```

`-ResetFlash` напрямую заменяет оба рабочих образа. `-UpdateSystemFlash` обновляет только A:, когда изменился SHA-256 собранного системного образа; если сборка не менялась, рабочий C: сохраняется. Прямой запуск без обоих ключей сохраняет существующий A: и его фактический размер независимо от seed. Резервные копии не создаются. Для проверки ROM без записи добавьте `-ProtectSystemFlash`: та же модель запрещает /WE через J4; чтение банков остаётся доступным. На любом диске DOS отклоняет удаление файлов System или Read-only, а также замену Read-only. System без Read-only можно изменять: атрибут сохраняется. При удалении NC выводит предупреждение. При ошибке запуска AUTOEXEC или его команды DOS возвращает встроенный драйвер A: и запускает ROM64KX.COM, затем NC. Это не обнаруживает зависание программы или её внутреннюю ошибку. `AT2MX.COM` последовательно записывает сектор и ждёт готовности по DQ7. `AT2MXF.COM` выполняет конвейерную запись; DOS распределяет новые кластеры по чипам через обычную FAT-цепочку. Оба драйвера читают одни и те же образы.

Нужны Python, Git, MSVC 2022 Community с Windows SDK и Qt 5.15.2 MSVC x64. Воспроизводимая подготовка Qt (около 36 МБ, проверка SHA-256; нужен 7-Zip):

```powershell
git clone https://github.com/vpyk/emu80v4.git D:\Projects\RetroPC\Specialist\Emulator\emu80-src
git -C D:\Projects\RetroPC\Specialist\Emulator\emu80-src checkout e5cfece5ce16e8da01d0fc68b97cc510234246b7
powershell.exe -NoProfile -File scripts/emu80/setup-build.ps1 -ToolsDirectory D:\Projects\RetroPC\Specialist\Emulator\Emu80-build
$env:SPECIALIST_EMU80_SOURCE_DIR = 'D:\Projects\RetroPC\Specialist\Emulator\emu80-src'
$env:SPECIALIST_EMU80_QT_DIR = 'D:\Projects\RetroPC\Specialist\Emulator\Emu80-build\qt\5.15.2\msvc2019_64'
powershell.exe -NoProfile -File scripts/emu80/build.ps1
powershell.exe -NoProfile -File scripts/emu80/deploy-build.ps1 -SourceDirectory $env:SPECIALIST_EMU80_SOURCE_DIR -QtDirectory $env:SPECIALIST_EMU80_QT_DIR -BuildDirectory D:\Projects\RetroPC\Specialist\Emulator\Emu80-build\flash-gui -DestinationDirectory D:\Projects\RetroPC\Specialist\Emulator\Emu80-MXOS-flash
$env:SPECIALIST_EMU80_DIR = 'D:\Projects\RetroPC\Specialist\Emulator\Emu80-MXOS-flash'
```

После этого запускайте задачу **Build and run Emu80 MMX Flash + floppy**. Для обновления собственной сборки закройте её окно и выполните `powershell.exe -NoProfile -File scripts/emu80/build.ps1 -Deploy`. Сценарий пересобирает модель и обновляет только runtime с маркером собственной сборки. Скрипты читают эти переменные также с уровня пользователя Windows.

**Build and run Emu80 MMX Flash + floppy** собирает системную flash, внешний диск и дискету. **Run Emu80 MMX Flash + floppy** берёт готовые образы из `images/`. Полный образ H: создаёт цель `Games2M` одновременно с четырьмя файлами для прошивки. Новый C: получает включённую защиту Software Data Protection (SDP), которую штатный AT512KS учитывает при записи.

Сборщик `scripts/images/build-image.ps1 Floppy720` создаёт `images/A-Floppy-720k-Programs.img`. Сквозная проверка `check-floppy.py` использует временную копию дискеты и актуальный образ H:.

Для подключения рабочей дискеты MMX в Windows закройте Emu80 и выполните `scripts/emu80/imdisk-floppy.ps1 Mount`. После работы выполните `scripts/emu80/imdisk-floppy.ps1 Unmount` и запустите **Run Emu80 MMX Flash + floppy**. Параметр `-DriveLetter X` выбирает букву в Windows.

Обе задачи **MMX Flash + floppy** сверяют SHA-256 образов A:, C: и H: с последней установкой в `deployment.json`. При изменении исходного образа заменяется его рабочая копия. При первом запуске со старой записью любой образ без сохранённой контрольной суммы устанавливается заново. Ручные вызовы `run.ps1 -Flash`, `-UpdateSystemFlash` и `-ResetFlash` по-прежнему выбирают прежние режимы развёртывания.

### Пул видимых MCP-экземпляров

Для очереди из нескольких игр `WorkerMachine(size, port, artifact_root)` держит одно окно на работника. Первый `start(disk=H, system=C, floppy=A)` запускает видимую машину, следующие вызовы подготавливают второй комплект носителей и выполняют полный холодный запуск гостя в том же процессе. Штатный MCP `switch_platform` переключает два имени одной конфигурации, Qt сохраняет основной HWND. PID, HWND, номер холодного запуска и активная конфигурация попадают в протокол. Простой `emu_reset` остаётся аппаратным сбросом для проверки возврата. Основная и банковая RAM при нём сохраняются, а содержимое flash перечитывается при создании модели. Проверка `python scripts/emu80/check-cold-boot.py` выполняет три холодные загрузки, проверяя окно, маркеры в MAIN и двух банках и чтение меняющегося H:.

Пул использует порты 19781–19796 на loopback Windows. Для кампании нужен Python 3 и пакет psutil. Из корня репозитория выполните `python -m pip install psutil`, затем `scripts/emu80/build.ps1 -Mcp -PoolTemplate`. Сборщик берёт исходники фиксированной ревизии и каталог Qt из тех же параметров, что и обычная сборка. На общей сетевой копии используйте локальный checkout по инструкции сборки. Шаблон устанавливается в `%LOCALAPPDATA%\Specialist-OS\emu80\pool-template`. Другой каталог указывается через `SPECIALIST_EMU80_POOL_TEMPLATE`. Для загрузочного профиля нужны образы C:, H: и A: из целей SystemEmuWritable, Games2M и Floppy720.

Модуль [mcp_pool.py](mcp_pool.py) выдаёт `with lease(size=8) as slot`. Размер 1–16 ограничивает автоматический выбор первыми N портами; явный `port=19796` закрепляет отдельную пробу за этим портом. При занятости лимит ожидания задаёт `timeout` в секундах. Параметры `system`, `disk`, `floppy` принимают пути к исходным образам C:, H:, A:. Каждый сеанс получает свежие рабочие копии в `pool/<порт>/specialist-os`, свой `_settings`, конфигурацию с уникальным именем и `slot.artifacts` с протоколом подготовки и PID. В параметре `artifact_root` можно выбрать место протоколов вместо `.local/emu80-campaign`. Во время работы `slot.verify_owner()` сверяет живой процесс, его EXE и loopback-listener. Блокировка файла удерживается всё время аренды. После гибели работника Windows освобождает блокировку; следующий арендатор находит оставленное окно по пути EXE и уникальному аргументу конфигурации, закрывает его и восстанавливает диски из seed.

Для отдельного вручную установленного runtime `%LOCALAPPDATA%\Specialist-OS\emu80\<порт>` служит `scripts/emu80/run-mcp-slot.ps1 -Port 19782`. Он проверяет PID, обновляет C: и сохраняет рабочий H:. Порт новой MCP-сборки выбирается переменной процесса `SPECIALIST_EMU80_MCP_PORT`; `run.ps1 -Flash -Mcp -McpPort 19782 -EmulatorDirectory <runtime>` устанавливает её для своего процесса. У исторических EXE порт фиксирован при компиляции. Для ручного запуска в новом диапазоне разверните MCP-сборку через `deploy-build.ps1 -Mcp` в каталог нужного номера. Для кампании runtime создаются автоматически из одного шаблона.

Раскладка стенда — smart, матрица original. Гостевой ввод направляется в `kbd_send` экземпляра `slot.url`. В MCP-сборке проекта `emu_speed(factor=32)` включает фиксированное ускорение; `emu_speed(factor=1)` возвращает обычный темп. Для записи на 1× вызовите `mx_audio(action="start")`, выполните действие или `emu_run_for`, затем `mx_audio(action="stop")`. Сервер возвращает PCM16LE mono в `pcm_base64`, частоту `rate`, число отсчётов `samples` и признак переполнения `truncated`. Буфер вмещает первые две секунды. Записывается рассчитанный выход звуковой схемы MX до mute. Динамики хоста и мониторинг ленты выключены.

Проверка проводится последовательно командами `python scripts/emu80/check-mcp-pool.py --size 8` и `python scripts/emu80/check-mcp-pool.py --size 16`. Каждая машина удерживает свою клавишу, тест читает все 12 колонок ВВ55 при одновременно нажатых клавишах и контрольный байт отдельного H:. Проверяются владельцы портов и различные файловые объекты A:/C:/H:, отказ второй аренды, аварийное завершение работника и повторная выдача. В новом сеансе тест подтверждает фиксированную скорость 32× и записывает сигнал ВИ53 с частотой 1 кГц при 1×. Отчёты пишутся в `docs/games/mcp-pool/check-N.json`.

Для одиночной диагностики flash-драйвера можно использовать отдельный каталог Emu80-flash-test.

```powershell
powershell.exe -NoProfile -File scripts/emu80/run.ps1 -EmulatorDirectory <Emu80-flash-test> -Flash -Mcp
python scripts/emu80/check-flash.py --runtime <Emu80-flash-test> --drivers Flash FlashFst
python scripts/emu80/check-flash.py --runtime <Emu80-flash-test> --pipeline-only
# Закрыть и запустить этот тестовый процесс заново, затем:
python scripts/emu80/check-flash.py --runtime <Emu80-flash-test> --verify-persisted
python scripts/emu80/check-system-flash.py --runtime <Emu80-flash-test>
```

Flash, FlashFst и FlashSys поддерживают B=5: синхронная запись, чтение и сравнение сектора общим кодом DOS. Обычный B=1 полного сравнения не делает; DATA polling и тайм-аут остаются обязательными. В DISKBEN режим выбирается при запуске. Проверочное чтение самого бенчмарка вне измерения сохраняется.

Начальный прогон требует неизменённого seed и установленного загрузкой AT2MX.COM. FlashSys устанавливается загрузкой ОС; тест его повторно не устанавливает. После перезапуска проверка `check-system-flash.py --verify-persisted` сверяет сектора и SDP. Для отказа записи запустите профиль с `-ProtectSystemFlash` и выполните `check-system-flash.py --locked`. Ограничения модели и отдельный C++ тест описаны в `source-emulators/emu80/README.md`.

Проверка потокового BAT, вложенности и вытеснения буфера модулем запускается командой `python scripts/emu80/check-bat-buffer.py --port 19782`. Укажите свободный установленный MCP-слот из пула 19781–19796. Стенд запускает собственный Emu80, создаёт файлы на его RAM-диске B: и закрывает экземпляр после проверки.

Проверка файлового пути: `python scripts/emu80/check-copy.py --runtime <Emu80-flash-test>`. Проверка запрета удаления и замены с атрибутами R/S/RS на C: и H:. `python scripts/emu80/check-protected-files.py --runtime <Emu80-flash-test>`. Запускайте её на свежем тестовом образе: она создаёт тестовые файлы. Она создаёт файл через DOS и исполняет процедуру F5 из NC для копирования FONT.PF с A: на H:, проверяет каталог, FAT-цепочку и данные в образе, затем читает файлы через DOS после сброса кэша. После перезапуска тестового процесса повторите с `--verify-only`. Перед проверкой дождитесь загрузки NC. `check-system-files.py` после `check-copy.py` проверяет копирование H: → A: без отдельного подтверждения, а после перезапуска с `--verify-persisted` — содержимое скопированного файла. Старый `check-readonly.py` относится к профилю с 64-КБ ROM и не подходит профилю с автоматически загруженным FlashSys. Старый отчёт `reports/flash-2026-10-29.json` содержит имя Flash, использовавшееся для прежнего варианта с полным сравнением; его контрольные суммы относятся к тому прогону.

Звук ВИ53 использует `SpecMxPit8253SoundSource`. Сверка XML crossboard: GATE0/1/2 подтянуты к единице, CLK0/1 получают 2 МГц, OUT1 тактирует CLK2. Два элемента ЛЕ1 формируют `NOT PC5 AND (OUT0 OR OUT2)`. OUT2 не подключён к GATE0. Именно эту логику реализует штатный источник звука MX в Emu80; источник `RkPit8253SoundSource` ей не соответствует. Магнитофонный выход PC7 не подмешивается в динамик. Причина слышимых шумов/разрывов пока не установлена; схема не является основанием для замены модели ВИ53. Точное соответствие схеме, цветовая палитра, запись системной flash, тайминги реального оборудования требуют отдельной проверки. Этот профиль не заявляет полную аппаратную эквивалентность MX2.

Проверка выделения кластеров и конвейера: `python -X utf8 scripts/emu80/check-flash-allocation.py --runtime <Emu80-flash-test>`. Она создаёт файлы на тестовом H:, читает их Flash/FlashFst и исполняет F5 NC; отчёты сохраняются в `docs/flash/interleave-001/`. Проверяется также B=5 у Flash, FlashFst и FlashSys. `check-driver-api.py` проверяет дескрипторы, инфо-панель NC, сохранность стека и отказ при ошибке чтения/сравнения. `check-diskbench-flash.py` проверяет оба режима меню DISKBEN. Эти сценарии меняют только отдельную установку Emu80-flash-test; результаты и снимки экрана сохраняются в `docs/flash/driver-api/`.

Проверка встроенного ROM-драйвера: `scripts/emu80/check-rom-banks.py`. Сценарий работает только с отдельным Emu80-flash-test; подготовительные фазы `pattern` и `relocate` меняют его системный образ при закрытом эмуляторе. Фаза `read` проверяет тома 128/256/512 КБ с запрещённой записью, `boot` — загрузку перенесённых выше 64 КБ файлов, `rom64` — старую раскладку MX2. Для варианта без Checked нужен `bin/DOS-rom-legacy.sys/.lst`, собранный из DOS.asm с `-DDISK_DRIVER_CHECKED=0`. Отчёты сохраняются в `docs/rom-banks/`.

Проверка ёмкости системной модели: `python -B scripts/emu80/check-system-capacity.py --runtime <Emu80-flash-test>`. Она записывает последний сектор тестового C: и проверяет остальные байты, длину образа, чтение встроенным драйвером и software ID. После перезапуска используйте `--verify-persisted` для проверки данных и SDP. На отдельно запущенном профиле с `-ProtectSystemFlash` используйте `--locked`. Проверены все три ёмкости без дополнения образов до 512 КБ.


### COM/EXE MXOS2 и пересборка образов

Утилиты теперь собираются в CPU/I80. COM и EXE на дисках имеют общий 16-байтный заголовок, RKS сохраняет стандартный контейнер. EXE и RKS передаются через NC.EXT в RUN.COM; EXE без ключа спрашивает режим. RAMFOS.MON загружается ключом -RF. Прежние сырые EXE/COM из старых образов не подходят новому DOS.

При обновлении пересоберите SystemEmuWritable и Games2M. Сборщик Games2M одновременно создаёт полный образ `H-Flash-2M-Games.bin` и четыре прошивки микросхем. Для запуска с новой сборкой используйте свой профиль Emu80 с `-Flash -ResetFlash`. Основной набор проверяется в системном flash-образе на 512 КиБ.

Проверка запуска через клавиатуру NC находится в `scripts/emu80/check-executable-ui.py`; он использует отдельный `.local/monitor-compat-001` и подтверждает владельца MCP-порта. Режим --prepare добавляет контрольные файлы только в остановленную тестовую копию H:. Ввод выполняется kbd_send без активации окна Windows. Хостовая проверка контейнеров — `scripts/tests/check-executable-v2.py`.
